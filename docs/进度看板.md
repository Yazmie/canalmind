**切分规则（C-21）**：
- **`### 第X条` 是唯一主切分单元**，一章（`## 第X章`）只作为 `chapterPath` 元数据，**不单独成 chunk**。
- **款/项按阈值条件切分**：条正文超过 `maxArticleChars`（默认 800）才下切；
  优先按款（`#### 一、`）边界，其次按项（`^N.`）边界，都不足 2 个边界时退回句子切分。
  ⚠️ 实测语料**最长条仅 528 字**，故该阈值在真实数据上**从不触发**（行为已由合成用例覆盖）。
- **正文与表格双存**：表格抽成独立 `TABLE` chunk，正文原位留 `[[TABLE:n]]` 占位标记。

⚠️ **本项踩坑（已写入复盘）**：CRLF 版文档曾静默少切一块（表格整块消失），
根因是**转义写错反斜杠数量**——同一换行写"一个反斜杠"时运行时 2 字符、能匹配真实 CRLF，
写"两个反斜杠"时 4 字符、**永远匹配不到**，且 `replace`/`split` 失败时都不报错。
详见 `docs/工程复盘/工程方法/转义与写入层的静默损坏.md`。

#### ⚠️ 两个必须如实说出的边界（⛔ 不要对外宣称"线上在用 HNSW"）

**边界一：本项目真实规模（541 行）下，规划器不会使用 HNSW —— 而且这个选择是正确的。**

| 计划 | 估算代价 | 实测耗时 |
|---|---|---|
| `Seq Scan`（规划器默认选择） | **101** | **3.43 ms** |
| 强制 `Index Scan using rag_chunk_embedding_hnsw` | 1487 | **1.39 ms** |

两者都只有毫秒级，规划器选了更简单的计划。**所以本项的准确表述是"证明索引可用、结果与精确检索一致、并量化了启用门槛"，而不是"线上正在用 HNSW"。**

**边界二（真实风险，已列为第 4 周复核项）：pgvector 的代价模型严重高估 HNSW。**

541 行上高估约 **5.7 倍**（估算 1487 vs 实际开销远低）；在 5 万行合成表上高估达 **约 80 倍**（估算 83837，而实际执行 **0.25 ms** 量级）。
**含义**：数据量增长后规划器**可能仍然不选该索引**。不能因为"≥1000 行就会选"就认为问题已解决 —— 规模测试时要按真实代价复核。

**⚠️ 顺带查出一个会让上述结论失真的坑：批量入库后必须 `ANALYZE`。**

`rag_chunk` 入库后**从未 ANALYZE**，`pg_class` 里 `reltuples = -1`、`relpages = 0`，**规划器此前是在没有统计信息的情况下做决定**。
ANALYZE 后（`reltuples=541`）结论才稳定。**"表里有数据"不等于"规划器知道表里有数据"** —— 这类偏差不报错，只会让 `EXPLAIN` 结论误导人。

**已修复到代码里**：`RagChunkRepository.analyzeChunkTable()`，并在 `PgVectorIngestCli` 写完库后**紧接调用**。
已用**重跑入库**验证：CLI 执行后 `reltuples` 自动为 541，不再依赖手工 ANALYZE；且**重跑幂等**（541 → 541，无重复行）。

**🐛 另一个发现：重跑入库会让表膨胀（upsert 产生死元组）**

重跑一次入库后，`pg_class.relpages` 从 **59 涨到 116**（行数仍 541），`relallvisible` 变为 0 —— `ON CONFLICT DO UPDATE` **每次更新都留下死元组**。
**含义**：反复重跑入库会持续膨胀表与索引。本项目当前规模无影响，但**批量重灌前应 `VACUUM`**（或接受膨胀），已记为运维注意项。**这不影响检索正确性**。

**🔬 带过滤查询的少返回（`iterative_scan`）：真实语料上未能复现，原因已查明**

在**真实 541 行表**上实测：即使用**最苛刻的文档过滤**（最小文档 14 行，`LIMIT 10`，强制走向量索引），**仍返回满 10 行，未出现少返回**。

**原因**：语料 26 篇文档、每篇 14~30 行，**单篇占比 ≥2.6%**，而 HNSW 默认 `ef_search=40` 个候选按比例足以命中 10 行 —— **过滤不够稀疏，触发不了该退化**。进一步实测（5 万行 + 0.2% 稀疏过滤）时，**规划器压根没用 HNSW**，而是走 `cat` 列 btree 索引取全部 100 个匹配行再精确排序（**这是更优计划**），**该退化路径从未被进入**。

⚠️ 早前那组"默认只返回 2 行、加 `iterative_scan` 恢复 10 行"的数字出自**合成 3000 行表**，
**⛔ 不得当作已在本项目验证过的结论**。如实结论是：**该风险在本项目当前规模下不成立**。

**库级会话参数（作为机制保障保留，零成本防未来规模增长）**

```sql
ALTER DATABASE canalmind SET hnsw.iterative_scan = relaxed_order;
ALTER DATABASE canalmind SET hnsw.max_scan_tuples = 20000;
```

理由：`hnsw.*` 是**会话级**参数，而"在应用里 SET 一次"在**连接池**下不可靠——只作用于当前物理连接，
于是"结果条数对不对"会**随机取决于本次请求落到哪条连接**（见 `工程复盘/检索工程/会话级参数与连接池.md`）。
**库级设置由机制保证所有新会话一致，不依赖调用方自觉。** 实测新会话（含 `canalmind` 用户）`SHOW` 得到
`relaxed_order`；连到未建 vector 扩展的库则报 `unrecognized configuration parameter`。

⚠️ **一个反直觉的实测细节**：对 `hnsw.*` 执行 `SHOW` **本身不会触发扩展加载**，
所以全新会话里先 `SHOW hnsw.iterative_scan` 可能报"未识别参数"。**判断是否生效要用真正用到向量的查询，不能只看 `SHOW`。**

**🐛 另一个新发现：HNSW 建索引会静默超出 `maintenance_work_mem`**

5 万行 × 1024 维合成表上建索引时 PostgreSQL 发出
`NOTICE: hnsw graph no longer fits into maintenance_work_mem after 13939 tuples`（默认 `maintenance_work_mem = 64MB`）。
**该规模下 HNSW 图不再是全质量构建，召回率会下降但不报错。** 对本项目 541 行**无影响**（未触及约 1.4 万行阈值），
但**语料规模增长后会成为真问题**。**教训**：`NOTICE` 容易被忽略，建完向量索引要主动查有无该提示；**"索引建成功"≠"索引是高质量的"**。

|---|---|---|
| 无过滤 | `Index Scan using _vec_probe_hnsw` | 10 行 ✔ |

**注意它不会报错，只是悄悄返回更少结果**——正是知识库《RAG 向量索引算法和向量数据库》
第 175–184 行提醒的过滤退化场景。

## 6. 已知坑（详见 `AGENTS.md` §7.2 / §7.3，此处只留索引）

| 坑 | 一句话 | 详见 |
|---|---|---|
| **Spring Boot 不读 `.env`** | 必须 `spring.config.import` 显式导入，只写 `${}` 占位符无效 | `AGENTS.md` §7.2 |
| **JDK 路径会变** | 别硬编码 `D:\JDKmove\JDK21`，用前先 `Test-Path` | `AGENTS.md` §7.3 |
| **别用 `setx PATH`** | 1024 字符静默截断，会直接损坏 PATH | `AGENTS.md` §7.3 |
| **`spring.ai.deepseek.chat.enabled=false` 无效** | 真正的开关是 `spring.ai.model.chat=none` | `DECISIONS.md` P-01 |
| **不要引入 WebFlux / Netty** | 流式靠 JDK HttpClient 连接器已可用，实测逐个增量 | `AGENTS.md` §7.2 |
| **不要把某运行时的网络失败当"环境不能出网"** | PowerShell/.NET 连不上 DeepSeek，但 **JVM 能连** | `AGENTS.md` §7.2 |
| **PG 连接信息（已确定）** | 本机 5432 / 用户 **`postgres`**（不是 `canalmind`，那是库名）/ 口令在 `.env`；`url` 默认值**不读 `POSTGRES_PORT`**，要覆盖 `POSTGRES_URL` | 看板 §3.3 / §4 |
| **`psql -c` 传中文会坏** | PowerShell 5.1 控制台是 **GBK**，中文参数变 `invalid byte sequence for encoding "UTF8"` → **改用 `psql -f` 读 `.sql` 文件** | 看板 §4 |
| **`hnsw.*` 不能用 `SHOW` 判断是否生效** | 该 GUC 由扩展注册，`SHOW` **本身不触发扩展加载**；要用真正用到向量的查询判断 | 看板 §3.3 |
| **批量入库后必须 `ANALYZE`** | 否则 `reltuples=-1`，"表里有数据"≠"规划器知道"；已修进 `RagChunkRepository.analyzeChunkTable()` | 看板 §3.3 |
| **结论随测量方式变化时先怀疑测量方式** | 我在同一问题上连续错三次（漏 ANALYZE / 伪造统计 / 解析截断） | `工程复盘/工程方法/结论随测量方式变化时先怀疑测量方式.md` |
| **别用 PS 的 `Set-Content -Encoding UTF8`** | **PS 5.1 的 `UTF8` 会写入 BOM**（`UTF8NoBOM` 在 5.1 不存在），本项目文件要求无 BOM | `DECISIONS.md` 2026-09-21 |
| **改 UTF-8 文件的正确姿势** | 用 `edit` 工具；必须用 PowerShell 时用 `[System.IO.File]::WriteAllText($f,$t,(New-Object System.Text.UTF8Encoding($false)))` | `DECISIONS.md` 2026-09-21 |
| **语料是 26 篇不是 28 篇** | C-20 最终定为 **7 主题类、编号 01–26 连续**；"28 篇"指篇目总数口径，"28"不是最大编号 | `docs/规则语料/README.md` §2 |
| **改语料后必跑校验** | `python backend\scripts\validate_corpus.py`，退出码 0 才算通过 | `DECISIONS.md` C-20 |
| **`.ps1` 必须带 BOM** | PS 5.1 读无 BOM 的 `.ps1` 会按 GBK 解析，中文全乱、语法报错 | `DECISIONS.md` 2026-09-21 |
| **`edit` 工具写的是无 BOM UTF-8** | 改完 `.ps1` **必须补回 BOM**（`.md`/`.py`/`.sql` 则相反，要求无 BOM） | 附录 A1 |
| **`hnsw.*` 参数只在加载扩展的会话存在** | 单发 `SET` 看似成功，新会话 `SHOW` 报 `unrecognized configuration parameter`；须 `psql -f` 同一会话 | 附录 A / `DECISIONS.md` |
