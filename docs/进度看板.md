**切分规则（C-21）**：
- **`### 第X条` 是唯一主切分单元**，一章（`## 第X章`）只作为 `chapterPath` 元数据，**不单独成 chunk**。
- **款/项按阈值条件切分**：条正文超过 `maxArticleChars`（默认 800）才下切；
  优先按款（`#### 一、`）边界，其次按项（`^N.`）边界，都不足 2 个边界时退回句子切分。
  ⚠️ 实测语料**最长条仅 528 字**，故该阈值在真实数据上**从不触发**（行为已由合成用例覆盖）。
- **正文与表格双存**：表格抽成独立 `TABLE` chunk，正文原位留 `[[TABLE:n]]` 占位标记。

### ⚠️ 已验证的业务风险：**带过滤条件的 HNSW 查询会少返回结果**（重要，入库前必读）

实测（3000 行 × 1024 维，过滤条件 `doc_id='doc-3'`，实际 116 行匹配，`LIMIT 10`）：

| 场景 | 计划 | 实际返回 |
|---|---|---|
| 无过滤 | `Index Scan using _vec_probe_hnsw` | 10 行 ✔ |
| **带过滤（默认设置）** | `Index Scan using _vec_probe_hnsw` | **仅 2 行** ⚠️ |
| 带过滤 + `hnsw.iterative_scan=relaxed_order` | `Index Scan using _vec_probe_hnsw` | **10 行** ✔ |

**原因**：HNSW 是近似索引，`LIMIT` 在**索引扫描阶段**就被满足，
于是只取回 `ef_search` 个近邻后按过滤条件筛，命中的可能远少于 `LIMIT`。
**注意它不会报错，只是悄悄返回更少结果**——正是知识库《RAG 向量索引算法和向量数据库》
第 175–184 行提醒的过滤退化场景。

**对本项目的影响与对策**：我们的检索**天然带过滤**（按文档版本 `effective_from/to`、
按 `doc_id` 限定范围）。故：

- 入库实现时**必须显式处理**：为连接执行 `SET hnsw.iterative_scan = relaxed_order`
  （或把过滤条件下推到检索之外），**不能依赖默认值**
- 该风险**纳入第 4 周消融实验对照项**，并作为 badcase 记录进《评测报告》
- 记录于 `DECISIONS.md` 变更日志
