#### 讲一下RAG的完整流程？你是怎么做文档切分的？

**参考答案：** RAG全称检索增强生成，核心是“先检索相关知识，再让大模型基于知识生成答案”，从根源上减少大模型幻觉。项目里的完整流程分为**离线预处理**和**在线检索生成**两大阶段：

**离线预处理阶段（知识库构建）：**

1. 文档加载：读取PDF、TXT格式的航运文档（报关规则、运河通行规范、港口收费标准等），提取纯文本内容

2. 文档清洗：去除页眉页脚、多余空格、无效符号，对表格、列表格式做结构化处理

3. 文本切分：按照策略把长文档拆分成合适大小的文本块（Chunk）

4. 向量化：调用Embedding模型，把每个文本块转换成向量

5. 存储：向量和对应原文、文档来源一起存入PgVector向量数据库

**在线检索生成阶段（用户提问时）：**

1. 用户输入问题，同样调用Embedding模型转换成问题向量

2. 向量检索：在PgVector中做相似度匹配，召回Top K个最相关的文本块

3. 结果重排序：对召回结果做相关性二次校验，过滤低相关内容

4. Prompt拼接：把检索到的知识库内容、对话历史、系统提示词拼接成完整的Prompt

5. 大模型生成：调用大模型API，流式返回生成的答案

6. 答案返回：同时附带引用的知识库来源，提升可信度

**关于文档切分：** 我没有用单一的固定长度切分，而是采用\*\*“固定长度\+语义重叠”\*\*的策略：

- 基础块大小设置为512个Token，块之间保留50个Token的重叠，避免语义被截断

- 针对航运文档里大量的条款、流程、列表结构，做了自定义切分规则：遇到标题、序号、换行分隔的独立条目时，优先按语义边界切分

- 技术上基于Spring AI的`DocumentSplitter`做了扩展，自定义了分隔符和切分逻辑，保证每个文本块都有完整独立的语义

#### 为什么选PgVector？不用Milvus、Chroma这类专用向量数据库？

**参考答案：** 主要是结合**项目定位、技术栈、部署成本和场景规模**综合考量的，不是专用向量库不好，而是PgVector更适合当前这个项目的场景：

1. **技术栈统一，学习和维护成本低** 项目整体是Java技术栈，业务数据本来就用PostgreSQL存储，PgVector是它的扩展，不用额外部署一套向量数据库组件，不用学习新的查询语法和运维知识，开发和部署都更轻量。

2. **事务与数据一致性优势** 向量数据和业务数据（文档信息、会话记录）存在同一个数据库里，知识库更新的时候，向量和原文可以在同一个事务里提交，不会出现数据不一致的问题。

3. **场景匹配度高** 这个项目是垂直领域的中小规模知识库，预计文档量在万级以内，PgVector完全能满足性能需求。它支持余弦相似度、HNSW索引，对于十万级以内的向量规模，查询延迟和专用向量库差距不大。

4. **扩展性有保障** 如果后续知识库规模扩大到百万级以上，也可以平滑迁移到Milvus等专用向量库，因为RAG的检索层是抽象设计的，底层替换不影响上层业务逻辑。

简单说就是：**小项目用PgVector够用、省事、不折腾，把精力放在业务逻辑和RAG效果上，而不是中间件运维上**。

#### 为了提升回答准确率，你做了哪些Prompt工程优化？

**参考答案：** 我主要从**角色约束、输出规范、知识边界、场景适配**四个维度做了优化，核心目标是让大模型严格基于知识库回答，不编造信息，同时符合航运场景的专业表达：

1. **明确角色与专业背景** 系统提示词里明确设定身份：“你是平陆运河航运物流专业客服，精通内河航运、报关报检、港口收费、船舶通行规则”，先给大模型设定专业人设，输出语气和术语会更贴合场景。

2. **严格的知识边界约束** 明确规则：**必须完全基于检索到的知识库内容回答，禁止编造知识库以外的信息**。如果检索结果里没有相关内容，必须直接回答“抱歉，这个问题我暂时无法解答，已为您转接人工客服”，不能自由发挥。

3. **结构化输出规范** 要求回答分点清晰、专业准确；涉及费用、流程、时间等关键信息时，必须准确引用原文；答案末尾必须标注信息来源（如「来源：平陆运河船舶通行收费标准2026版」），既提升可信度，也方便人工校验。

4. **航运场景专项优化** 针对航运领域的专业术语、简称、固定表达，在Prompt里做了术语统一说明，比如“六景港区”“过闸费”“EDI申报”等，避免大模型理解偏差或表述错误。

5. **多轮对话上下文引导** 拼接历史对话时，明确标注“以上是历史对话记录，请结合上下文理解当前问题”，避免多轮对话后话题跑偏。

通过这些优化，专业问题的回答准确率从最初的60%左右提升到了85%以上，幻觉率大幅下降。

#### 多轮对话的上下文是怎么管理的？上下文长度超限怎么处理？

**参考答案：上下文管理方式：**

1. 每个会话绑定唯一的sessionId，用户的每轮提问和AI回复都以会话为单位存储

2. 活跃会话的历史消息缓存到Redis里，设置30分钟过期，提升读取速度；历史全量同时落库到MySQL，用于后续分析和回溯

3. 每次用户提问时，从Redis取出该会话的历史消息，和当前问题、检索到的知识库内容一起拼接成Prompt，传给大模型

**上下文长度超限处理：** 我采用了\*\*“滑动窗口\+摘要压缩”\*\*的两级策略：

1. **第一级：滑动窗口策略** 默认保留最近8轮对话，超出的部分直接截断丢弃，优先保留最新的对话内容。因为航运客服场景的问题大多是短链路，8轮足够覆盖完整的咨询流程。

2. **第二级：对话摘要压缩** 如果单轮对话内容很长，即使8轮也会超限，就触发摘要压缩：调用大模型把更早的历史对话总结成100字以内的核心摘要，用摘要替代原始对话记录，既保留上下文语义，又大幅减少Token占用。

同时我会在拼接Prompt前做Token数量估算，超过大模型上下文窗口的70%就自动触发上述策略，保证不会超限。

#### Function Calling的实现原理是什么？你是怎么封装业务工具的？

**参考答案：实现原理：** Function Calling（函数调用）的核心是让大模型具备“判断什么时候该调用外部工具”的能力。流程是：

1. 开发者提前把工具函数的名称、功能描述、参数格式（JSON Schema）告诉大模型

2. 用户提问后，大模型先判断：这个问题能不能直接回答？需不需要调用工具？

3. 如果需要调用，大模型会返回指定格式的JSON，包含要调用的函数名和对应的参数

4. 后端接收到后，执行对应的业务函数，拿到执行结果

5. 把工具执行结果再传给大模型，让它基于结果生成最终的自然语言回答

**项目里的封装方式：** 我是基于Spring AI原生的`FunctionCallback`机制来实现的：

1. 定义业务工具类，比如`ShippingFeeCalculator`（运费估算工具），在方法上添加`@Tool`注解，写明工具功能描述和参数说明

2. 每个工具方法接收结构化参数，做参数校验，执行业务逻辑，返回结构化结果

3. 在Spring AI的ChatClient里注册这些工具函数，大模型就可以自动识别和调用

4. 同时做了异常处理：如果工具执行出错，会返回错误信息，大模型会基于错误信息给用户友好提示，而不是直接报错

比如运费估算工具，用户问“从六景到广州港100吨货多少钱”，大模型会自动调用运费计算函数，传入起运港、目的港、货重参数，拿到结果后整理成清晰的费用明细返回给用户。

#### 向量检索用的什么相似度算法？阈值怎么设定的？

**参考答案：相似度算法：** 用的是**余弦相似度（Cosine Similarity）**，这也是PgVector默认支持的算法。它计算的是两个向量在空间中的夹角余弦值，取值范围是0到1，值越大表示语义越相似。 选择余弦相似度是因为它对文本长度不敏感，更适合语义检索场景，比欧氏距离更适合文本向量匹配。

**阈值设定：** 阈值是通过**测试集调试\+业务场景适配**出来的，不是拍脑袋定的：

1. 我先整理了100条标注好的航运问题和对应的正确答案，做成测试集

2. 分别测试0\.5、0\.6、0\.7、0\.8不同阈值下的召回率和准确率

3. 最终设定了三级阈值策略：

    - 相似度≥0\.7：认为高度相关，直接纳入检索结果，用于生成答案

    - 0\.5≤相似度＜0\.7：认为弱相关，只取Top1做补充参考，不做主要依据

    - 相似度＜0\.5：认为无相关知识，触发“无法解答、转人工”的兜底逻辑

因为是专业领域知识库，对准确率要求高，所以把合格阈值设得偏高（0\.7），宁可漏答也不误答，避免给客户错误信息。

#### 这个项目如果线上高并发，你会怎么优化？

**参考答案：** 可以从**缓存优化、检索性能、大模型调用、架构演进、降级策略**五个层面来优化，结合Java生态的技术栈：

1. **缓存层优化**

    - 把高频问题（比如“报关需要什么资料”“过闸费怎么收”）的标准答案缓存到Redis，设置合适的过期时间，用户直接命中缓存就不用走RAG和大模型，大幅降低压力

    - 会话上下文继续用Redis缓存，同时热点知识库的向量也可以做缓存

2. **向量检索性能优化**

    - 给PgVector的向量字段创建HNSW索引，提升查询速度

    - 对知识库做分类，检索时先按业务类别过滤，再做向量匹配，缩小检索范围

    - 如果量级继续增大，就迁移到Milvus专用向量库，支持分布式部署和更大规模检索

3. **大模型调用优化**

    - 采用流式输出（SSE），边生成边返回，降低用户等待感知，同时提升服务吞吐量

    - 做请求合并和批量处理，非实时请求可以批量调用大模型

    - 接入多个大模型服务商，做负载均衡和降级兜底，避免单服务商限流

4. **服务架构演进**

    - 从单体架构拆成微服务：知识库服务、对话服务、工具服务独立部署，各自扩容

    - 引入消息队列（RabbitMQ/Kafka）做异步解耦，比如日志、统计、知识库更新等非核心流程异步处理

    - 接入Sentinel做限流熔断，保护核心接口

5. **降级策略**

    - 高并发时，优先保证问答核心功能，关闭统计、日志等非核心功能

    - 大模型调用超时或失败时，自动返回预设的兜底话术，同时提示转人工

#### 开发过程中遇到的最大难点是什么？怎么解决的？

**参考答案：** 最大的难点是**航运专业场景下，通用大模型的回答准确率低、容易出现幻觉**。

一开始我直接调用通用大模型做问答，发现很多专业问题都答不对：比如平陆运河的过闸收费标准、内河船舶的通行规则，大模型要么瞎编，要么混淆其他港口的规则，专业术语也经常出错，根本达不到可用标准。

**解决思路：** 我没有选择微调大模型（成本高、数据量不够），而是从**RAG增强\+Prompt工程\+知识库精细化**三个方向入手：

1. **做垂直领域的RAG知识库**：收集整理平陆运河官方文件、港口规则、报关流程等权威文档，全部经过内容校验，确保知识库本身准确无误

2. **强化Prompt约束**：加上严格的“只基于知识库回答、禁止编造、标注来源”规则，从生成逻辑上限制幻觉

3. **引入引用溯源机制**：每个答案都必须标注来源文档，既提升用户信任度，也方便人工排查错误

4. **建立 bad case 迭代机制**：把答错的问题收集起来，要么补充知识库，要么优化Prompt，持续迭代

**最终效果：** 专业问题的回答准确率从最初的60%左右提升到了85%以上，基本能覆盖80%的常见咨询问题，达到了客服场景的可用标准。

这个过程也让我明白：垂直领域的AI应用，**行业知识的质量和Prompt的精细度，比模型本身更重要**。
