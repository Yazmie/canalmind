## 开场一句（直接可用）

> 这个项目让我最深的体会是——**RAG 系统里，"不一致"会以三种面目出现，
> 而我处理它们的方式逐层升级了。**

1. **同一份语料内部**的矛盾（人眼可查）→ 闸室 300×34 米 vs 单船 16 米宽，**逻辑上互斥**

## 技术含金量最高的一条（准备好被深挖）

> **HNSW 索引命中 ≠ 结果正确。**
> 带 `WHERE` 过滤 + `LIMIT` 时，近似索引会**静默少返回**——
> 实测 116 行匹配、`LIMIT 10`，**只返回 2 行**；打开 `hnsw.iterative_scan = relaxed_order` 才恢复 10 行。
> **我们的检索天然带"文档版本有效期"过滤，所以这不是边缘场景，是主路径问题。**

**预备追问**：
- *"为什么不用精确索引？"* → HNSW 的召回/延迟权衡更适合本项目；**关键不是换索引，而是承认"近似+过滤"必然有语义缺口，再用显式配置 + 结果对账管住它。**
- *"iterative_scan 有代价吗？"* → 有，扫描/缓存读取量明显上升（`shared hit` 949 → 2478），**是用检索开销换结果完整性**，要写进评测而不是当免费午餐。
- *"怎么发现的？"* → 我看到资料提醒"HNSW 遇过滤条件要重点看执行计划"，就专门去测了带过滤的场景——**而默认场景看起来完全正常**。
- *"这个参数在连接池下怎么办？"* → `SET` 是**会话级**的，必须用连接初始化回调保证每条物理连接都被设过，否则"结果对不对"会随机取决于落到哪条连接。**这类 bug 极难复现。**

> **⚠️ 同一族还有一条本轮新增（属「对外表达」纪律，很容易说错）**：
> 本项目 **541 行**规模下**规划器压根不选 HNSW**——默认 `cosine`（`<=>`，算子类与索引不匹配）是
> `Seq Scan on rag_chunk (rows=541)` + top-N heapsort（3.479 ms）；换成**算子类匹配**的 `ip`（`<#>`）
> **仍然是 `Seq Scan`**；**只有 `SET enable_seqscan=off` 才出现** `Index Scan using rag_chunk_embedding_hnsw`（1.216 ms）。
> **所以能说出口的是**：「索引**可用**、结果与精确检索 Top-20 完全一致、**启用门槛实测 ≥1000 行**」；
> ⛔ **不能说**「HNSW 已启用 / 线上在用 HNSW」。
> - *「你怎么发现自己差点说错？」* → 我按 C-23 与规格书原话去核对「确认索引用上了」，**发现这句话在 541 行下不成立**——
>   **「建了索引」和「用上了索引」中间隔着三个条件**：算子类匹配、规划器认为划算、统计信息是最新的。
> - 细节：[检索工程/建了索引不等于用上了索引](检索工程/建了索引不等于用上了索引.md)

## 方法论五条（回答"你平时怎么做事"用这个框架）

1. **不信任自己的 PASS** → 每新增一条校验，都做**"注入错误"测试**，确认它真会报错、退出码变 1，再恢复。
   > 一句话：**"一个从不失败的检查，无法证明它有效。"**
2. **"我没找到" ≠ "它不存在"** → 我曾断言"知识库没覆盖"，**结果错了**（覆盖得很完整）。
   现在把"无覆盖"当成**需要举证的主张**：要说清搜了哪些词、哪几个文件。
   > ⚠️ **补一层（本轮新增）：一条否定结论我连着错了四次，且「空」有三种成因**——
   > **① 真的没有；② 范围不全**（只搜一个目录 / 被 `.gitignore` 排除的路径根本没被搜）；
   > **③ 查询本身失败而被静默**（我用 `Get-CimInstance` 查进程得到「（无 java 进程）」，
   > 而**我自己的付费批次当时正在跑**——真因是查询被**拒绝访问**、被 `-ErrorAction SilentlyContinue`
   > **吞掉**；换 `Get-Process` 立刻看到 PID 15760）。**三者的输出在屏幕上完全一样**，
   > 所以见到「空 / 无 / 0」先问「**这是哪一种空**」；⛔ 结论性查询**不得吞异常**。
   > 细节：[工程方法/局部搜索不能支撑否定结论](工程方法/局部搜索不能支撑否定结论/README.md)
   > ⚠️ **再补一层（第 9 轮新增）：正面的全称判断同样要举证，「独有 / 唯一」也不例外**——
   > 我由**一条 L6 样例**断定"这三个字段是 L6 独有的"（还写进了注释、测试名和决策记录），
   > 落库后按层一数：**L3 0/20、L5 17/20、L6 15/15** ⇒ **L5 也有，整整漏掉一层**。
   > 看一条样例只能得出"**这条有**"，得不出"**别的没有**"；写进代码或结论前先问
   > "**这句话是否超出了我实际核对过的范围**"。
   > 细节：[诚实记录/公开更正自己的错误结论/断言某字段独有而其实只看了样例](诚实记录/公开更正自己的错误结论/断言某字段独有而其实只看了样例.md)
3. **信息要放在消费者会去看的地方** → 同一个疑问被**两个独立评审各提一次**，
   那是"**我的文档放错位置**"的信号，不是对方没看懂。我把它从决策日志搬到了复核者实际会打开的文件里。
4. **别人（含 AI 审计）的结论也只是「另一个工具的输出」** → 一次只读对抗式审计给出 **23 条待修订**，
   我**逐条核验后核出它自己至少 3 处错**（其中一处若照搬，就会把一个**正确**的 gold 改坏）。
   所以**审计是线索不是结论**：采纳前用**独立手段**（直接查库读全文、自己重算）逐条复核。
   > 一句话：**照搬别人的结论，等于把别人的错记在自己账上——而且不报错。**
   > 细节：[工程方法/审计结论也要逐条核验](工程方法/审计结论也要逐条核验.md)
5. **评估"模型能力"之前，先确认"仪器的量程"够不够**（本轮新增，这条最容易被误读成"模型不行"）→
   重排侧 `max_tokens=4096` 在 30 条候选档下 **3/3 必然降级**（`finish_reason=LENGTH`、`completion`
   **恒等于** 4096——该模型先推理再输出，**推理 token 与正文共享同一预算**）；`timeout=30 s`
   **正好压在实测均值 29.4 s 上**（最小 21.6 / 最大 43.5 s；有一次**成功**的调用耗时 **29.875 s**）。
   **两处在产物里都只表现为「保留融合原序」——与「重排没有效果」完全一样。**
   改量程后同一档单题复测：**1 次尝试成功、30 条候选全部重排**（`degradedQueryCount=0`）。
   > 一句话：**`max_tokens` 与 `timeout` 不是调参，是量程；量程不足时，失败会被记成"能力不足"，
   > 而产物只会说"降级了"。默认值也是结论的一部分。**
   > 代价如实讲：因为它在产物里看不出来，**一整批计划 40 题的真实调用跑到约 15 题才止损叫停、全部作废**。
   > 细节：[工程方法/量程不足会把配置掐死记成能力不足](工程方法/量程不足会把配置掐死记成能力不足/README.md)

## 最能体现"我会排查"的一条：合法但错

> **编译通过、测试也绿、一句报错都没有，而行为是错的。**
> 我发现同一篇文档的 LF 版切出 4 块、CRLF 版只切出 3 块，**表格整块消失**——
> 根因是**转义写错了反斜杠数量**：同一个换行，源码里写"一个反斜杠"时运行时是 **2** 字符、
> 能匹配真实 CRLF；写"两个反斜杠"时是 **4** 字符、**永远匹配不到**。
> 于是换行归一化从未生效；而 `replace` 没匹配上就原样返回、`split` 切不开就返回单元素数组——**全都不报错**。

**预备追问**：

- *"你怎么查出来的？"* → **不是靠读代码**，是靠 ①**并排 A/B 对照实验**（两个常量，比长度、比是否替换成功）；
  ②测试里打**码点级断言**，看到 `005C 006E`（反斜杠+n）才确认字面量真的进了正文；
  ③`javap -v` 看**字节码常量池**，发现源码看着对、产物里是另一个东西。
- *"最后怎么修的？"* → **从源头消除这个变量**：用 `String.valueOf((char) 13)` / `(char) 10` 拿真实字符，
  不用字符串转义——写入层再怎么折叠反斜杠也折不到它。同时把不变量钉在**数据边界**
  （record 的紧凑构造器里归一化），而不是在每个使用点各自容错。
- *"这中间走过弯路吗？"* → **走过，而且我主动讲**：一个跨语言的假结论让我做了**全局替换**，把 4 个文件改坏；
  回滚又用了全局加倍，把本来正确的字符字面量也改坏。
  **教训：编辑类操作必须逐处、可断言、可回滚，禁止全局替换。**
- *"为什么不靠更仔细地读代码避免？"* → 因为**这类错误读不出来**。正确做法是换判据：
  **"我看过了"不构成证据，"两个独立 oracle 一致"才算。**

## 又一个"合法但错"：中文 BM25 的三次**静默失效**（本轮新增）

> 三件事合成一句话：**分数照样算得出来，只是不再有意义。**

**1. 用户词典"加载成功"，词却永远不被选中**

> 词典照抄标准 jieba 的**三列**格式，而这个 Java 移植库的 `loadUserDict` **只认两列**，
> 于是词频**静默退回默认值 3.0**。基础词典 349045 词、总频次 60101878，
> 默认词频的打分是 `log(3/60101878) = -16.81`——**比基础词典里任何词都低**。
> **"加词"这个动作本身，把词变成了全库最低分，且一句报错都没有。**

- *"你怎么发现的？"* → **先写判据再跑**：把"每条词典词都必须在自己的文本里被完整切出"写成用例，它当场红。
  **如果只检查"词典能加载吗"，这个缺陷会一路活到线上。**
- 细节：[检索工程/结巴用户词典的列数陷阱](检索工程/结巴用户词典的列数陷阱.md)

**2. 结构标记进了倒排表**

> 行首的 Markdown 列表编号（SQL 实测 **1170 处**、覆盖 **454 个正文 chunk 中的 301 个（66%）**）
> 让词元 `1`/`2`/`3` **占据 df 榜首**（df 317 / 318 / 310，idf 仅约 **0.52**）——纯排名噪声。

- *"为什么不能靠停用词表解决？"* → 停用词表按**词**过滤，这里要按**位置 + 形态**过滤；
  一刀切会连"2 小时""4.20 元/吨"这类**真内容**一起杀掉。
- *"这条规则怎么定的？"* → **先测再写**：实测语料里**只存在一种编号写法**（`1)`、`1、`、`（1）`、`(1)` 各 **0 处**），
  才敢只写这一条精确规则，而不是写"看起来像编号的都剥"的**贪婪正则**。
- *"怎么证明剥对了、没剥多？"* → **两个独立口径对齐**：剥离前后两档案词元总数 35764 → 34594，
  **减少量恰好 1170**，与 SQL 独立数出的编号处数**完全相等**。
- 细节：[检索工程/结构标记不该进倒排表](检索工程/结构标记不该进倒排表.md)
  （这次规则变更还牵出一个更大的问题：**改了切分规则但档案身份没变，就地重灌会混两套口径** →
  [检索工程/分词规则也是索引格式的一部分](检索工程/分词规则也是索引格式的一部分.md)）

**3. 子进程"挂起 + 无输出"，优先怀疑它在等交互输入**

> 漏传 `env=` → psql 拿不到 `PGPASSWORD`，转去**弹口令提示**；
> 而 psql 的提示读的是**控制台，不是 stdin**，所以 `stdin=DEVNULL` **挡不住它**——
> 命令就永久等一个**永远不会有人输入的密码**（harness 600s / 脚本 300s 超时都触发了）。

- *"你怎么排查的？"* → **走过一条弯路并主动讲**：先怀疑"管道捕获受限"，改成把输出重定向到文件——
  **仍然挂住**，这一步排除了管道这条线。真因是缺 `env=`。
- *"怎么防？"* → **传 `env=`** + 给 psql 加 **`-w`（宁失败不等待）** + 显式 `timeout=`：
  把"永久等待"变成"**一条清楚的错误**"。**先怀疑"它在等什么"，而不是"为什么没有输出"。**
- 细节：[环境坑/psql从子进程调用会挂住](环境坑/psql从子进程调用会挂住.md)

## 又一族"不报错的错"：**评测资产自己也会错**（Golden Set L2 这轮）

> 一句话：**尺子自己错了不会报错，只会让每次实验都"看起来在进步"。**

**1. 评测集错了，只表现为"指标好看"**（所以给数据集也写了校验脚本）

- 三类风险**都不会让任何脚本变红**：gold chunk id 抄错（会被误读成检索缺陷）、**分布失衡**、
  题面照抄条款用词（检索虚高 → **系统性高估召回**）。
- 依据知识库《AI 应用评测体系》第 100 行：**"样本分布往往比总量更先决定评测能否发现问题"**。
  → ⚠️ **这处行号是刻意保留的，不是漏改**：知识库是**只读第三方资料、内容冻结**（行号不会漂），且 `AGENTS.md` §4.1 **要求**引用知识库时给出**文件名与行号**，而它**不入 git**（`.gitignore` 第 29 行）、无法靠版本核对——**行号是唯一可定位方式**。目录里「会变动的文件别用行号」那条实践提示**只管脚本 / 看板 / 数据包 / 产物，不管知识库**。
- 锚点：`backend/scripts/verify_golden_set.py`（检查项清单在该脚本 **docstring 的「检查项」小节，共 10 项**）——**首轮抓出 7 项错误**（6 项反照抄 + 1 项我自己写错的断言）。

**2. 规则过严，会把"对的"判成"错的"**（比过松更危险）

- **断言写错范围**：我最初断言"该文号**全库**都不出现"——实测 `PLYH-GZ-2026-001` 全库出现 **4 次**
  （`02` 两处 / `03` 一处 / `04` 一处），而**该文档自己的 21 个 chunk 里 0 次**：那 4 次是**别的文档在引用它**。
  真实声明应是"**本文档自己的 chunk 不含自己的文号**"。
- **规则误伤正确的题**：反照抄规则分档后发现，**两类实质正确的题会被判失败**——术语题**必须**点出被定义的术语
  （「计费单位」），标识符题**必须**写出版本号（「与 V1.0 的衔接」问"上一版何时废止"）。
  实测（不加豁免）：**会有 3 条硬失败，全是"正确的题"**。
- **改法**：分三档（连续 ≥5 字、标题 ≥8 字且重合 ≥0.95 = 硬失败；≥0.8 = 警告）+ 三类**声明式豁免**
  （T4 术语本身；数据集逐条声明的 `allowedTitleOverlap` 标识符；跨主题类 gold）。当前实测：**硬失败 0、
  反照抄警告 8**、豁免**术语 3 / 标识符 2 / 跨主题类 gold 1**（另有 `gold 跨文档` 警告 1 → 机读产物 `warnings` **9 条**）。
  ⚠️ **豁免必须逐条打印并落进机读产物**——曾经只有术语豁免有打印路径，标识符豁免**生效时静默不打印**，
  读者分不清「没报错」是「确实没重合」还是「被豁免掉了」；**2026-09-21 已修**（三类全打印 + 写进
  `golden-l2-validation.json` 的 `termExemptions` / `identifierExemptions` / `crossClassGoldExemptions`）。
- **讲法**：**过松只是没抓到；过严会让"正确的做法"被迫改坏**——规则就变成了造假指南。豁免必须可见、有理由。

**3. 真实数据没到位，先用合成输入空跑一遍**（这条最值得讲）

- 指标脚本写完、真实命中还没有 → 先造合成命中（40 条，名次 1 / 12 / 25 / 未命中）空跑 I/O。**抓到 2 个 bug**：
  - ①`", ".join(...)` 得到的**字符串**又被 `" OR content LIKE ".join(...)` 拼了一次——第二次是在**字符串的字符**上 join，拼出语法错误 SQL；
  - ②（更隐蔽）匹配串 `'%[TABLE:<id>]%'` 要求 id 后**紧跟** `]`，而真实标记是 `[TABLE:<id> rows=N cols=M]`
    → **一条都匹配不上、静默返回 0 条**（SQL 实测 87 个 TABLE 占位中 **0 个**是 id 后紧跟 `]`）。
- **讲法**：**"能跑通"和"跑对了"是两件事**。bug ② 不报错、只静默为空——直接上真实数据，极可能被读成"这类失败不存在"。
- 度量工具同理：`eval_retrieval.py --selftest` 用 4 条构造题**手算期望值**再断言（`HitRate@1=0.25`、
  `HitRate@5=0.5`、`HitRate@30=0.75`、`Precision@5=0.1`、`MRR@30=0.308333`，退出码 0）。
  ⚠️ 这两个 bug 是**在真实命中到位之前**抓到的，**本条不写任何真实指标数值**（真实指标现已产出，
  出处以《评测报告》为准——见下方第 6 条）——**不写没有基线的数字**。

**4. 我曾把自己标注错误的后果，写成了系统的"已知限制"**（这条最能体现"我会证伪自己"）

- 一条"30 位内完全召不回"的题（问某**文号**对应哪份文件、规定了什么），真因是**我的 gold 标错了**：
  标成的那个块**全文不含该文号**、答不出题干前半句；而文号其实出现在**别的文档的 4 个「依据」条**里，
  每处都把**文号与文件名绑定**。

  并把它当**已登记缺陷**写进了数据集、评测报告与决策记录。
- **推翻它的证据来自我自己另一条线的产物**：BM25 探针在同一查询上的 **rank 1–4 正是那 4 个块**

| **写入层的编码与转义会静默改内容** | ①编辑工具写出的 `.ps1` 是**无 BOM**，PowerShell 按 GBK 解中文 ⇒ **解析期就死**，而**包装器仍退出 0**（内层退出码是空值）；②双引号 here-string `@"..."@` 里**反引号是转义符**，把文案里的 `` `v2-rrf-rerank.json` `` 静默吃成 `2-rrf-rerank.json`——**改动恰好落在要引用的证据文件名上** | ①改用 **PowerShell 自带 AST 解析器**（`Parser::ParseFile`）静态自证，⛔ 不再拿"跑起来没报错"当判据；②逐字读输出才发现少了字符（[环境坑/脚本文件BOM](环境坑/脚本文件BOM.md)、[环境坑/PowerShell脚本的反引号陷阱](环境坑/PowerShell脚本的反引号陷阱.md)） |
| **付费脚本的失败点留在最后一步** | 跑消融实验的 D3 臂（40 次 LLM 重排）：**40 次调用全部发完了**，脚本最后一步才因为「把 hits 产物当成 metrics 产物传给对照脚本」报错退出 | 修法是**给付费脚本加 `-SkipPaidRun` 开关**——免费分支（指标重算、多臂对照、文案输出）可反复空跑；**先空跑跑通全链路，才允许去掉开关真跑**。规律：**花钱的调用必须排在所有零成本校验之后** |

> **面试可以这样收口（第 4 周版）**：这三种错的共同点是**"成功"和"正确"被分开了**——
> 测试全绿不等于输入接上了，脚本退出 0 不等于脚本跑了，输出打出来了不等于内容没被改。
> 所以我的纪律升级成两条：**①能用零成本手段自证的地方，绝不靠"结果看起来对"；②付费脚本必须把校验全部前置。**

## 第 5 周新增：**"一半正常"比"全坏"更难查**

| 现象 | 一句话 | 怎么抓到的 |
|---|---|---|
| **同一个 JVM、同一组参数，一半 CLI 中文乱码、一半正常** | JDK 18+ 的 `System.out` 按**控制台代码页**编码（本机 GBK）⇒ 只写 `-Dfile.encoding` **不管用**，要 **`-Dstdout.encoding`**。⚠️ **而 RAG 侧那几个 CLI 之所以正常，是那个类里恰好写着 `System.setOut(UTF-8)`——那是"碰巧没踩到"，不是"已解决"** | 一键演示脚本把平时**分散在十几条命令**里的调用集中跑一遍 ⇒ "只有一部分乱码"这种平时**不会同时出现**的对比才浮出来（[环境坑/Java控制台输出编码](环境坑/Java控制台输出编码.md)） |
| **明知约定，写的时候还是违反了它** | 项目早有约定「SQL 一律走 `psql -f <UTF-8 无 BOM 文件>`，⛔ 不用 `psql -c`（中文会被控制台代码页改坏）」，而我写演示脚本时**仍然在 `psql -c` 里写了中文标签** | 我在**跑之前复核**时自己发现并改掉了（⚠️ **这是依据已登记条目的预防，不是本次实测报错**）。⇒ **"知道约定"与"写的时候想起来"是两件事**，所以约定必须沉进**模板/包装函数**，不能只写在文档里（[环境坑/psql从子进程调用会挂住](环境坑/psql从子进程调用会挂住.md)） |
| ⚠️ **同一条约定，我在同一天又踩了两次** | 上面那条"预防"记完的**当天**，我在**临时的 `psql -c` 核验命令**里又写了中文标签 ⇒ 两条查询**当场报错**：`无效的 "UTF8" 编码字节顺序: 0xcc 0xf5` | **这才是真结论**：约定**沉进文档不管用**——交付脚本里我守住了（因为有包装函数），**临时命令里没有包装函数，所以必然复发**。⇒ **临时核验命令也必须用同一套包装**，否则"写进文档的约定"只保护了被审查的那一条路径（[环境坑/psql从子进程调用会挂住](环境坑/psql从子进程调用会挂住.md)） |
| ⚠️ **同一天又踩 BOM（第 5 次）——但这次被自证拦下** | 改完 `demo.ps1` 后 **换行是对的（`CRLF=410 / LF=0`）、只有 BOM 丢了**。⛔ **"CRLF 对就以为合规"是新的失手形态**：CRLF 不符时 `git add` 会警告，**BOM 丢了 git 一声不响**。而缺 BOM 的 `.ps1` 在 PS 5.1 下按 **GBK** 解析 ⇒ **15 处语法错误，且报错位置离真实原因很远** | 上次定下的**两步自证**（①前三字节 ②AST 解析）**在提交前跑了** ⇒ 当场拦下、**未入库**；补回 `EF BB BF` 后语法 0 错误，并按 README 记录的原样命令实跑 **退出码 0**。⇒ **靠记忆一定复发（已 5 次），有效的是"写入后立即自证"**（[环境坑/脚本文件BOM](环境坑/脚本文件BOM.md)） |
| ⚠️ **埋点"Span 全都在"，但调用链是**平的**** | Micrometer 的 Span **父指针只在 `openScope()` 之后才存在**，而父是**子 Span 启动时**取的 ⇒ 手工 `start()`/`stop()` 埋出的是**一棵父全为 null 的平树**：Span 一条不少、名字全对、**不报错**，只是"哪一步导致哪一步"永远推不出来 | 用 **8 个变体实测**定位出 `observe(...)`（会自动开 scope）才是正确惯用法；并用 `ObservationHandler` **断言父子关系**而不是"看导出的 Trace"；还把"手工 start/stop 不嵌套"本身写成断言，将来库改语义会红（[工程方法/观测埋点的父指针会静默丢失](工程方法/观测埋点的父指针会静默丢失.md)） |
| ⚠️ **"我注册过传播器了"——但跨线程照样丢** | 父指针靠 `ThreadLocal`，跨线程默认丢；**只注册 `ThreadLocalAccessor` 并不会自动传播**，必须**显式包装执行器**。4 个场景实测：裸线程池 / **只注册不包装** / `ForkJoinPool.commonPool()`（SSE 实际形态）**全是 `null`**，只有"注册 **+** `ContextExecutorService.wrap`"才保住 | 这种**"半配置状态"完全合法、不报错**，最危险的是人会以为"我已经配过了"⇒ 把"注册≠生效"本身写成断言；并发现全局单例 `ObservationThreadLocalAccessor` 用不注销会**污染别的测试**（假绿），已在 `@AfterEach` 归还（[工程方法/跨线程埋点父指针丢失](工程方法/跨线程埋点父指针丢失.md)） |
| ⚠️ **构建是绿的，产物却在运行时炸** | 源码里有**编译错误**，构建**不失败**、照样产出 surefire 报告，而产物是**一被调用就抛 `java.lang.Error`** 的类——测试"跑到了"却全数报错。**失败信号被搬到了最贵的位置**（运行期离"我改了哪一行"最远），且报告里**大部分是绿的**，红的几条像是"测试自己的问题" | 用 **`javac` 全树独立复编**同一份源码，**立刻**拿到真正的错误（与构建是两条独立编译路径）；再用 `javap` 看出那份 `.class` **有 `attemptOnce` 却没有 `lambda$extract`** ⇒ 它是**从出错源码带伤生成**的、不是陈旧字节码（⚠️ 我在这一条上判错了两次：把"文件**被跳过**"与"跑的是**旧字节码**"**捆成一个判断**，证伪了后半就把**成立的前半也一起扔了**——而"被跳过"正是根因，判它的证据是"**构建成功**"这件事本身（javac 若真编过它，2 处 `effectively final` 错误会让构建失败）；又拿"仓库里没有 ecj"去质疑对方的实测，**而这个推理本身就不成立**：IDE 自带编译器、不走 Maven 仓库。见 [诚实记录/我误判带伤字节码的来历](诚实记录/我误判带伤字节码的来历.md)）；防御写进配方：**跑测试前先删 `target/classes` 与 `target/test-classes`**（[工程方法/编译错误被静默放过](工程方法/编译错误被静默放过/README.md)） |

> **收口句**：这一轮最值得讲的不是"我修好了一个乱码"，而是
> **"我怎么把『碰巧没踩到』与『已经解决』分开"**——
> **同一条链路上，另一段代码里存在一行 `System.setOut` 就可能让同一类缺陷只暴露一半**，
> 而这种"一半正常"的状态，最容易被误判成"已经修好了"。

## 第 5 周新增之二：**一句没人验证的"汇总句"，被抄进了三份文档**

| 现象 | 一句话 | 怎么处置 |
|---|---|---|
| **我写的「`eval_record` 六层全部在库」，实测只有 5 层** | **L4 一条都没有**——它的分数一直在（`layer-L4-inheritance-v1.json`），只是**没落库**。⇒「**出了分**」与「**在库里**」是**两件事**，我按前者写了后者 | **补能力**（写 L4 落库通道 + 新开 run `…-artifacts-v3` = 160 条 / 6 层，⛔ 不动 v2）＋ **就地标注**每处被污染的断言（⛔ 不静默改掉） |
| ⚠️ **这句话被放大进了 `DECISIONS.md` 三处** | 其中包括 **「第 4 周目标验收通过」** 那一条 ⇒ **一句没核对的话，进了验收依据** | 新增决策条 **C-53b** 写明"当时称六层、实测 5 层" |
| ⚠️⚠️ **同一个错，我在同一节里犯了两次** | 第①次是标题写「取自库内 `eval_record`」而库里只有 80 条；补了 Judge 三层后写成"六层"——**补的是 3 层，缺的是第 4 层（L4）**。**"上一次刚更正过"反而制造了下一次的自信** | 修法**不是"下次仔细点"**，而是把汇总句变成**能被一条命令证伪的断言** |

> **收口句**：**汇总句是最容易腐烂的一类文档**——它**看起来像结论**，却**没有任何东西会自动验证它**，
> 而且**它会被别的文档引用、放大**，于是"一句话没核对"变成"**三份文档一起错**"。
> ⇒ 两条硬规定（已写进 `AGENTS.md` §6）：①凡"有几层 / 多少条 / 覆盖什么"的话，
> **必须能由一条能跑的命令当场证伪**（本项目：`HarnessCli --report --run-id <id>`）；
> ②并列数值**必须带限定域**（"（`…-artifacts-v2` run 下）135 条"，⛔ 不许只说"135 条"）。
> **一个无法被证伪的汇总句，等于一句没人验证过的话。**
> → [工程方法/汇总句必须由能跑的检查守护](工程方法/汇总句必须由能跑的检查守护.md)

## 体现严谨的两个细节

- **把"刻意设计的难点"和"真实缺陷"分开管理**：已废止的费率表版本**必须保留**，它是评测资产。
  > **把测试数据洗得太干净，评测就测不出区分度。**
- **一致性有"作用域"**：单文件校验只能查文件内部错；跨文件矛盾必须用跨文件规则。
  设计校验体系时先问"**这个不变量横跨多大范围**"，再决定检查放在哪一层。

- **评测集的标注缺陷已修订为 v2（23 处），但仍有未闭合的部分**——修订后**严格族的 `HitRate@k` 一字未变**，

## 心态提醒

- **不懂的就说不会**，但要说出"我会怎么查"（正好用上方法论第 2 条）。
- **不要写没有基线的数字**（本项目所有指标都要求能定位到《评测报告》）。
- **项目性质如实说**：本地仿真、无真实数据。讲**工程判断力**，不吹业务体量。
- 每条都准备一个"**我当时以为 X，结果是 Y**"的转折——评审最爱听这个，因为它证明你真的动手了。
  - 可直接用的一个（第 14 轮实测）：**做提示词 A/B 之前，先 grep 出"谁在读这段提示词"**。
    我一度按名字认定 `SYSTEM_PROMPT` 就是系统提示词，还给它写了冻结测试；实测才发现
    **Web 侧与评测侧读的是两段不同的提示词**——产出评测出分的作答链路根本不经过那个 Bean。
    若照原样跑，结果**必然 v1≡v2**，而我会写下"该 Prompt 改动无效（0.1500 → 0.1500）"，
    **40 次付费调用照扣、退出码 0、没有任何东西报错**。
    ⇒ 教训：**⛔ 不要靠命名推断调用关系**；凡要改一个"被某条链路读取"的常量，
    **先实测它的消费方**（grep 一遍引用点，几分钟，换掉一次"结论全错但不报错"的实验）。
    留痕：`诚实记录/公开更正自己的错误结论/把未被作答路径使用的提示词当成Prompt基线.md`
  - 另一个可直接用的（第 21 轮，**我自己的一次带红提交**）：**"我把验证和提交写在了同一条命令里，
    所以测试的红我看到了却没起作用。"** `mvn test` 与 `git commit` 顺序执行，`$LASTEXITCODE` 我只**打印**、
    没**判断** ⇒ 打印 ≠ 把关。更该记的是：那次失败是"改了字面量、而测试断言那个字面量"的**必然**失败，
    改前 grep 一下就能预知。
    ⇒ 一句话讲法：**验证必须是一个"闸门"，不是一个"步骤"——失败时流程还能照常往下走，它就不是闸门。**
    ⛔ 我没有用 `reset --soft` 把红提交和修复合成一个漂亮提交，因为那等于把失误从历史里抹掉。
    留痕：`诚实记录/验证与提交串在同一条命令里就不是闸门.md`
