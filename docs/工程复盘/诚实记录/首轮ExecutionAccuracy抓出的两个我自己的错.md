# 首轮 Execution Accuracy 抓出的两个"我自己的错"

> 留痕要求：本项目 §8.2 规定"发现自己的错误结论时必须留痕，不得静默改掉"。
> 这两处都不是被测系统的错，而是**我写的判据与我的实现**的错——
> 若不是跑了一次真实评测，它们会一直待在报告口径与代码里。

## 错误一：判据把"该答却追问"排除出了分母

**我写的判据**（`backend/scripts/eval_execution_accuracy.py` 初版）：
状态为 `NEEDS_CLARIFICATION` / `REJECTED` / `DEGRADED` 的题**不计入准确率**，
理由是"把'不知道就不答'算错会罚正确行为"。

**错在哪**：曲线被用错了层次。
决策 C-35 说的是「**缺参**按是否追问判」——针对的是**题面本身缺参数**的那类题（L6）。
而 L1 的题面**已把参数写全**（每题的 `expected.args` 就是从题面唯一确定的），
此时系统反问用户等于**没答上来**。把它们排除，等于给"抽取漏掉参数"这类**真实缺陷**开了免罚通道，
准确率会被系统性抬高。

**证据**：首轮跑出 40 题里有 4 题走追问（L1-019/020/021/022），若按初版判据，
报告会写"EA = 100%（36/36）"——**一个因为把失败的题删掉而得到的满分**。
修正后判据是：L1 只排除"判分器自身异常"，追问/拒绝/降级**计入分母且单独归类**
（`该答却追问`、`降级未作答`、`无数据` 与"答错（数值不符）"分开），
并额外报一个"有作答之下的正确率"作对照。修正后同一批数据是 **EA 90.0%（36/40），有作答时 100%**。

**判分器自检也同步改了**：原来断言"追问应被排除"，现在断言"追问**必须计入分母**且归入独立 bucket"——
否则下次有人再把它"优化"回排除，自检不会拦。

## 错误二：契约允许的输入，服务端只实现了一半

**现象**：同一批 4 道题，追问话术是"费种 过闸费 按货类分档，请补充货类"。
第一反应是**模型抽取不准**——用户明明说了"成品油/硫酸/烧碱/集装箱货物"。
我先去改提示词（加了一条"用户说货种时不要再索要货类"，并同步改了契约描述）。

**改完复测：一模一样，还是 4 题。** 这才回头看服务端代码，发现根因在**我自己**：

```java
String category = categoryOf(call, feeType, traces);   // ← 只看 cargo_category
...
String cargoName = call.stringArg("cargo_name");       // ← 货种在这里才被读，晚了一步
```

`categoryOf()` 只认 `cargo_category`，模型**已经正确填了 `cargo_name`**，
服务端却在拿到货种之前就抛"缺货类"。
⇒ 契约里写的是"货种**或**货类"两个入口，**服务端只实现了其中一个**。
表现症状（"反问缺货类"）与根因（缺另一条代码路径）**方向完全不同**——
这就是"先怀疑模型"的代价：白白多花了一轮 Prompt 调整。

修正：`categoryOf()` 在 `cargo_category` 缺失时，**由 `cargo_name` 推货类**；
两条都缺才追问。修正后单元测试仍 54/54 通过（`missingCategoryAsksBack` 用例只给吨位与日期，仍然正确追问）。

## 教训

1. **"指标变好"也可能是判据变松**。任何"把某类样本排除出统计"的规则，
   都要问一句：**被排除的是不是恰好是我做得最差的那部分？** 是则说明判据在替我掩盖问题。
2. **症状的措辞会误导排查方向**。系统说"请补充货类"，听起来是"用户没说"；
   但用户说了，只是**没被读到**。⇒ 遇到"缺参"类追问，先去确认**那个参数是不是其实已经在请求里**。
3. **契约声明了几个入口，就要有几个测试**。`cargo_name` 与 `cargo_category` 二选一这件事，
   单测里我只覆盖了"两个都不给 ⇒ 追问"，**没覆盖"只给货种 ⇒ 应当能算"**，
   于是漏洞从单测缝隙里过去了。已有的用例是"缺参 → 追问"，缺的那条正是"另一种合法入口 → 应当作答"。
