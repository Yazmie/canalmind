# 我误判带伤字节码的来历（两个都很有说服力的错误判断）

> 主因所在类：**诚实记录**（`AGENTS.md` §8.2 第 5 条：发现自己的错误结论必须在本目录留痕）。
> 技术主篇在 [工程方法/编译错误被静默放过](../工程方法/编译错误被静默放过/README.md)。
>
> 返回本类索引：[../README.md](../README.md)

查到"构建不失败、产物运行时才抛 `Error`"之后，我连着下了两个**错**的判断。
两条都**自洽、都能解释现象**，差一点就被写进复盘和汇报。

## 猜想一：这是 Maven **增量编译跳过**了该文件

**我的推理**：`target/classes/…/ToolArgumentExtractor.class` 的时间戳（10:30:41）
**晚于**那份编译不过的 `.java`（10:30:40）。按 Maven 编译器插件的"存量检查"，
`.class` 比 `.java` 新 ⇒ 该文件被跳过 ⇒ **测试跑的是旧字节码**。

**为什么错**：我用 `javap` 看了那份 `.class`——它**有 `attemptOnce` 方法，
却没有 `lambda$extract`**。而当前源码是 `observe(() -> attemptOnce(…))`，
正常编译必然生成 `lambda$extract`。
⇒ 这份字节码是**从出错源码"带伤生成"**的，**不是旧的**。
（⚠️ 我当时还漏了一层：**旧版本**里 `attemptOnce` 是被**直接调用**的，
所以"有 `attemptOnce` 而无 lambda"同时也可能与旧版吻合——**只看一个特征不够**，
要把两版源码各自的产物特征都列出来再对。）

**教训**：时间戳只能提示"谁新谁旧"；**要判断字节码对应哪一版源码，得看字节码本身**
（方法/合成 lambda 的有无）。
⇒ 与 [工程方法/结论随测量方式变化时先怀疑测量方式](../工程方法/结论随测量方式变化时先怀疑测量方式.md) 同源。

## 猜想二：同事注释里那句"实测教训"不可信

**我的推理**：代码注释里写"该文件在本机曾被静默放过（主源码报 0 错、运行时才以
`Unresolved compilation problems` 抛 Error）"。我据此去查 `pom.xml` 有没有 `compilerId`、
两个本地仓库有没有 `ecj`——**都没有**。于是我在给用户的汇报里写了
"这条注释的『实测』不可信"，并准备让对方改掉。

**为什么错**：随后我在 `target/surefire-reports/` 里读到了**报告原文**，
`java.lang.Error: Unresolved compilation problems` 一字不差。
**那份实测是对的，我的怀疑是错的**——而且我抱着"找不到 ecj"这个**否定性证据**
去推翻一条**已经存在的肯定性证据**，方向正好是反的。

**教训**：这是 [工程方法/知识库无覆盖的错误结论](../工程方法/知识库无覆盖的错误结论.md)
的同一条：**"我没找到"≠"它不存在"**。
⚠️ 更该记住的是它的**后果**：若我按当时的判断去要求对方删掉那条注释，
就把**当时唯一一条真实证据**抹掉了，真正的机制反而更查不出来。
⇒ **否定别人的实测之前，先去找他说的那份证据**（本例中它就躺在 `target/` 里）。

## 两条的共同点（这才是要固化的）

| | 猜想一 | 猜想二 |
|---|---|---|
| 我手里的证据 | 时间戳（**间接**） | "仓库里没有 ecj"（**否定性**） |
| 我推翻的对象 | 字节码的实测特征 | 对方的实测结论 |
| 错在哪 | **拿间接证据当直接证据** | **拿"我没找到"当"它不存在"** |
| 本该先做的一步 | 看字节码本身（`javap`） | 去找那份 surefire 报告原文 |

⇒ **"能解释现象"不等于"就是它"**。两条猜想都自洽，所以危险的不是它们不合逻辑，
而是**它们太合逻辑、以至于我不再去找那份更直接的证据**。
