# 把验证与提交串在同一条命令里，于是"验证"变成了走过场

> 记录时间：第 21 轮。⚠️ 本条记的是**我自己的操作纪律失误**，且它**已经产生了一次带红提交**。

## 发生了什么

第 21 轮我改了一处 Javadoc 与一条异常信息（`L4RunCli` 的压缩桩理由，随 **C-53** 从"D10 未决"更新为"尚未接线"）。
随后我用**一条命令**同时做了三件事：

```powershell
mvn test > t21.log 2>&1
"TEST_EXIT=$LASTEXITCODE"          # ← 打印了，但没人看
...
git add <路径> ; git commit ...     # ← 与上面同一条命令，不等测试结果
```

结果：

- `TEST_EXIT=1`，`Tests run: 529, Failures: 1` ⇒ **`BUILD FAILURE`**
- 而 **`git commit` 照常成功**（提交 `f33e9ae`）

**红着提交了。** 直接违反 `AGENTS.md` §1「改动**通过其自身验证之后**再提交；⛔ 不提交未验证、半成品、或明知会红的改动」。

## 为什么这次和以前那次带红提交不同（值得单独记）

项目里已有一条"带红提交的教训"（改语料后只跑了语料自己的校验脚本，没跑**消费者**的测试）。
那次的问题是**跑错了测试**；这次的问题是——

> **测试跑对了，我也看到了红，但提交动作根本不以那个结果为条件。**

`git commit` 与 `mvn test` 在**同一条命令串**里，是无条件顺序执行的。
`$LASTEXITCODE` 我只是**打印**出来，⛔ 没有**判断**它。
⇒ 打印 ≠ 把关。**把验证和不可逆动作串在一起，验证就退化成了走过场。**

## 更值得注意的一点：我本该发现它

那条失败的断言是 `L4RunCliTest:96`：

```java
assertTrue(e.getMessage().contains("D10"), "抛出信息必须指明是 D10 未决导致的，便于排查");
```

**我改的正是这句话里的 "D10"。** 也就是说：这**不是**一个隐蔽的、需要跑全量才发现的失败——
它是"改了 A 的字面量，而测试断言 A 的字面量"这种**必然发生**的失败。
只要在改动前 grep 一下这个字符串，就能提前知道会红。

⇒ 双重失误：①改字面量前没查引用；②查了（跑）却不据其决定是否提交。

⚠️ 而这两条的**共同根因**是同一个：**把"我执行了核对动作"当成了"我据核对结果做了决定"。**

## 修法与止损

1. ✅ 定位失败断言 → 更新其**理由文字**（判据不变：仍要求"抛出信息必须指明原因"，只是原因从 D10 变成 C-53），并补一条"理由要写清楚是「没接线」而不是「没实现」"；
2. ✅ 重跑全量 → `Tests run: 529, Failures: 0` / `BUILD SUCCESS`（提交 `f1f976e`）；
3. ⛔ **未改写历史**：`f33e9ae`（红）与 `f1f976e`（修）都保留在历史里。
   理由：已 push 的提交一律不改，未 push 的也默认不改（§1），且**我无权自行整理**——
   用一次 `reset --soft` 把两次合成一次漂亮的提交，恰恰会把这次失误**从历史里抹掉**。

## 可复用的纪律（写进自己的操作习惯）

| ⛔ 不要 | ✅ 要 |
|---|---|
| `mvn test; git commit`（同一命令串） | **先跑测试并看到全绿，再在后续步骤里单独执行提交** |
| 只 `echo $LASTEXITCODE` | **据它做条件判断**；不为 0 就**停下报告**，不提交 |
| 改字面量前不查引用 | 改任何**会被断言的字面量**前，先 grep 引用点 |

> 一句话：**验证必须是一个"闸门"，不是一个"步骤"。**
> 如果失败时流程还能照常往下走，那它就不是闸门。
