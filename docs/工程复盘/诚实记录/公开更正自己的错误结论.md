## 第二次更正：表格占位标记的写法

**上面一条是"我的结论错了"，这一条是"我们的文档错了"——出处不同，纪律相同。**

| 项 | 内容 |
|---|---|
| **改的是什么** | 项目文档曾把表格占位标记写成 `[[TABLE:n]]`（**双**中括号 + **序号 n**）：`docs/进度看板.md`「正文与表格双存」一条、`docs/DECISIONS.md` **C-24** 的③项。⚠️ 行号会随文档改动漂移，**锚点认条款名（「正文与表格双存」/ C-24）而不是行号**。 |
| **实际情况** | **代码产出的、且库里实存 87 处的形式**是 `[TABLE:<16 位十六进制 chunk_id> rows=N cols=M]`——**单**中括号 + **内容派生的 chunk_id** + 行列数。注意它连"编号"都不是：**id 是由内容算出来的**。 |
| **核对方式** | ①读 `backend/scripts/verify_chunks.py` 里的 `MARKER = re.compile(r"\[TABLE:([0-9a-f]+) rows=(\d+) cols=(\d+)\]")`；②**直接在库里 `count(*)` 统计**（得 **87** 处）。**两个独立口径一致**，才敢下"文档不准"这个结论。 |
| **影响面** | 若照旧文档去写分词器，剥离规则会**一个标记都匹配不到**——16 位十六进制 id 就会变成词元，**每个 chunk 都被灌入一堆 id 片段，任意两个 chunk 都"相似"，且不报错**（详见 [../检索工程/结构标记不该进倒排表.md](../检索工程/结构标记不该进倒排表.md)）。 |
| **怎么处理的** | ①照**代码与库里的实测**实现，并在 `JiebaShippingTokenizer.stripTableMarkers` 的 javadoc 里写明"早前文档写成 `[[TABLE:n]]`，是文档不准，以代码与库里实测为准"——**把差异写在代码旁边**，下一个读代码的人就不会再去信旧文档；②**两份源文档已在同一会话内改正**：`docs/进度看板.md`「正文与表格双存」一条就地加了勘误说明，`docs/DECISIONS.md` C-24 的③项同样加了勘误并指向本节。故现在**文档、代码、库三处口径一致**。 |
| **为什么先改代码、后改文档** | 先改文档的风险是：写了勘误却还没实现，文档与实际行为又不一致（只是换了个方向不一致）。先按实测把行为做对、把锚点留下，**再去改文档**，中间任何时刻都能指出"当前真实行为是什么"。 |
| **一般教训** | **文档与代码不一致时，以「代码 + 库里的既成事实」为准**，并把差异写进注释/文档——**文档会滞后，数据不会撒谎**。这与 [../工程方法/知识库无覆盖的错误结论.md](../工程方法/知识库无覆盖的错误结论.md) 属同一类：**"我看过的某份文档说 X"不构成证据，"代码这样写、库里是这样"才构成证据。** |

## 同族的第三个形态：**不是结论错了，是归因错了**

上面两次分别是"**我的结论错了**"（断言知识库无覆盖）与"**我们的文档错了**"（表格占位标记写法）。
第三次的出处又不同：**错误本来是我的，我却把它归因给了系统**——一条实际由 gold 标注错误造成的
"检索未命中"，被我写成了系统的"已知实现限制"并登记进数据集、报告与决策记录，
**最后靠一次"证伪自己产物"的对抗式复核推翻，而证据来自本项目另一条线自己的基线产物**。

> 前两次的危险在"**结论不可靠**"；这一次的危险在"**归因错误会让人停止排查**"——
> 于是一个并不存在的系统缺陷被永久保留下来，还会污染后续决策。
