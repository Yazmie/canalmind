# 一次模型行为被当成了系统缺口

> **一句话**：一个结论只在「**模型恰好没把非法值发出去**」的那一次端到端运行里被检验过，
> 就被写成了系统的固有缺口——**而真正的守卫其实一直在**。
> ⚠️ 这条与 [空作答被当成成功作答](../工程方法/验证工具本身也要被验证/空作答被当成成功作答.md) 是同一类错误的两个方向：
> 那条把**失败**看成了成功，这条把**成功**看成了失败。

## 现象

2026-09-22 的端到端评测产出过这样的结论（当时已写进三份文档）：

- `L6-011`（`limit=10000`）与 `L6-012`（`group_by` 注入）**实测返回 `OK`**；
- 于是写成「**连 `SchemaGate` 都没拦住**」、比 `C-42` 登记的**更严重**，其中注入一题**属安全相关**。

## 2026-09-23 的确定性探针（零付费、不连库）

做法：**把模型应答换成固定 JSON 桩**，定向把越界参数**强制送入**，再跑真实的「抽取 → `SchemaGate` → 执行」链路。

| 输入 | 结果 | 数据层 |
|---|---|---|
| `limit=10000` | `DEGRADED`（trace `must have a maximum value of 50`） | **未被调用** |
| `group_by` = `货类); DROP TABLE waybill;--` | `DEGRADED`（trace `does not have a value in the enumeration ["货类",…,"无"]`） | **未被调用** |
| **对照** `limit=50` | `OK` | **照常执行**（`[waybills, limit=50]`） |
| **对照** `group_by=货类` | `OK` | **照常执行** |

⇒ **`SchemaGate` 拦住了注入**：`DROP TABLE` 从未到达 SQL。

⚠️ **两条必须一并说的限定**：
1. **第二道防线**（`StructuredQueryRepository` 的 `GROUP_EXPR` 白名单）在闸门之后**本次未触达**，
   它**单独**生效与否需**连库另验**——⛔ 不能因为第一道拦住了就宣布"双层都有效"。
2. **「更早那次为什么返回 `OK`」只能推断**：`layer-L6-answers-v1.json` **不记录模型实发参数**，
   最可能是**模型自己没把非法值原样发出去**。⛔ **不得写成「当初测错了」**，
   只能写「**今天复现不出来，原因只能推断**」。

## 三条方法教训（这才是要带走的）

1. **"被测系统的行为"与"模型的行为"是两层**。端到端跑只能证明「**这一次**没出问题」，
   **不能证明守卫存在**。要证明守卫，必须**绕过模型、定向送入非法输入**（固定桩 + 断言状态与 trace）。
   ⇒ 凡是"守卫/校验到底有没有生效"这类问题，**探针比评测更合适**：确定性、零付费、可逐条对照。
2. **同一件事的两种记录会互相打架，而且没人会主动对齐**：本轮报告 **§5.3** 写的是「判 `DEGRADED`」，
   而 **§5.5** 的逐题表写的是「实测 `OK`」——**同一份文档里两处结论相反**，靠人工扫才被发现。
   ⇒ 更正时**两处一起改并留痕**，别只改一处。
3. **"缺口存在"与"性质变了"要分清**：今天拦住的是**越界参数的执行**，但状态给的是 `DEGRADED`、
   数据集要的是 `REJECTED` ⇒ **该题仍按失败计**。⛔ **不许因为"守卫有效"就把整条说成没问题**；
   表述要落到「**执行层校验拦住了注入**」，⛔ **不是「没有注入风险」**。
