# 把「没被作答路径使用的提示词」当成了 Prompt 基线

> ⚠️ 本条记录的是**我自己在 C-51 第 13 轮的错误结论**，以及它差点造成的付费损失。
> 记录时间：第 14 轮（发现于执行 v2 实验**之前**）。⛔ 本轮**未发生**任何付费调用。

## 我当时的结论

第 13 轮我为了做 Prompt v1 / v2 对照，把 `ChatClientConfig.SYSTEM_PROMPT` 认定为**系统提示词的 v1**，
给它加了冻结注释、写了逐字快照测试，并据此新增了 `PromptVersions`（`v1()` 指向它、`v2()` 从它派生）。

**这个结论是错的。**

## 实测到的事实

全仓库检索 `SYSTEM_PROMPT` / `defaultSystem` 的使用点，结果表明：

- `ChatClientConfig.SYSTEM_PROMPT` **只有一个消费方**：`ChatStreamController`（Web 流式问答接口）；
- 而**产出 L3 / L5 / L6 出分产物**的评测链路是
  `LayerRunCli` → `QuestionPipeline.create(jdbc, env, chatModel, …)` → `AnswerComposer`，
  它拿到的是**裸 `ChatModel`**，**⛔ 从不经过 `ChatClientConfig` 这个 Bean**；
- 该链路真正使用的系统提示词在
  `backend/src/main/java/com/canalmind/eval/pipeline/AnswerComposer.java:61-69`
  的 `systemPrompt()`，并在第 146 行以 `new SystemMessage(systemPrompt())` 放进消息列表。

⇒ **两条链路的系统提示词是两个互不相干的东西。** 我冻了一个（Web 侧），
而实验要改的是另一个（评测侧）。

## 差点造成的后果（这是本条记录的真正价值）

若按当时的接线直接跑 v2：改的是 `ChatClientConfig`，而 L5 作答根本读不到它
⇒ 结果必然是 **v1 ≡ v2**，我会据此写下

> 「Prompt 强化对 L5 没有效果（0.1500 → 0.1500）」

并把它当成一条**实验结论**写进《评测报告》。而真相是**那段提示词从未被 L5 的作答读过**。

**这属于本项目反复出现的同一类错误：「合法但错」**——产物格式对、数字对、流程跑通、
退出码 0，**唯独测的不是我以为在测的东西**。区别只在于这次它是**假阴性**（把有效的改动判成无效），
而之前几次多是**假阳性**（把失败判成成功）。

⚠️ 更值得记的一点：**40 次付费调用会照常扣费**，且不会有任何东西报错。
「跑了、出数了」与「测对了」是两件事——这与 `LayerRunCli` 里
「**能跑通**和**跑对了**是两件事」的既有告诫是同一条。

## 为什么这次在付费前被挡住

因为接线之前先做了一次**「谁在读这段提示词」的全仓库检索**，而不是假设
「名字叫 SYSTEM_PROMPT，那它就是系统提示词」。

**可复用的教训**：⛔ **不要靠命名推断调用关系**。
凡是要改一个"被某条链路读取"的常量，先**实测它的消费方**——
`grep` 一遍引用点，成本几分钟，收益是避免一次"结论全错但不报错"的实验。

## 修正动作

- ✅ 第 13 轮已落地的 `PromptVersions` + 冻结测试**保留**——Web 侧提示词值得冻结，
  且冻结测试本身没写错（它确实逐字匹到了 `ChatClientConfig` 的文本块）；
- ⚠️ 但 v1/v2 对照的**目标必须改到 `AnswerComposer.systemPrompt()`**；
- ⛔ **在重新接线并核对「该链路确实读到了 v2」之前，不得执行 v2 的付费批次**——
  本次核对办法：用 `--echo-prompt` 之类的手段**确认提示词正文里出现了 v2 的追加块**，
  而不是只看"跑成功了"。
