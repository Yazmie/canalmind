# HNSW 索引命中，却不报错地少返回结果

> 类别：[检索工程](README.md) ｜ 返回总索引：[../README.md](../README.md)
> **★ 这是本目录技术含金量最高的一条。**

| 项 | 内容 |
|---|---|
| **背景** | 决策 C-23 选了 **HNSW** 索引（pgvector），规格书第 628 行要求"**检查执行计划确认索引用上了**"。 |
| **第一轮验证** | 3000 行 × 1024 维的实测：`EXPLAIN` 显示 `Index Scan using _vec_probe_hnsw`——**索引确实命中，看起来一切正常**。 |
| **但知识库提醒了我** | 知识库《RAG 向量索引算法和向量数据库》第 175–184 行特别提醒：**HNSW 遇到 `WHERE` 过滤条件时要重点看执行计划**。我就去专门测了带过滤的场景。 |
| **发现的问题（实测数据）** | 过滤条件 `doc_id='doc-3'`（实际匹配 116 行 / 3000 行），`LIMIT 10`：<br>· 无过滤 → 返回 **10 行** ✔<br>· **带过滤（默认设置）→ 只返回 2 行** ⚠️<br>· 带过滤 + `hnsw.iterative_scan = relaxed_order` → 恢复 **10 行** ✔ |
| **根因** | HNSW 是**近似索引**，`LIMIT` 在**索引扫描阶段**就被满足了。于是它只取回 `ef_search` 个近邻，**再**按过滤条件筛——命中数可能远少于 `LIMIT`。**最危险的地方是它不报错，只是悄悄少给结果。** |
| **为什么对本项目特别要紧** | 我们的检索**天然带过滤**：要按文档**版本有效期**（`effective_from` / `effective_to`）限定只用现行版本，还要按 `doc_id` 限定范围。**这不是边缘场景，是主路径。** |
| **怎么解决的** | ①把 `SET hnsw.iterative_scan = relaxed_order` **写进入库/检索实现要求**，明确"不得依赖默认值"；②把该风险纳入**第 4 周消融实验的对照项**，并作为 **badcase** 记录进《评测报告》；③把实测数据与复现脚本 `backend/scripts/verify_pgvector.ps1` 一起留档。 |
| **业务含义** | **"索引命中"不等于"结果正确"。** 性能优化的近似结构，会用**结果完整性**换速度，而且**静默地换**。所以：<br>· 验收检索链路时，不能只看"走的什么索引"，必须**对账结果条数**；<br>· 任何"带过滤 + Top-K"的场景都要专门测；<br>· **近似索引的副作用，必须用"结果数对不对"来守护**，而不是用"计划好不好看"来判断。 |
| **可能被追问** | "为什么不用精确索引（IVFFlat / 暴力搜索）避开这个问题？"→ 答：可以，但 HNSW 在召回率/延迟上的权衡更适合本项目规模；**关键不是换索引，而是承认"近似 + 过滤"必然有语义缺口，然后用显式配置（`iterative_scan`）+ 结果对账把它管住**。 |
| **可能被追问（进阶）** | "`iterative_scan` 的代价是什么？"→ 实测数据显示它的扫描/缓存读取量更大（`shared hit` 从 **949** 增到 **2478**），**是用更多检索开销换结果完整性**——这个权衡必须写进评测，而不是当成免费午餐。 |
| **复现方式** | `powershell -ExecutionPolicy Bypass -File backend/scripts/verify_pgvector.ps1 -ConnectOnly`（须先另起后台作业跑临时 PG 集群，见[环境坑/pg_ctl受限令牌](../环境坑/pg_ctl受限令牌.md)） |
