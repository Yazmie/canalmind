# embedding 模型是"索引格式"的一部分

> 类别：[检索工程](README.md) ｜ 返回总索引：[../README.md](../README.md)

| 项 | 内容 |
|---|---|
| **背景** | 决策 C-22 选了 Ollama + 本地 `bge-m3`。 |
| **约束来源** | 知识库《RAG 知识库文档如何更新……》**第 39 行**把"本地模型与云 API 混用"点名为生产中最易忽视的坑，原话是上线后**"召回率直接腰斩"**；第 302 行指出**换模型必须全量重建索引**。 |
| **怎么落地的** | ①把"**索引与查询必须使用同一 embedding 模型/版本**"写成 **C-22 的配套硬约束**；②模型信息写入 chunk 元数据，查询时校验，**不一致直接拒绝**而不是降级。 |
| **实测佐证** | 本次实测 `bge-m3`：维度 **1024**、向量范数 **1.000001**（已 L2 归一化）。范数为 1 这件事直接决定了**内积 `<#>` 与余弦排序等价**——即索引侧的算子选择（`vector_ip_ops`）是有依据的，不是随便挑的。 |
| **业务含义** | 向量检索里，**embedding 模型是"索引格式"的一部分**，不是可替换的实现细节。它更像是**数据库的排序规则（collation）**：悄悄换掉，索引依然能查、依然不报错，但**结果已经没有意义了**。 |
| **可能被追问** | "怎么防止误换模型？"→ 答：**把模型身份当成数据契约**：写入时记入元数据、读取时强制校验、不匹配则**失败而非降级**（降级会把"明显错误"变成"难以察觉的劣化"）。 |
| **可能被追问（进阶）** | "为什么选内积而不是余弦？"→ 答：因为实测确认向量**已 L2 归一化**，此时内积与余弦**排序完全等价**，而内积计算更省。**但这是个前提依赖**——若将来换的模型不做归一化，这个选择就不再成立，所以范数这件事必须记录在案。 |
