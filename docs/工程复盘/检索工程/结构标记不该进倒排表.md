# 结构标记不该进倒排表

> 类别：[检索工程](README.md) ｜ 返回总索引：[../README.md](../README.md)

| 项 | 内容 |
|---|---|
| **现象** | 第一轮入库后，词元 `1` / `2` / `3` / `4` **占据 df 榜首**：df 分别 **317 / 318 / 310 / 217**，也就是出现在约 **60% 的 chunk** 里，idf 只有约 **0.52**。它们与任何业务语义无关，是**纯粹的排名噪声**——任何查询都会被它们带偏，而且**不报错**。 |
| **根因（一类标记）** | 语料是 Markdown 写的规则文本，里面有一类**纯结构标记**：行首的 Markdown 有序列表编号 `1. ` `2. ` …。SQL 实测 **1170 处**，覆盖 **454 个正文 chunk 中的 301 个（66%）**。 |
| **根因（二类标记）** | 表格被切成独立 TABLE chunk 后，正文原位留下占位标记 `[TABLE:<16 位十六进制 chunk_id> rows=N cols=M]`，实测语料 **87 处**；另有 **7 个 BODY chunk 的正文就只有这一个标记**（每个 **38 字节**，是"整节只有一张表"时的切分退化产物）。不剥的后果是**16 位十六进制 chunk_id 会变成词元**——每个 chunk 都被灌进一堆 id 片段，"任意两个 chunk 都相似"，同样**不报错**。 |
| **剥离规则（刻意保守）** | 行首 + **1~3 位 ASCII 数字** + `.` + **至少一个空白**，四条缺一不可。于是 `4.20 元/吨`（点后是数字）**不匹配**、`2026 年`（4 位数字 / 无点）**不匹配**、`障碍消除后 2 小时内补办申报`（不在行首）**不匹配**——**这些是真实内容，必须保留**。 |
| **为什么只写这一条规则** | **判定必须来自对语料的测量**：先实测出语料里**只存在这一种编号写法**——`1)`、`1、`、`（1）`、`(1)` 各 **0 处**——才敢只写这一条精确规则，而不是写一个"看起来像编号的都剥"的贪婪正则。**贪婪正则的第一个受害者就是真实数值。** |
| **交叉验证（本次最强的一条证据）** | 剥离前后两个档案**共存在库里**，于是可以做独立对照：`rules-v1` 词元总数 **35764** → `rules-v2` **34594**，**减少量恰好 1170，与 SQL 独立测出的编号处数完全相等**。副产物：倒排行数 **24783 → 23696（−1087）**，而**词表大小不变（都是 3303 个词）**——因为数字本身在表格单元格、"2 小时"这类真实内容里也存在，被剥掉的只是**编号那一次出现**。**两个口径（Java 侧切分 / SQL 侧统计）给出同一个数，这才算证据。** |
| **7 个"只剩标记"的退化 chunk 怎么处理** | 它们切不出任何词元，**不进 BM25 语料**（否则以 dl=0 拉低 avgdl，把全库的分数尺度带偏）。但**判据必须分成两类**：**正文只有标记/标点 → 说明原因后排除**；**含实质文字却切不出词元 → 直接让入库失败**。后者的含义完全不同——**那是分词器或词典失效了**，把它当"空 chunk 跳过"就是把一个真缺陷**静默吃掉**。入库 CLI 会逐个打印原因（`classifyEmptyChunk`）。 |
| **把观察变成检查** | 上面那组量化对比**不是一次性观察，而是可重复执行的检查**：`backend/scripts/verify_bm25.py` 每次运行都断言"**词元减少量 == 语料里实测的编号处数**"，不等就 **FAIL**。 |
| **结论与做法** | 判断标准是"**这个片段是文档结构还是内容**"。凡是"**任意两个文档都会因为共享它而相似**"的片段——占位标记、列表编号、表格分隔行——都**不该进倒排表**；而"要不要剥"**必须靠测量**，不能靠"我觉得这看起来像标记"。 |
| **业务含义** | 倒排表的 df 是一个**全局量**：一个无意义的片段只要**到处都出现**，就会自动获得"高频停用词"的地位。停用词表能挡掉通用词（的 / 了 / 是），**挡不掉"你自己语料的结构"**——那是只有你能测出来的东西。 |
| **可核对锚点** | • `backend/src/main/java/com/canalmind/rag/tokenize/JiebaShippingTokenizer.java`（`stripTableMarkers` / `stripListMarkers`，含 1170 / 66% / 87 / 7 几个实测数字的 javadoc）<br>• `backend/src/main/java/com/canalmind/rag/ingest/Bm25IngestCli.java`（`classifyEmptyChunk`：两类"空 chunk"分开判定）<br>• `backend/scripts/verify_bm25.py`（检查项 6：断言词元减少量 == 实测编号处数）<br>• `backend/src/test/java/com/canalmind/rag/tokenize/JiebaShippingTokenizerTest.java`：`listMarkersAreStripped`、`listMarkerStrippingDoesNotHitRealNumbers`、`tableMarkerIsStripped`<br>• 对照档案：`docs/评测报告/bm25-baseline.json` |
| **可能被追问** | *"怎么确认剥对了、没剥多？"* → 靠**两个独立口径对齐**：一个是 Java 侧两个档案的词元总数之差（1170），一个是 SQL 侧直接数的编号处数（1170）。**单看"切分结果变得更好看了"不构成证据。** |
| **可能被追问（进阶）** | *"为什么不用停用词表把 1/2/3 加进去？"* → 因为那会**同时杀掉真实数字**（"2 小时""4.20 元/吨"里的数字是真内容）。停用词表按**词**过滤，而这里要按**位置 + 形态**过滤——**同一个"不要它"，判据的粒度不同。** |
