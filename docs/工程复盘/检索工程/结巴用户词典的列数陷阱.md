# 结巴用户词典的列数陷阱（词频静默退回默认值）

> 类别：[检索工程](README.md) ｜ 返回总索引：[../README.md](../README.md)

| 项 | 内容 |
|---|---|
| **背景** | 中文 BM25 需要分词前置，而知识库对「中文 BM25 分词」**无覆盖**（`AGENTS.md` §4.6 明确列为已知缺口），故走外部查证 + 实测。选用的库是 `com.huaban:jieba-analysis:1.0.2`——纯 Java、零传递依赖、Apache-2.0。 |
| **现象** | 自定义词**几乎永远切不出来，而且不报错**。词典文件写得"看起来完全正确"（照抄标准 jieba 的三列格式：`词 词频 tag`），分词器照常启动、照常输出词元，只是那些**领域词一次都不出现**。 |
| **根因** | `loadUserDict` 用 `line.split("[\t ]+")` 取字段，**只有 `tokens.length == 2` 时才采用第二列作为词频**。写成三列时行内多出一个字段，词频这一支直接落空，**静默退回默认值 3.0**。 |
| **为什么难发现（一）** | 3.0 这个默认值本身"合法"——不抛异常、不打日志，词表里也确实**有了**这个词。失效发生在**最大概率路径的打分**里，而不是加载环节。你检查"词典加载成功了吗"，答案是"成功了"。 |
| **为什么难发现（二）** | 该库基础词典 **349045 词、总频次 60101878**，于是默认词频的打分是 `log(3/60101878) = -16.81`（自然对数）——**比基础词典里任何词都低**。实测参考值：通过 **-7.45**、管理 **-7.70**、规定 **-7.80**、船 **-8.95**、闸 **-10.85**。于是"把词加进词典"这个动作，等于**把它加成全库最低分**：最大概率路径**永远不选它**。 |
| **实测证据** | 用 `javap` 核对 `WordDictionary` 的公开方法：只有 `loadUserDict(java.nio.file.Path)` 与 `loadUserDict(Path, Charset)` 两个重载——**没有 InputStream 版本**。这条"没有 InputStream 版本"的事实，决定了下面第三条坑的绕法。 |
| **词频怎么定** | 本项目最终选 `DOMAIN_FREQ = 100000`（`log = -6.40`，高于基础词典里实测最高频的"通过" -7.45），实测 **164 个词典词全部能被完整切出**。 |
| **第二类坑：注释行与空行** | 词典文件里 `#` 开头的注释行会被解析成"词 = `#`、词频 = 注释正文"，随后 `Double.valueOf` 抛 `NumberFormatException`；而该方法**只 catch IOException**，所以异常会直接冒出来。空行则执行 `freqs.put(null, ...)`——往词表里塞一个 **null 键**。**即"文件里加一句注释"和"文件末尾多一个空行"都是缺陷，不是风格问题。** |
| **第三类坑：IOException 被吞** | `loadUserDict` 把 `IOException` **吞掉只打日志**。于是"临时文件没写成 / 读不了"这类失败在它的视角下是**静默**的——词典照旧是空的，词照旧切不出来，链路照旧不报错。又因为它**只接受 `Path`**，而本项目词典是打进 jar 的**类路径资源**（运行时没有真实路径），实现上必须先落一份**字节完全相同**的临时文件再交给它——**这条"落临时文件"的路正好落在上面那类静默失败上**。 |
| **因此必须自己核对** | 加载后**不能信库自己**：本项目对所有词条调用 `WordDictionary.containsWord`，**缺一个就启动即报错**。判据是"库的词表里真的有这个词"，而不是"我调过 `loadUserDict` 且它没抛异常"。 |
| **为什么要自建词典** | "为什么非要自建词典"是会被追问的，实测缺口就是答案：`南宁港`、`过闸`、`闸室` 在基础词典里**不存在**；`危险品` 基础词频只有 **19**（`log = -14.97`），会被切成 `危险`/`品`。这些恰好是本项目语料的核心名词。 |
| **结论与做法** | ①**自己写严格解析器**（`ShippingDictionary.parse`）：必须**恰好两列**、词频为**正整数**、**无注释、无空行、无重复**，违反就抛异常，并在消息里给出**生成脚本路径**（让人知道该去改生成步骤，而不是去手改词典）；②加载后用 `containsWord` **逐条核对 164 个词条**；③单元测试与 CLI 自检都断言"每条词典词都被完整切出"——`Bm25IngestCli --selftest` 实测输出 `词典自检：164 词，实检 164，失败 0`；④**词典不进 git 手改**：由 `backend/scripts/build_shipping_dictionary.py` 从权威来源生成，档案里记的是词典文件字节的 **sha256**（不是版本号），理由是"**版本号靠人记得改，sha256 由文件字节算出**"。 |
| **业务含义** | 这是"**合法但错**"的又一个变种，而且失效方式最阴——**你做的操作（加词）让这个词的排名变得更差了**。默认值不是"中性"，它是在**真实数据的量纲**里的一个具体值。凡是有缺省值的配置，都要问一句：**这个缺省值相对于真实数据是什么量级？** |
| **可核对锚点** | • `backend/src/main/java/com/canalmind/rag/tokenize/ShippingDictionary.java`（严格解析、`containsWord` 逐条核对、词频常量、`sha256()`、`VERSION`）<br>• `backend/src/test/java/com/canalmind/rag/tokenize/ShippingDictionaryTest.java`<br>• `backend/src/test/java/com/canalmind/rag/tokenize/JiebaShippingTokenizerTest.java`（用例 `everyDictionaryWordIsKeptWhole`）<br>• `backend/scripts/build_shipping_dictionary.py`（词典由它生成，**不手改**）<br>• `backend/src/main/resources/rag/tokenize/shipping-dictionary.txt`：**164 词**，sha256 `180d70e1281426a730049ac492fa57a0b4a7d0b91ba0f8b3c1c75f04478d4cb1`<br>• `Bm25IngestCli --selftest` 实测输出：`词典自检：164 词，实检 164，失败 0` |
| **可能被追问** | *"你怎么发现词没切出来？"* → 不是靠读代码，是靠**先写下判据再跑**：把"每条词典词都必须在自己的文本里被完整切出"写成用例（`everyDictionaryWordIsKeptWhole`），它当场红。**如果只做"词典能加载"的检查，这个缺陷会一路活到线上。** |
| **可能被追问（进阶）** | *"为什么不直接抄标准 jieba 的三列格式？"* → 因为**不同实现的格式契约不一样**：Python 版 jieba 支持 `词 词频 tag`，而这个 Java 移植版**只认两列**，且它的失败方式不是报错而是退回默认值。**跨语言移植来的库，格式契约要按实现核，不能按名字核。** |
