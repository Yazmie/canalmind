## 本类共同教训

**性能优化的近似结构，会用"结果完整性"换速度，而且静默地换。**

所以验收检索链路时：
- 不能只看"走的什么索引"，必须**对账结果条数**
- 任何"**带过滤 + Top-K**"的场景都要**专门测**
- **近似索引的副作用，要用"结果数对不对"来守护**，而不是用"计划好不好看"来判断
- ⚠️ **语料里的"结构标记"必须按真实形态匹配**：表格占位标记带**行列信息**，真实写法是
  `[TABLE:<id> rows=N cols=M]`（SQL 实测：87 个 `TABLE` chunk 的占位标记中，**id 后紧跟 `]` 的 = 0 个**、
  **id 后接空格 + 行列数的 = 87 个**）。所以按 `'%[TABLE:<id>]%'` 精确匹配会**一行都匹配不到且不报错**——
  这是[用合成输入先空跑评测链路](../工程方法/用合成输入先空跑评测链路.md)抓到的 bug ②，属"结构标记"这一族的又一例。

## 第二条主线：**决定"被索引的表示"的东西，全都是索引格式**

BM25 分词这一轮又咬出三次"**不报错的失效**"，它们其实是同一件事的不同侧面：

| 失效 | 一句话 | 条目 |
|---|---|---|
| **用户词典加载成功，词却永远不被选中** | 三列格式 → 词频静默退回默认值 3.0 | [结巴用户词典的列数陷阱](结巴用户词典的列数陷阱.md) |
| **结构标记进了倒排表** | 列表编号 / 占位 id 让"任意两个文档都相似" | [结构标记不该进倒排表](结构标记不该进倒排表.md) |
| **改了切分规则，档案身份没变** | 就地重灌会把两套口径混进同一档案 | [分词规则也是索引格式的一部分](分词规则也是索引格式的一部分.md) |

> **讲法**：这三条合起来是一句——**"同样的输入被表示成什么"也是索引格式**，
> 和 embedding 模型、索引算法一样必须被版本化、被测量、被守卫。
> 而它们的共同症状是：**分数照样算得出来，只是不再有意义。**

## 第三条主线：**「配置好」不等于「生效了」，而且没说出口的口径等于没有**

向量通道这一轮又咬出两条，它们同属一件事：**配置与口径都活在代码/文档里，唯独不在证据里**。

| 失效 | 一句话 | 条目 |
|---|---|---|
| **索引建了、算子类也匹配了，但规划器不选它** | 541 行下 `<=>` 与 `<#>` **都是 `Seq Scan`**；只有 `SET enable_seqscan=off` 才出现 `Index Scan using rag_chunk_embedding_hnsw` | [建了索引不等于用上了索引](建了索引不等于用上了索引.md) |
| **两种等价度量的分数差 1e-7，而产物没有度量字段** | 名次 40/40 一致、分数不同；**仅凭产物无法判断用了哪个度量** | [度量口径没进产物](度量口径没进产物.md) |

> **讲法**：验收一句话要落到**具体条件**上——「索引能用吗」和「这次查询用了索引吗」是两个问题；
> 「分数可比吗」和「这两份分数是同一口径吗」也是两个问题。
> ⛔ 尤其注意**对外表达**：本项目当前只能说「索引可用且结果与精确检索一致」，
> **不能说「HNSW 已启用」**（跨类指针：[诚实记录/已知薄弱环节](../诚实记录/已知薄弱环节.md)）。
> 而口径必须写进**产物之外的元数据或产物字段**里——否则一旦两份产物被混用，
> 漂移量只有 1e-7，**任何「看起来差不多」的直觉都不会报警**（跨类指针：
> [数据一致性](../数据一致性/README.md) 那类讲的正是「隐式数据契约」）。
> **另一半在摘要侧**：摘要（数据包 / 汇报数字）若不写「取自哪个产物、哪个 sha」，就会过期而不报警
> —— 跨类指针：[诚实记录/中间产物值被当成最终值沿用](../诚实记录/中间产物值被当成最终值沿用.md)。
