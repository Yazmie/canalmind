# 建了索引 ≠ 用上了索引

> 类别：[检索工程](README.md) ｜ 返回总索引：[../README.md](../README.md)
>
> **一句话**：算子类不匹配 → `<=>` 根本用不上那个索引；改成算子类匹配的 `<#>` 之后**仍然不被选中**——
> **「建了索引」「算子类匹配」「规划器愿意用」是三件独立的事**，而失败的样子都是「`EXPLAIN` 里少一行字」，不报错。

| 项 | 内容 |
|---|---|
| **现象** | 向量通道默认度量是 `cosine`（精确扫描 `<=>`），而 V3 迁移建的 HNSW 索引是 **`vector_ip_ops`（内积算子类）**——`backend/src/main/resources/db/migration/V3__add_rag_chunk_vector_table.sql` 第 232–233 行 `CREATE INDEX … USING hnsw (embedding vector_ip_ops)`。**两者算子类不匹配**，所以默认路径**必然**走顺序扫描。 |
| **我当时的判断（错在哪）** | 决策 **C-23** 要求「须 `EXPLAIN ANALYZE` 验证命中」，规格书第 628 行也要求「检查执行计划确认索引用上了」。我原本以为：改成与索引算子类一致的 `--metric ip`（`<#>`）就会看到 `Index Scan`——**把「算子类匹配」直接当成了「会被选中」**。 |
| **实测事实（逐条可核对）** | ① `cosine`：`Seq Scan on rag_chunk (rows=541)` + `Sort Method: top-N heapsort`，`Execution Time: 3.479 ms`（《评测报告》§3.4 记作 3.5 ms）；<br>② **`ip`（`<#>`，算子类与索引匹配）同样是 `Seq Scan`**（`rows=541`，2.628 ms）——**541 行规模下规划器不选 HNSW**；<br>③ **只有 `SET enable_seqscan=off` 时才出现 `Index Scan using rag_chunk_embedding_hnsw`**（`Incremental Sort` + 索引返回 6 行取 5 行，1.216 ms）→ 证明**算子类确实匹配、索引确实可用**；<br>④ **同样禁用 seqscan 的 `cosine` 仍然只有 `Seq Scan`**（3.153 ms）→ `<=>` 侧**没有任何可用的向量索引**。 |
| **锚点** | 探针与被测语句同体：`backend/target/vector-probe/explain-vector.sql`（A–D 段）与 `explain-vector2.sql`（E–G 段，含两处 `enable_seqscan=off` 对照），输出 `explain-out.txt` / `explain-out2.txt`。<br>「两种度量只差算子」的实现：`backend/src/main/java/com/canalmind/rag/vector/VectorSearcher.java`——`SEARCH_SQL_TEMPLATE` 的两个 `%s` 分别是**打分表达式**与**排序算子**，类注释写明「两种度量只应差在算子」。<br>报告口径：`docs/评测报告/检索段-纯向量基线.md` §3.4。 |
| **为什么规划器不选它（本项目已记录的根因）** | ① 批量入库后**从未 `ANALYZE`**，`pg_class.reltuples = -1`、`relpages = 0`——规划器是在**没有统计信息**的情况下做决定；② `ANALYZE` 之后（`reltuples=541, relpages=59`）结论仍不变：规划器默认 `Seq Scan` cost **101** / 实测 **3.65 ms**，强制 HNSW cost **1487** / 实测 **1.10 ms**，**两者都只有毫秒级，选更简单的计划是合理的**；实测 **≥1000 行才自发选 HNSW**；③ pgvector 的代价模型**显著高估** HNSW（541 行约 **5.7 倍**、5 万行**合成表**约 **80 倍**）。三条均记在 `docs/DECISIONS.md` 的更正行与 `docs/进度看板.md` §3.3。 |
| **教训** | **「建了索引」和「用上了索引」之间隔着三个独立条件**：算子类匹配、规划器认为划算、统计信息是最新的。任何一条不成立，**`EXPLAIN` 里只是「没有那行字」**——不报错、不告警。而验收时最容易发生的事，恰恰是把「计划里没有那行字」读成「大概是走了吧」。 |
| **因此不能对外说什么** | 严格按 C-23 与规格书第 628 行的原话，**「确认索引用上了」在当前 541 行规模下并不成立**。可对外讲的准确表述是：**索引可用**（算子类匹配、强制后命中，且 Top-20 与精确顺序扫描完全一致：overlap 20 / missing 0），**但未被规划器选中**。⛔ **不得宣称「HNSW 已启用 / 线上在用 HNSW」**。 |
| **顺带的一个正向结论** | 评测基线**故意**走 `cosine`：算子类不匹配 → 必然精确顺序扫描 → **没有近似误差**——这正是基线想要的（也让「过滤后静默少返回」这类近似副作用不进基线）。见 [HNSW索引过滤条件静默少返回](HNSW索引过滤条件静默少返回.md)。 |
| **⚠️ 未验证** | ① 换到 **≥1000 行**（规划器自发选 HNSW）后，**基线与执行计划都还没重跑**——已列为第 4 周规模测试复核项；② 代价模型高估的「80 倍」那一档来自**合成表**（本项目真实语料只有 541 行），**不可当作真实语料的结论**。 |
| **可能被追问** | 「既然用不上，建它做什么？」→ 答：C-23 的选型是为**规模增长**准备的；本项目真正拿到的是**把启用门槛量化出来**（≥1000 行）加上「索引可用且结果与精确检索一致」的证明。**这才是中小数据量下「验证索引」能得到的诚实结论。** |
