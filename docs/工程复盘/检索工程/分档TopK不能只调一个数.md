# 分档 Top-K：为什么不能只调一个数

> 类别：[检索工程](README.md) ｜ 返回总索引：[../README.md](../README.md)

| 项 | 内容 |
|---|---|
| **设计依据** | 知识库《RAG 优化》第 147–149 行给出**三档参数**：`recall_top_k`（召回 30–100）→ `rerank_top_n`（精排 5–10）→ `context_top_n`（进上下文 3–6）。 |
| **要点** | 这三档是**串联漏斗**，各自解决不同问题：召回档要"宁可多召回、别漏"；精排档要"排序准"；上下文档要"喂给模型的别太杂，且控制 token"。 |
| **业务含义** | **只调"最终给几条"是调不出效果的**——如果召回阶段就漏了，后面精排再准也救不回来。**分档参数化的意义是把"漏"和"排错"两类问题解耦**，分别定位。 |
| **可能被追问** | "怎么知道是哪一档的问题？"→ 答：这也是我要建 **Golden Set + Context Recall 基线**的原因：**Recall 低 → 召回档的问题；Recall 高但答案错 → 精排或生成的问题。** 没有基线，就只能靠感觉归因。 |
| **⚠️ 与 HNSW 陷阱的联动（容易被忽略）** | 分档的前提是"**召回档真的召回了 `recall_top_k` 条**"。而[带过滤的近似索引会静默少返回](HNSW索引过滤条件静默少返回.md)——**也就是说，召回档可能根本没拿到你以为的条数**，后面的调参照样做不准。**这两个问题必须一起看。** |
