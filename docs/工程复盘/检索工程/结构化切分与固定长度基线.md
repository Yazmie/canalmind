# 结构化切分与固定长度基线：为什么两者都要

> 类别：[检索工程](README.md) ｜ 返回总索引：[../README.md](../README.md)

| 项 | 内容 |
|---|---|
| **设计依据** | 知识库《RAG 文档处理与切分策略》**第 83 行**指出法规/合同类文档应"**按条、款、项**切分以保留法律效力单元"；《RAG 优化》**第 364 行**明确要求**保留固定长度基线**用于对照。 |
| **决策** | **D1 → C-21**：结构化切分（条/款/项）为**主路径**，固定长度切分作为**评测基线**（基线是必做项，不是备选方案）。 |
| **为什么两者都要** | 结构化切分是**更好的方案**，但"更好"需要**证据**。没有基线，就无法说明提升来自切分策略，还是来自"文档本来就短"。第 4 周的消融实验要有对照物才能出结论。 |
| **业务含义** | 这对应**"每个优化都要有对照"**的工程习惯：**改动 A 之后指标变好，不能直接归功于 A**——可能是别处变了，也可能换任何切分方式都会变好。**基线不是备选方案，是论证材料。** |
| **可能被追问** | "结构化切分的代价是什么？"→ 答：**切分逻辑更复杂**（要识别条/款/项层级、表格与正文混排），且**对文档格式更敏感**——所以我在写语料时就把格式约定固化（见 `docs/规则语料/README.md` §3），并加了格式校验，避免切分器面对"意外格式"。 |
| **⚠️ 语料格式校验与切分的关系** | `validate_corpus.py` 里的"条号连续、条标题唯一、标准管道表"等检查，**不只是语料卫生——它们正是结构化切分的前置条件**。切分器依赖"每条都有可识别的标题"，这个不变量必须由校验守护。 |
