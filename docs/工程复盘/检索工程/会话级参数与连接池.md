# 会话级参数与连接池：`hnsw.*` 为什么"在新会话里不存在"

> 类别：[检索工程](README.md) ｜ 返回总索引：[../README.md](../README.md)

| 项 | 内容 |
|---|---|
| **问题** | 单独执行 `SET hnsw.ef_search = 100` 看似成功，但紧接着在新会话里 `SHOW hnsw.ef_search` 报 `unrecognized configuration parameter`（PG 日志实测确认：`ERROR: unrecognized configuration parameter "hnsw.ef_search"`）。 |
| **根因** | `hnsw.*` 是 **pgvector 注册的自定义 GUC**，**只有当该会话加载了 `vector` 扩展之后才存在**。每条 `psql -c` 都是一次独立会话。 |
| **怎么解决的（测试侧）** | 把 `SET` 与 `EXPLAIN` 放进**同一个 psql 会话**（写成 `.sql` 文件用 `psql -f` 执行）。 |
| **业务含义（这才是重点）** | 这直接关系到**连接池**：`SET` 是**会话级状态**，在连接池下会**串到别的请求上**。所以：<br>· 会话级参数（如 `ef_search`、`iterative_scan`）**不能靠"全局 SET 一次"**；<br>· 必须明确是"每连接设置"还是"每查询设置"，并在连接池层面保证它**一定生效且不泄漏到无关请求**。 |
| **可能被追问** | "连接池下你会怎么落？"→ 答：用连接初始化回调统一设置会话参数（保证每个物理连接都被设过），或改用 `SET LOCAL` 限定在事务内——**关键是"参数生效"必须是机制保证的，不能靠约定**。 |
| **⚠️ 一个反向风险** | 如果只在**部分**连接上设了 `iterative_scan`，那么"结果条数对不对"会**随机取决于这次请求落到哪条连接**——这类 bug 极难复现。**这正是它必须由机制保证、而不能靠约定的原因。** |
