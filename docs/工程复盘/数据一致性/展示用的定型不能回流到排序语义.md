# 展示用的定型不能回流到排序语义

## 背景：一个刻意的设计决定

第 3 周的结构化查询要把结果与**金标准逐字节比对**（Execution Accuracy，决策 C-35）。
为避免"`2.90` vs `2.9` 这种表示差异"被判成"算错"，仓库里的聚合数值**一律在 SQL 里就 `::text` 定型**：

```sql
coalesce(round(sum(w.weight_ton), 2), 0)::text AS value
```

这解决了一类问题（表示差异），却在同一行代码里埋下另一类问题。

## 现象：排名按"文本"比大小

分档取前 N 名要排序，而排序表达式当时**复用了同一个 `valueExpr`**：

```java
sql.append(" ORDER BY " + valueExpr + " DESC NULLS LAST, label ASC");
```

按"运单数"统计时，`valueExpr = count(*)::text` ⇒ **ORDER BY 用的是文本序**：

```
"10" < "9"     （字典序）
  但
  10 >  9      （数值序）
```

后果不是报错，而是**名次错**：运单数 9 的分组排在第 1，运单数 10 的分组排在第 2。
只有在"跨位数"（9 → 10）的分组上才暴露，10 组以内、或各组位数相同时**完全看不出问题**——
本数据集按月份分组恰好是两位数、按货类分组计数在四位数量级，所以我第一遍看输出时"没觉得不对"。

**是我在写金标准生成脚本（Python 侧）时才发现的**：Python 侧我按数值排序，两边对不上，
于是回头查 Java 的 ORDER BY。**两套实现的价值就在这里**——同一口径写两遍，
差异会在比对时冒出来，而不是等用户发现名次不对。

## 教训（可迁移）

1. **"展示用的定型"（`::text`、`to_char`、`format`）一旦回流到比较/排序/聚合语义，就会静默改行为。**
   定型只能用在**最后一跳**（出参），不能参与 `ORDER BY`、`WHERE`、`GROUP BY` 的语义。
2. **同一表达式承担两个职责时，要显式拆成两个**。修复后：

   | 职责 | 表达式 |
   |---|---|
   | 出参（逐字节可比） | `count(*)::text` |
   | 排序（语义正确） | `count(*)` |

   代码里加了注释点名"**不能用 valueExpr 排序**"，因为下一个人很可能再顺手复用一次。
3. **"看起来对"的排序最难抓**：结果集行数对、标签对、只有次序可能错。
   ⇒ 凡"取前 N 名"的接口，评测集里就该有**跨位数**的样本（本项目的 L1-031 就是"运单数前 5 名"）。
