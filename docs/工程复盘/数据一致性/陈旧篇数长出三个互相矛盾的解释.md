# 陈旧的篇数长出三个互相矛盾的解释（都以为"已经交代过了"）

> 类别：[数据一致性](README.md) ｜ 返回总索引：[../README.md](../README.md)

| 项 | 内容 |
|---|---|
| **现象** | `docs/规则语料/README.md` 说语料是 **28 篇**（`:3` 仿真声明、`:23` §2 标题、`:34` 合计行，共 3 处），而**实际是 26 篇**。⚠️ **README 自己就矛盾**：`:27`–`:33` 的「篇数」列相加 `4+5+4+4+3+4+2 = 26`，文件区间 `01`–`04`…`25`–`26` 也正好是 **26** 篇——**只有合计行与两处标题写 28**。 |
| **怎么暴露的** | 写简历时要填一个语料规模数字，没有照抄文档，而是去**磁盘数了一遍**：`docs/规则语料/` 下 27 个 `.md` = **26 个编号文件 + 1 个 README**。⇒ 数字对不上，才回头查。 |
| **根因** | 决策 **C-20** 初稿定的是 **8 个主题类 / 篇目 01–28**；后把"航行保障与安全"并入 A 类变成 **7 类**，编号随之改为 **01–26 连续**（`docs/DECISIONS.md:62` 的「勘误」明确记了这次合并）。**类数与编号都改了，唯独"28 篇"这个总数没人改**。 |
| **权威实测（三重独立证据）** | ① **磁盘**：26 个编号文件（01–26）；② **闸门**：`backend/scripts/validate_corpus.py:44` 写死 `EXPECTED_FILES = 26`，实跑 `文件数：26（期望 26）` → `[PASS]`、退出码 **0**；把常量**临时改成 27** 立刻红（`✗ 文件数不符：26 != 27`、退出码 **1**）⇒ **26 是被机器强制的**；③ **README 自身**：篇数列求和 = 26、区间 = 26。⇒ 三票独立指向 26。 |
| **⚠️ 这条真正的代价：陈旧值没被留着，而是被"解释"了三遍** | 28 这个陈旧值出现在 3 份文档里，**每一处都配了一个听起来合理的解释**——而**三个解释互相矛盾，且都不成立**。① `validate_corpus.py:42`：「初版误写为 28——那是**篇目编号最大值**而非文件数」——**篇目编号最大值就是 26**（`01`–`26`），不是 28；该注释与它下面 2 行的 `EXPECTED_FILES = 26` 自相矛盾。② `docs/进度看板.md:2119`：「"28 篇"指**篇目总数口径**，"28"不是最大编号」——与 ① **直接冲突**（一个说 28 是最大编号、一个说不是），且若总数真是 28，README 篇数列就该求和为 28。③ `docs/DECISIONS.md:62`（C-20）：决策列写「**28 篇** / 7 个主题类」，同格「理由」栏的勘误又写「篇目编号相应为 **01–26** 连续（非 01–28）」⇒ **同一格内自相矛盾**。⇒ 三个解释彼此对不上，却**每一处都让读者以为"这件事已经交代过了"**，于是没人再去数一遍。 |
| **最终修法** | ⏸ **本轮未改**。修它要动 **C-20（已确认决策）+ `AGENTS.md` §3 + `DECISIONS.md` 2 处 + `进度看板.md` 3 处 + `工程复盘/README.md:7` + 校验器 docstring 2 处**，共 7 个文件；按 `AGENTS.md` §4.4「已确认决策不得被后续会话推翻」，**已上报用户裁示**。⛔ **没有静默改掉任何一处**。 |
| **可复用的规则** | ①**给陈旧值补一个解释，比留着不管更危险**：沉默至少还会让人去数一遍；一个**听起来合理**的解释会**终止怀疑**——而它若是错的，还顺带误导下一个人。②**同一个陈旧值会长出多个解释**，因为它们各自被独立"合理化"，**没有一处会去读另一处**。③**"改代码"不等于"改口径"**：`EXPECTED_FILES` 改对了，**同一文件第 7、11 行的 docstring 仍写「28 篇 / 文件数 = 28」**——常量与描述它的文字是两处。④**对外数字应取"有闸门保护的那一个"**：26 有 `EXPECTED_FILES` 守，28 什么都没有。 |
| **与本类既有条目的关系** | 三条同族，但**载体不同**：[陈旧清单能通过自己的校验器](陈旧清单能通过自己的校验器.md) 是陈旧**产物**（校验器只查产物内部自洽）；[两张同名表各自更新导致七处状态矛盾](两张同名表各自更新导致七处状态矛盾.md) 是**状态列**（没有任何检查器会读它）；**本条是第三种载体——陈旧数字 + 事后的解释**。三者共同点：**不变量横跨的范围，超出了任何校验器读的范围**。 |
| **⚠️ 未验证** | 我**没有**核对当初 8 类→7 类合并时是否存在 27、28 号文件被**删除**（未查 `git log`）。故严格说只能断定「**当前是 26，且 28 从未被任何机器检查保护过**」，⛔ 不能断定「28 一定从来不存在」。 |
| **可能被追问** | 「你简历写 26 篇，仓库 README 写 28 篇，是不是对不上？」→ 答：**26 是机器强制的**——`validate_corpus.py` 的 `EXPECTED_FILES = 26` 是闸门，我实测把它改成 27 立刻红并退出码 1；README 那处 28 是**未更新的陈旧值**，而且 README **自己的篇数列求和也是 26**。⇒ 对外数字取**有闸门保护的那一个**。 |
