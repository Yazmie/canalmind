# 运河节点港名单：一个隐式的数据契约

> 类别：[数据一致性](README.md) ｜ 返回总索引：[../README.md](../README.md)

| 项 | 内容 |
|---|---|
| **问题** | 语料 `docs/规则语料/01-船舶过闸管理办法.md` 第十五条写「过闸费**仅对经平陆运河的航次**收取」，并列出 5 个"运河节点港"。 |
| **背后的耦合** | 这 5 个港口名单**不是描述性文字**——决策 **C-18** 规定 `voyage.via_canal` 字段的口径就是「起点港或终点港 ∈ `is_canal_node=True` 的集合」（`generate_seed_data.py` 第 116–129 行）。**名单一改，计费口径就变。** |
| **实测核对** | 语料 5 个节点港与数据库 `PORTS` **逐项一致**（连江段与类型也一致）：平塘江口港点 `HZ02` / 陆屋港 `LW01` / 钦州内河港 `QZ01` / 钦州港 `QZ02` / 钦州港保税港区 `QZ03`。 |
| **怎么解决的** | 加了双向机器校验 `check_canal_node_ports()`：语料中每一行的「港口名 / 江段 / 类型 / 是否节点」都反查数据库 `PORTS`，并且**必须覆盖全部节点港**（防漏）。用"注入错误"验证过它会报错（把钦州港错标为"否"→ 报错、退出码 1）。 |
| **业务含义** | **文档里出现的每一个"业务实体名"，都可能是一个隐式的数据契约。** 判断标准很简单：**这个名词会不会被程序用来做判断？** 会 → 它就必须与数据源强一致，不能靠"抄写时小心一点"。 |
| **可能被追问** | "5 个港口你也值得写个校验？"→ 答：重点不是"5 个"，而是**这类耦合会随业务增长而失控**。今天是 5 个港口，明天是 30 个货种、50 条费率。**把契约校验自动化，成本是固定的；靠人复核，成本随规模线性增长。** |
