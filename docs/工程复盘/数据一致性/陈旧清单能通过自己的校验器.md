# 陈旧的清单能通过它自己的校验器（"与语料同版"没人查）

> 类别：[数据一致性](README.md) ｜ 返回总索引：[../README.md](../README.md)

| 项 | 内容 |
|---|---|
| **现象** | `docs/评测报告/chunks-baseline.json`（固定长度切分清单）**正文是旧版语料**：它还写着 `2026-09-16 至 2026-12-31（含）`，而当前语料已改成 `2026-09-16 至 2027-01-01（终止日不含；业务末日为 2026-12-31…）`。⚠️ **它一直通过 `verify_chunks.py`（错误 0 项）**，没人发现。 |
| **怎么暴露的** | 做「Chunk 策略」消融时要先把 L2 的 gold 标注映射到固定长度坐标系，结果 5 条 gold **定位失败**。逐条查分叉点才看到：3 条的差异**正好落在 2026-09-21 那次语料改动的三处正文**上（生效期端点左闭右开、两版费率表衔接条款）。⇒ 不是映射写错了，是**清单与语料不同版**。 |
| **根因** | 那次语料改动后，**结构侧清单重生成过**（541 块、`chunk_id` 集合逐个相同、只有 5 个 chunk 内容变——这条当时是**核对过**的），但**基线侧清单漏了**。而 `verify_chunks.py` 的检查项全是**清单内部**一致性（块数、字段、字符数自洽…）——**"这份清单对应哪一版语料"根本不在它的检查范围里**。 |
| **权威实测** | 重生成后 `385 → 386 块`、`618,542 → 619,833` 字节；**新旧两份都 `verify_chunks.py` PASS、错误 0 项**。⇒ 这就证明：**校验器绿 ≠ 数据可用**，它只证明了"清单自己不矛盾"，没证明"清单与语料同版"。 |
| **代价（差一点就成假失败）** | 若不重生成就去建固定长度索引，会有 3 条 gold **映射不上**，而"映射不上"会被**合理误读成"固定长度切分策略更差"**——**用错误的证据得出方向正确的结论**，这比结论错更危险，因为它不会引起怀疑。 |
| **最终修法** | ①用 `ChunkManifestCli --strategy baseline` **重生成**并替换；②把**重建法**作为映射口径（固定长度块是重叠滑窗、`baselineCharOffset` 步长恒 260 ⇒ 按声明偏移反推底层文本，**重叠区逐字符一致**是真自检，实测 0 冲突）；③写死的自检：**任一 gold 定位不到即非零退出**，⛔ 不出表。 |
| **可复用的规则** | **凡"派生产物"（清单 / 索引 / 标注 / 基线）都要带一个"它对应哪一版输入"的判据**，并且该判据要**由机器比对**，⛔ 不能只查产物内部自洽。本项目已有同族教训：[跨代对比的自证会假失败](../工程方法/验证工具本身也要被验证/跨代对比的自证会假失败.md)（自证等式两端分属不同世代 ⇒ 报出不存在的失败）——**那条是假失败，这条是假成功，根因是同一个：没有"世代"这个字段。** |
| **可能被追问** | "怎么防？"→ 答：**把版本判据写进产物**（如清单里记源语料的 `sha256`），并让校验器**比对**它，而不是只校验内部自洽；本项目 `eval_record` 表已按知识库那样存了 `datasetVersion` / `inputHash` / `gitCommit`，**同一套思路要用到切分清单上**。 |
