# 费率口径跨来源漂移：规则写了、检查没做

> 分类：[数据一致性](README.md) ｜ 返回总索引：[../README.md](../README.md)
> 锚点：`docs/规则语料/06、07、08、09`、`backend/scripts/generate_seed_data.py`（2026-09-22 前的版本）、
> `V5__align_tariff_with_corpus.sql`、`backend/scripts/verify_corpus_db_rates.py`

## 一句话

**语料费率表与数据库 `tariff_rule` 在四个维度上同时不一致，而 README 里"两者必须一致"的
规则写了整整一轮第 1 周却没有任何脚本校验它——于是"没报错"被读成了"没问题"。**

## 漂移的四个维度（实测，2026-09-22）

| 维度 | 语料费率表 | 库内旧值（公式生成） |
|---|---|---|
| 吨位档位 | 过闸费 `0/500/2000/5000` | `0/1000/3000` |
| 费率数值 | 建材 2026 版 **2.55 元/吨** | **1.0200 元/吨** |
| 分档依据 | 引航费/停泊费按**船舶总吨位** | 按**货类**（且 `vessel` 表根本没有总吨位字段） |
| 计费单位 | 港杂费 **元/次**、装卸费 9.00 元/吨 | 港杂费 **元/吨**、装卸费 8.00 元/吨 |

后果不是"数字有点不同"，而是**双通道互相打脸**：
同一个问题「2026 年建材过闸费多少」，检索通道答 2.55 元/吨（读语料），
结构化通道答 1.02 元/吨（读库），而第 3 周的 Execution Accuracy 又要求"用数据库执行结果做 oracle"——
oracle 本身就是错的。

## 为什么没被发现：三层原因叠加

1. **规则写了、检查没做**。`docs/规则语料/README.md` §4 明确要求"费率表取值**必须**与
   `tariff_rule` 逐字一致"，但 `validate_corpus.py` 的 **11 项检查里没有一项校验数值**——
   它检查列头、检查船闸尺度、检查港口名单，就是不检查钱。
   ⇒ 与[钢材归类跨来源冲突](钢材归类跨来源冲突.md)同一个坑：**跨来源不变量必须用跨来源检查守住**，
   写在文档里的"必须"不是检查。
2. **两侧各有自洽的假象**。语料元数据自称"费率取值与仿真业务数据保持一致"（没查证就写下的承诺）；
   库侧 `generate_seed_data.py` 用 `基准 × 货类系数 × 档位折扣 × 1.015^期数` 造费率，
   注释还写着 `BASE_UNIT_PRICE` 是"元/吨"——**看起来每一步都有出处**，
   唯独没有一个数字来自语料。⇒ 见[把合理当解释的风险](../工程方法/把合理当解释的风险.md)。
3. **缺陷藏在"能跑"里**。引航费的单位是 `元/次`，价格却取自"元/吨"的基准，
   于是费率变成 **0.60~1.34 元/次**（真实量级应是几百到几千元/次）——
   数据能生成、约束能通过、查询能返回，**没有任何一处会报错**。

## 处置（决策 C-31 / C-36）

1. **定权威源**：以**语料**为唯一事实来源，库侧改为**由语料派生**
   （新增 `backend/scripts/corpus_tariff.py` 解析语料费率表 → 生成 `tariff_rule` 99 条）。
2. **补结构**：`vessel.gross_tonnage`（总吨位）+ `tariff_rule.tonnage_basis`（吨位口径）
   + 哨兵货类 `不区分`，并把两条口径配对**下沉为 CHECK 约束**——
   让"引航费按货类分档"这种错误**在建表层面就写不出来**。
3. **补检查**：`verify_corpus_db_rates.py` 做**双向逐格比对**（语料重新独立解析一遍，
   库内多出语料没有的规则也算错）+ 全量费率命中复核 + 全量金额自洽复核。
4. **让检查自证**：脚本带 `--selftest`，会故意改坏一条费率并断言检查**确实报错**，
   然后回滚复核。理由是"[检查有效性必须被验证](../工程方法/检查有效性必须被验证.md)"——
   永远绿灯的检查与没有检查等价。

## 可迁移的教训

- **"文档里写了必须"不等于"有检查"**。凡跨来源的口径，问一句：
  *如果它现在不一致，哪个脚本会红？* 答不上来就是没有检查。
- **降级为"未实现清单"而不是沉默略过**。语料里有 6 项条款不可实现
  （如「核定最低计费吨位」全语料无定义、堆存仓储费率无对应数据表），
  本轮**逐条登记原因与锚点**并写进机读产物——沉默略过会让"实现了多少"变成不可核对的宣称。
- **覆盖缺口也要报**。71 个费率档位里有 **18 个没有任何仿真数据触发**
  （船队总吨位上限 3,017 ⇒ 引航费/停泊费最高两档不可达）。
  这不是缺陷，但**出题时必须知道**，否则会写出"数据里根本答不出"的题。

## ⚠️ 与本类既有结论的关系（诚实记录）

本类 README 原先写着一条更粗的启发式：**"能被自动化验证的一方，才是权威源"**，
即冲突时以有 `CHECK` 约束、被测试守护的一方为准，反向修文档。

**本轮选的是反方向**（以语料为准、改库），因此这条启发式需要收窄：

> 权威源应当是**"规则/事实的作者"**，而不是**"有约束的那一方"**。
> 约束只能保证**一致性**（唯一命中、枚举合法、区间不重叠），
> **不能保证正确性**（费率取值对不对）。

在本项目里，语料是规则的文本作者（人手撰写、写给业务方看、并被检索通道整篇消费），
库内 `tariff_rule` 是**派生数据**；派生数据必须从权威源派生，而不是反过来。
只有当冲突双方**都被设计为同一事实的权威载体**（如 `CHECK` 枚举 vs 文档枚举）时，
"有约束的一方优先"才成立。
