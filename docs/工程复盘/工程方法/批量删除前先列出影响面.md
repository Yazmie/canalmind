# 批量删除/移动前，先列出"将要被影响的文件"

> 类别：[工程方法](README.md) ｜ 返回总索引：[../README.md](../README.md)
> 本条的规范性约定同时写在 [../README.md](../README.md) 约定 6（维护本目录的人会看到）。

| 项 | 内容 |
|---|---|
| **问题** | 我在把工程复盘从"单文件"重构成"分类目录"时，用 `Get-ChildItem *.md \| Remove-Item` 清理旧文件——**结果把同一批里刚新建的 `面试速查卡.md` 一起删掉了**（新文件也在顶层、也匹配 `*.md`）。 |
| **根因** | **通配符删除的危险不在"删错文件"，而在于它删除的是"当时恰好匹配的东西"**。而我对"当时匹配了什么"的认知，来自**上一次的目录状态**，不是执行那一刻的真实状态。 |
| **怎么发现的（这才是重点）** | **不是我看出来的**——是**我在同一轮里刚写好的 `check_links.py` 当场报出来的**：`✗ 缺少顶层文件：面试速查卡.md`。**检查在新方法第一次使用时就开始兜底了。** |
| **怎么解决的** | ①恢复被删文件；②把这条写成规范性约定（[../README.md](../README.md) 约定 6）：**批量删除/移动前先打印匹配清单并核对总数**；③把"结构完整性"作为自检的固定一项（分类目录齐全、每类有 `README.md`、无编号式文件名）。 |
| **业务含义** | **生产环境的 `DELETE` 也应当先 `SELECT COUNT(*)` 核对**——同一个道理，只是规模不同。危险的通配操作不止文件：批量 SQL、批量重命名、批量改配置，都是"匹配范围与预期不一致"这一件事的不同形态。 |
| **与另一条的呼应** | 这与[追加型内容不能用替换式编辑](追加型内容不能用替换式编辑.md)是**同一族问题**：都是"操作语义与内容性质不匹配"（append 被当 replace、精确删除被当通配删除），而且**都不会报错**。 |
| **可能被追问** | "怎么系统性避免？"→ 答：**把"影响面确认"变成执行前的一个显式步骤**，并用结构自检在事后兜底。**不依赖"我这次会小心"。** |
