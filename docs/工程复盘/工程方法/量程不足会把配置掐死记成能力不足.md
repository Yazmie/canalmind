# 量程不足会把「被配置掐死」记成「能力不足」

> 类别：[工程方法](README.md) ｜ 返回总索引：[../README.md](../README.md)

| 项 | 内容 |
|---|---|
| **一句话** | `max_tokens` 与 `timeout` 不是「调参」，是「**量程**」。量程不足时调用确实会失败，但**产物只会说「降级了」**——从产物读出来就是「模型能力不足」。 |
| **现象（最要命的一格）** | 混合检索第四路（RRF + LLM 重排）在 **30 条候选**档下「降级」频发；降级在产物里的表现是**保留融合原序**——**看产物与「重排没有效果」完全一样**。产物自证：`backend/target/eval/item5/pilot-rerank.json` 里 `config.rerankTopN = 30`、`degradedQueryCount = 3`，而每题 30 条 `hits` 的 `rerankRank`/`rerankScore` 全为 `null`。 |
| **真因 A（输出额度）** | 该档跑 3 条真实试点查询：**3/3 全部降级**，三题同因——`degradeReason` 文案是「重排模型返回了**空正文**」、`finish_reason` 均为 **`LENGTH`**、**`completion` 恒等于 `maxTokens`=4096**（预算被吃光、正文一个字都没写出来）；提示词规模 **8710 / 9041 / 9556 字符**。<br>→ 结论：**该模型先推理再输出，推理 token 与正文共享同一 `max_tokens` 预算**；候选越多、提示词越长，越容易把预算耗在思考上。故 4096 在**这一档是「必然降级」而不是「偶发」**。 |
| **真因 B（调用超时）** | 同一档单题重排耗时实测 **最小 21.6 s / 均值 29.4 s / 最大 43.5 s**，而当时的 `DEFAULT_TIMEOUT` 是 **30 s**——**正好压在均值上**。<br>→ 后果：大量**本来能成功**的调用被判成「超时降级」，而产物**不会说「是被我的超时线掐死的」**。<br>→ **铁证**：本项目记录到一次**成功**的重排，耗时 **29.875 s**，离 30 s 上限只差 **0.1 秒**。 |
| **处置** | ① 重排侧 `maxTokens` **4096 → 8192**（环境变量 `CANALMIND_RERANK_MAX_TOKENS` 可覆盖）；② `DEFAULT_TIMEOUT` **30 s → 90 s**（环境变量 `CANALMIND_RERANK_TIMEOUT_SECONDS` 可覆盖）。**两处非法值一律抛异常，⛔ 不静默退回默认值**——静默回退会让人拿到一份「额度/超时其实没生效」的产物，而**产物里看不出这一点**。 |
| **同一族的前置证据（本项目已有）** | `degradeReason` 里两种**不同失败档**：**空正文**（`degradeKind=BLANK_COMPLETION`，确定性失败、**不重试**）与**有正文但被截断**（`UNPARSABLE`，**全场唯一可重试档**）——它们的**旁证长得一样**（同一个 `finish_reason=LENGTH`、同一个 4096），于是曾被误读成「**分类不一致**」。→ 判定必须看**档位**（产物现已有 `degradeKind`），⛔ 不是看文案。 |
| **可反驳的检查（已实测成立）** | 若「行为不同只是因为档位不同」成立，则那次 `attempts=3` 的题，其 `previousDegradeReasons` **必须恰有 2 条**——实测**正是 2 条** ✓（同题前两次是「有正文但被截断」，故可重试；题 1/2 是空正文，`attempts=1`）。 |
| **代价与止损（诚实记录）** | 因为「30 s 压在均值上」这件事**在产物里看不出来**，曾有一整批**计划 40 题的真实调用被跑掉后作废**（跑到约 **15 题**即止损叫停，那批调用全部浪费、未产出被引用的产物）；本轮及相邻会话累计付费调用 ≈ **100 次**（其中另一条实现线约 **54 次**）。⛔ **不要写成「没有损失」**——**发现得晚，代价是钱与时间**。 |
| **教训（要能被面试复述）** | ① **`max_tokens` 与 `timeout` 不是「调参」，是「量程」**；量程不足时，失败会被记成「能力不足」，而**产物只会说「降级了」**。<br>② **在评估任何「模型能力」之前，先确认仪器的量程够不够**；量程类失败与能力类失败**必须能在产物里分开**——办法是把 `finish_reason`、token 用量、**失败档位**、生效的 `maxTokens` / `timeout` 都写进产物或 banner。<br>③ **默认值也是结论的一部分**：默认值选错，会让整批数据「**看起来是模型不行**」。 |
| **可能被追问** | 「你怎么知道是量程不够，而不是模型不行？」→ 答：**两条互相独立的证据**——① `completion` **恒等于** `maxTokens`（4096），说明预算被耗尽，而不是模型不肯输出；② 把量程调大后**同一题复测成功**（1 次尝试、30 条候选**全部**拿到重排名次）。两者一致才下结论，⛔ 不靠「我觉得是额度问题」。 |

## 两个量程数字对照（数字都能对到实测）

| 旋钮 | 原值 | 新值 | 依据（实测） |
|---|---|---|---|
| `maxTokens`（重排侧） | 4096 | **8192**（环境变量 `CANALMIND_RERANK_MAX_TOKENS`；非法值**抛异常**） | `rerankTopN=30` 档 **3/3 必然降级**：空正文 + `finish_reason=LENGTH` + **`completion` 恒等于 4096** |
| `DEFAULT_TIMEOUT`（重排侧） | 30 s | **90 s**（环境变量 `CANALMIND_RERANK_TIMEOUT_SECONDS`；非法值**抛异常**） | 30 条候选档单题耗时 **21.6 / 均值 29.4 / 43.5 s** ⇒ **30 s 正好压在均值上**；一次**成功**的调用耗时 **29.875 s**（离 30 s 只差 0.1 s） |

> **90 s 的取值依据**写在 `LlmReranker.DEFAULT_TIMEOUT` 的 Javadoc 里：≈ 实测最大值 **43.5 s** 的 2 倍。
> 该 Javadoc 同时**逐字**写着这条现象的判据：
> 「会把大量**本来能成功**的调用判成超时降级，而产物里的表现与「重排没效果」**完全一样**（都是降级 + 保留融合原序）——这正是最该避免的那种「没跑成看起来像没效果」。」

## 产物里长什么样：一条长文案 ≠ 一个可比较的数字

`pilot-rerank.json` 里题 1 的 `degradeReason`（**逐字**，只此一段就说明白了三件事：模型调通了、预算是被推理吃掉的、正文一个字都没有）：

```text
重排模型返回了空正文（finish_reason=LENGTH，prompt 5250 tokens / completion 4096 tokens，
提示词 8710 字符）：已保留融合原序。⚠️ 最常见的原因是 max_tokens 被「推理 token」吃光——
本模型先思考再输出，预算耗尽时 content 为空而 finish_reason=length，
于是「没输出」与「没调通」在产物里长得一样。…
```

⚠️ **这段文字是修复后才有的**——`finish_reason` 与 token 用量原本**从不进产物**，那时
「**被预算截断**」与「**模型吐了非法 JSON**」在产物里**长得一模一样**。补齐这三样之后，
「量程类失败」才第一次成为**可核对**的失败。

## 量程的生效值必须自己报出来（banner）

CLI 自检的 banner 会打印**生效值**（而不是 `--help` 里的默认值）——这是「默认值也是结论的一部分」的落地：

```text
重排额度    ：maxTokens=8192（CANALMIND_RERANK_MAX_TOKENS 可覆盖，默认 8192；
             推理 token 与正文共享这个预算，故提示词越长 / 候选越多越容易写不出来）
重排超时    ：timeout=<生效秒数>s（CANALMIND_RERANK_TIMEOUT_SECONDS 可覆盖，默认 90s；
             超时即降级，且这一档不重试。…）
```

## 一条迟到的实测（引用时**必须连局限一起写**）

另一条实现线在**被叫停之前**曾跑过一次 40 题重排整批（`maxTokens=16384`、超时 90 s），
结果为 **0/40 降级**——这直接印证了「量程够 → 失败消失」。

⛔ **但它的产物没有落盘**：写入时撞上「另一会话并发重编译 `target/classes`」，
JVM 混着加载了新 `RetrievalResultJson.class` 与旧 `RerankOutcome.class`，
报 `NoSuchMethodError: RerankOutcome.attempts()`，整批输出丢失，**只剩逐题日志**。
⇒ **引用时只能说「另有一次 40 题整批的逐题日志显示 0/40 降级」，⛔ 不得当成可核验产物。**
（出处：`backend/target/eval/v2_datapack.md` §8.6.1 那条以「一条迟到的实测」开头的记录，
该文件为生成产物、**不入 git**。）

## 跑任何批量评测前的检查清单

1. **先看 banner 里 `maxTokens` / `timeout` 的生效值**（⛔ 不是看 `--help` 里的默认值、也不是看你写进 `.env` 的值）——本项目的 banner 逐字打印它们，就是为了回答「我设的 16384 到底生效了没有」。
2. **先跑 1~3 题试点看降级率**，再决定要不要开整批。⚠️ **试点必须与整批同档**：本项目「1/4 偶发」取自 `rerankTopN=10` 档，「3/3 必然降级」取自 `rerankTopN=30` 档——**两档不可混说**（候选越多、提示词越长，量程越不够）。
3. **把量程类失败与能力类失败在产物里分开**：`finish_reason`、`prompt` / `completion` tokens、**失败档位**（`degradeKind`）、生效的 `maxTokens` / `timeout`，一个都不能只留在日志里。
4. **用「可反驳的检查」自查分类**：重试过的题（`attempts > 1`）必须满足 `len(previousDegradeReasons) == attempts - 1`；本项目 `attempts=3` 的题实测恰有 2 条 ✓。
5. **量程值 / 超时值是实验条件，必须随产物可追溯**——它们决定「降级率」这个观测量，⛔ 不要埋在常量里靠人记得。
6. **开跑前先算账**：一次整批真调用 × 单价 × 可能的重跑次数；**量程没定就不要开跑**（本项目为此付掉 ≈100 次调用，其中一整批跑到约 15 题即作废）。
