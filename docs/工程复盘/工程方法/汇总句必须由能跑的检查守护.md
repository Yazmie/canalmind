# 汇总句必须由能跑的检查守护

> **一句话**：我写的「**`eval_record` 六层全部在库**」**当时只有 5 层**（L4 一条都没有），
> 而这句话还被**放大进了三份文档**；更糟的是——**同一个错，我在同一节里犯了两次**。

## 1. 事实（两次，同一节，同一句话型）

都在《评测报告》§2「分层通过率（数据取自库内 `eval_record`）」：

| 次 | 写的断言 | 当时的实测事实 |
|---|---|---|
| ①（C-52） | 标题「取自库内 `eval_record`」 | 库里**只有 L1/L2 共 80 条**，L3/L5/L6 其实读的是 `layer-L{3,5,6}-judged-v1.json` |
| ②（C-53b 更正） | 「**六层全部在库**」（run `…-all6-artifacts-v2`，135 条） | 该 run **只有 5 层**：L1 40 / L2 40 / L3 20 / L5 20 / L6 15 ——**L4 一条都没有** |

⚠️ **第 ② 次的放大面比第 ① 次大得多**：「六层全部在库」被抄进了 `DECISIONS.md` **三处**，
其中包括 **「第 4 周目标验收通过」** 那一条——**一句没核对的话，进了验收依据**。

## 2. 为什么两次都没被发现

- **它是一句"汇总"**：读起来像**已经核实过的结论**，而不像"待验证的猜测"。
  于是无论是我还是评审，都**不会去查它**——没人会去查一句"看起来就是结论"的话。
- **没有任何东西会自动验证它**：数字有出处（报告），报告有出处（产物），
  但**"有几层"这句话本身，当时没有任何一条命令会因为它错了而变红**。
- **它的"正确版本"每次都要重新算**：L4 的分数一直在（`layer-L4-inheritance-v1.json`），
  但**没落库** ⇒ "在不在库里"与"出没出分"是**两件不同的事**，而我按后者写了前者。
- **同一个坑的第一次更正，反而制造了第二次的自信**：①被更正后我补了 Judge 三层，
  于是"六层"这个说法**感觉上已经被兑现了**——但补的是 **3 层**，缺的是**第 4 层（L4）**。

## 3. 处置（⛔ 不静默改掉）

1. **补上能力**：L4 落库通道（`ArtifactIngest.readL4` + `HarnessCli --l4`）⇒ 新 run
   **`w4-2026-09-22-all6-artifacts-v3` = 160 条 / 6 层**（⛔ 不动 v2，v2 保持 135 条 / 5 层）。
2. **就地标注**每一处被污染的断言（报告 §2、看板 §0/§3/§4、`badcase记录.md`、`DECISIONS.md` 三处），
   写清"**当时称六层、实测 5 层**"，并新增决策条 **C-53b**。
3. **把规则写进规则文件**：`AGENTS.md` §6 第 6 条。

## 4. 可复用的两条规则

1. **凡汇总句，必须能用一条能跑的命令当场证伪。**
   本项目标准手法：`HarnessCli --report --run-id <id>` —— 一条命令就能证伪任何
   "有几层 / 多少条 / 覆盖什么"的说法。**证伪成本必须是"一条命令"这个量级**，
   否则它迟早会退化成"没人查过的话"。
2. **并列数值必须带限定域。**
   `eval_record` 里**同时存在多轮 run**（实测 3 个：v1 80 / v2 135 / v3 160 ＝ **375 条**），
   所以「135 条」是**不完整指称**——必须写「（`w4-2026-09-22-all6-artifacts-v2` run 下）135 条」。
   ⇒ 有多个并列实例的数字，**引用时必须带 `run_id` / 版本 / 分片等限定语**。
