# 跨线程埋点父指针丢失：注册了传播器 ≠ 自动生效

> **一句话**：Span 的父指针靠 **`ThreadLocal`**，跨线程默认**丢**；而**只注册 `ThreadLocalAccessor`
> 并不会自动传播**——必须**显式包装执行器**（`ContextExecutorService.wrap`），
> ⛔ 两者缺一不可，且缺了**不报错**、Span 照旧产生，只是变成一棵平树。

## 1. 实测（2026-09-22，4 个场景）

| 场景 | 子 Span 的父指针 |
|---|---|
| ① 裸线程池（`Executors.newSingleThreadExecutor`） | ⛔ **`null`** |
| ② 注册 accessor **且** `ContextExecutorService.wrap(...)` | ✅ `ai.agent.run` |
| ③ **只**注册 accessor、**不**包装线程池 | ⛔ **`null`** ← 关键反例 |
| ④ `ForkJoinPool.commonPool()`（SSE 的实际形态） | ⛔ **`null`** |

⇒ 修法只有一个：**注册 + 包装**。

## 2. 真正值得记住的是场景 ③（"半配置"陷阱）

`ContextRegistry.registerThreadLocalAccessor(accessor)` 看起来就像"打开了传播开关"，
**实测不是**：它只是"**让快照知道怎么捕获/恢复这个值**"，
而**谁来捕获、谁来恢复**要靠**执行器被包装**那一步。

⛔ 半配置状态的危险在于它**完全合法**：编译通过、启动正常、Span 一条不少、名字全对、
**没有任何异常**，只是**边全断了**。于是排查的人会去怀疑"埋点写错了"或"后端丢了"，
而**不会怀疑"我少包了一层执行器"**。

## 3. 为什么场景 ④ 值得单独列

`CompletableFuture` 的异步方法默认跑在 **`ForkJoinPool.commonPool()`** 上——
这正是 Spring AI 流式调用会切过去的地方，也是知识库《AI 可观测性与 Trace…》第 324 行
记录的官方限制的成因（模型 Span 与 HTTP Span 之间断链）；第 306 行已点明
"上下文默认基于 `ThreadLocal`，提交给普通线程池后若没有自动插桩或显式包装，子线程看不到父上下文"。

⚠️ **本测试只证明了这个机制**（commonPool 未被包装 ⇒ 丢父），
⛔ **不等于"已复现 Spring AI 的行为"**——那是知识库的记录，不是本项目的实测。

## 4. 怎么防（已落到代码）

- **测试固化**：`AiObservationThreadPropagationTest` 把①③④的 **`null` 本身**断言下来
  （`AiObservabilityTest` 固化的则是同线程的"只 `start()` 不建链"）。
  ⇒ 将来库若改语义，这些断言会**变红**，提醒复核本文与 README 已知限制第 9 条。
- ⚠️ **全局单例要还回去**：`ObservationThreadLocalAccessor.getInstance()` 是**单例**，
  注册进 `ContextRegistry.getInstance()` 会影响**整个 JVM**；测试用完必须
  `removeThreadLocalAccessor(ObservationThreadLocalAccessor.KEY)`，否则会**污染别的测试**
  （别的测试若恰好包装了执行器，就会意外拿到本测试设过的 registry ⇒ 假绿）。
- **业务侧纪律**：本项目复合通道按 **C-37 串行**、编排里**没有**自建线程池，
  故当前**不受影响**；但**一旦并行化**（含 SSE 路径），必须包装执行器，⛔ 不能只注册 accessor。
