# 机制与证据分级：是「别的编译路径写了带伤类 + Maven 跳过它」

> 返回：[编译错误被静默放过](README.md) ｜ [../README.md](../README.md)

## 结论（能解释全部观测的最简机制）

1. **Maven 在这台机器上用的是 javac**：`pom.xml` 的 `maven-compiler-plugin` **没有 `compilerId`**，构建日志也逐行写着 `Compiling 110 source files with javac`。
2. 但 `target/classes` 里那份 `ToolArgumentExtractor.class` **不是 javac 产的**——它一被调用就抛 `Unresolved compilation problems`，那是 **Eclipse 编译器（ecj）错误恢复**的签名行为（同样的源码交给 javac，只会让构建直接失败）。
3. Maven 的增量检查按**时间戳**判断"该文件是最新的"，于是**跳过它**。⇒ **构建成功，而类里带着炸弹。**

## 证据分级（⛔ 不把推断写成实测）

| 环节 | 等级 | 依据 |
|---|---|---|
| Maven 用 javac、且未配 `compilerId` | **实测** | `pom.xml` + 构建日志 |
| 那份 `.class` 是**带伤**的（不是干净的旧类） | **实测** | 运行时抛 `Unresolved compilation problems`，堆栈指到 `extract(ToolArgumentExtractor.java:99)` |
| 该文件**被 Maven 跳过**、没被 javac 编过 | **实测（反证）** | 若 javac 编过它，2 处 `effectively final` 错误会让构建 `BUILD FAILURE`；而那次构建**成功** |
| 带伤类**来自 Maven 之外**的编译路径 | **推断（强）** | 上两行合起来：Maven 用 javac、javac 会失败、而类是 ecj 签名 ⇒ 不是 Maven 产的 |
| 具体是**哪一个工具 / IDE** | ⛔ **无直接证据** | 没看到那条编译路径的日志，也没确认过它的编译器设置 |

⇒ ⛔ **不要**把"某个 IDE 用 Eclipse 编译器自动构建"当成已证实的事。
本机能确证的止于"**Maven 之外存在一条编译路径，往 `target/classes` 写了类**"。

⚠️ 同时更正我上一版的一个**错误推理**：我用"两个 Maven 仓库里都没有 `ecj`"来排除 ECJ 行为——
**这不成立**：**IDE 自带编译器，不走 Maven 仓库**。否定性证据的适用范围比结论需要的窄时，它什么都证明不了。

## 为什么值得单独记：它决定了防御该怎么写

- 若机制是"**构建把编译错误吞了**"，那该去查编译插件配置——而**实测那边没问题**；
- 真实机制是"**有一条我控制不到的编译路径在往 `target/classes` 写类**"，
  所以唯一可靠的防御是**跑之前先删 `target/classes` 与 `target/test-classes`**，
  外加一次**独立的全树 `javac`**——这两条都**绕开"谁写的、什么时候写的"**这个问题。
