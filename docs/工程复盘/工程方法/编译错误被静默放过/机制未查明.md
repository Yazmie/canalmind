# 机制未查明：出错文本像 ecj，但本机找不到 ecj

> 返回：[编译错误被静默放过](README.md) ｜ [../README.md](../README.md)

`Unresolved compilation problems` 是 **Eclipse 编译器（ecj）** 的特征行为——
它不中止构建，而是把出错方法体替换成"运行时抛 `java.lang.Error`"的桩，
从而让构建继续、让产物带上炸弹。**但本机排查没有找到 ecj**：

| 排查项 | 实测结果 |
|---|---|
| `backend/pom.xml` 的 `maven-compiler-plugin` 配置 | **无 `compilerId`**（只配了 `<parameters>true</parameters>`），默认为 javac |
| `backend/.m2repo` 里的 `plexus-compiler-eclipse` / `org.eclipse.jdt:ecj` | **不存在** |
| 全局仓库 `D:\MavenRepo\maven-3.9.12` 同上 | **不存在** |
| `D:\Project_AI\.proto\settings.xml` | 只有 mirror id（`huaweicloud`），无 `compilerId`/属性 |
| `backend/.mvn/maven.config`、`jvm.config` | **不存在** |

## 能确定什么 / 不能确定什么

- ✅ **能确定（实测行为）**：同一份有编译错误的源码，`javac` **立刻失败**，
  而走构建**不失败**，产物**一被调用就抛 `java.lang.Error`**。
  ⇒ **防御措施不依赖机制**，照主篇第 3 节做即可。
- ❌ **不能确定**：这颗带伤字节码**是谁生成的**。

## 一个尚未排除的方向（⛔ 无证据，故不写成结论）

`target/classes` 同时也是 **IntelliJ 的默认输出目录**。若 IDE 端以 Eclipse 编译器
做过自动构建，就能解释这些字节码的来源——但本轮**没有任何证据**指向它
（没看到 IDE 构建日志、也没确认 IDE 的编译器设置）。

⇒ 记在这里的价值是：**下一个人若再遇到，知道该往哪里看**，而不是重新猜一遍。
