# 我的两个错误猜想（留痕）

> 返回：[编译错误被静默放过](README.md) ｜ [../README.md](../README.md)

查到"构建不失败、产物运行时抛 `Error`"之后，我连着下了两个**错**的判断。
按本目录的约定（发现自己的错误结论必须留痕，不得静默改掉），记在这里。

## 猜想一：这是 Maven **增量编译跳过**了该文件

**我的推理**：`target/classes/…/ToolArgumentExtractor.class` 的时间戳（10:30:41）
**晚于**那份编译不过的 `.java`（10:30:40）。按 Maven 编译器插件的"存量检查"，
`.class` 比 `.java` 新 ⇒ 该文件被跳过 ⇒ **测试跑的是旧字节码**。

**为什么错**：我用 `javap` 看了那份 `.class`——它**有 `attemptOnce` 方法，
却没有 `lambda$extract`**。而当前源码是 `observe(() -> attemptOnce(…))`，
正常编译必然生成 `lambda$extract`。
⇒ 这份字节码是**从出错源码"带伤生成"**的，**不是旧的**（旧版本里 `attemptOnce`
是被**直接调用**的，所以有 `attemptOnce` 而无 lambda 恰好也吻合——这一点我一开始没分清）。

**教训**：时间戳只能提示"谁新谁旧"，**要判断字节码对应哪版源码，得看字节码本身**
（方法/合成 lambda 的有无）。⚠️ 顺带一条：这个错误判断**说出口时很有说服力**——
它自洽、且能解释现象，差一点就成了写进复盘和汇报的结论。
⇒ 与 [../结论随测量方式变化时先怀疑测量方式.md](../结论随测量方式变化时先怀疑测量方式.md) 同源。

## 猜想二：同事注释里那句"实测教训"不可信

**我的推理**：他在代码注释里写"这条编译错误在本机曾被静默放过（主源码报 0 错、
运行时才以 Unresolved compilation problems 抛 Error）"。我据此去查
`pom.xml` 有没有 `compilerId`、两个本地仓库有没有 `ecj`——**都没有**。
于是我在给用户的汇报里写了"这条注释的『实测』不可信"，并准备让他改掉。

**为什么错**：随后我在 `target/surefire-reports/` 里读到了**报告原文**，
`java.lang.Error: Unresolved compilation problems` 一字不差。
**他的实测是对的，我的怀疑是错的**——而且我抱着"找不到 ecj"这个**否定性证据**
去推翻一条**别人已经拿到的肯定性证据**，方向正好是反的。

**教训**：这是 [../知识库无覆盖的错误结论.md](../知识库无覆盖的错误结论.md)
的同一条：**"我没找到"≠"它不存在"**。
⚠️ 更该记住的是它的**社交后果**：若我按当时判断去要求同事删掉那条注释，
就把**唯一一条真实证据**抹掉了，而真正的机制反而更查不出来。
⇒ **否定别人的实测之前，先去找他说的那份证据**（本例中它就躺在 `target/` 里）。
