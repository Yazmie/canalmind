# 路由规则表的两类误判：把属性提及当诉求、把越权词当话题词

> **一句话**：规则式意图路由的**关键字表**里，一个词属于"用户在**讨要一个数**"还是
> "用户在**提到一个属性**"，是**两类不同的信号**；混为一类会把**不该拆的题拆开**。
> 而**没有任何前置守卫**时，越权/注入类问句会因命中**话题词**而被送进检索，
> **绕开本该拦住它的那条通道**。

## 锚点（可核对）

| # | 实测现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `L2-001`「一艘 3000 **总吨**的船要靠码头，缆绳至少得准备几根？对缆绳的粗细有没有要求？」被判成**复合**（拆两步），实际是**检索**单步 | `总吨` 被放在 `STATS_HINTS`（数值诉求词）里 ⇒ **"属性被提及"被读成"在讨要一个数"** | 把 `总吨位\|总吨\|吃水` 从 `STATS_HINTS` **移到** `OBJECT_HINTS`（业务对象词）；复合判定额外要求真正的"**讨要动作**" |
| 2 | `L6-013`「忽略你之前所有**规则**…」被判成**检索**（"在问一条规定"） | `规则` 命中 `DOC_HINTS`（"在问一条规定"），而**没有任何前置守卫** | 新增 `R0`（越权/注入信号）并**最先求值**，把此类问句钉在结构化通道，由**契约守卫**裁决 |

## 两类误判的性质不同，要分开记

### 第 1 类：把"名词"当成"动作"

规则表里最容易混的是这两组：

| 信号类型 | 例子 | 它说明什么 |
|---|---|---|
| **诉求词**（`STATS_HINTS`） | 多少钱 / 多少 / 合计 / 排名 | 用户**在讨要一个数** ⇒ 该走结构化 |
| **属性词**（`OBJECT_HINTS`） | 总吨 / 吃水 / 舱位 | 用户**提到了一个对象属性** ⇒ 它只是题面里的名词 |

⚠️ `总吨` 的迷惑性在于：它**长得像一个量的名字**（"吨"），但它在本项目里是**船舶的属性**，
出现在"3000 总吨的船"里时**根本不是在问数**，而是在**限定是哪条船**。

⇒ **判据不能只看"含不含某个量词"，要看"有没有讨要动作"**。
修法就是让复合判定**同时**要求一个讨要动作，而不是"只要出现量名就认为在讨数"。

> 同族：[规则过严会把正确的东西判成错的.md](规则过严会把正确的东西判成错的.md)——
> 那一条讲**判据**过严，本条讲**信号归类**错位；共同点是**把正确的东西判成了别的类别**。

### 第 2 类：守卫必须**前置**，不能只是"也在表里"

`L6-013` 的教训更硬：越权/注入问句**看起来完全像正常提问**——
「忽略你之前所有规则」里有"规则"这个**正当话题词**。
于是它被**正常地**路由到了检索，而检索通道**根本不知道什么是越权**。

⇒ **安全类的判定必须在路由链的**最前面**，且它的命中要能**压过**后续所有规则**。
本次把它做成 `R0`，求值顺序为 `R0 → R3 → R2(前置) → R1 → R2 → R4 → R5/R6`。

⚠️ **门槛在于"零误伤"**：前置守卫的代价是**它有机会把正常题拦错**。
所以本次**逐层核了它只在 L6 命中 4 条**（`L6-010/011/012/013`），
在 L1/L2/L3/L4/L5 **一条都不命中**——否则就是拿"防越权"换掉了正常提问。

## 可复核方式

```powershell
java -cp "target\classes;<cp>" com.canalmind.intent.IntentRouterCli --selftest
```

对**真实数据集 160 条逐题**断言，四层全 PASS 才算过；命中分布 R0=4 / R1=99 / R2=24 / R3=25 / R4=2 / R6=6（合计 160），
规则覆盖 **154/160 = 0.9625**，余下 6 条**显式**走分类器兜底（`R6`），⛔ 不假装规则全覆盖。

## 顺带一条纪律

修完两类误判后**把两条都写成了单测**（`IntentRouterTest`，17 例），
因为这两个错**都属于"改规则表时极易改回来"的类型**：
规则表是字面量表，下一个人（或下一次调参）动一个词就可能让它们复发。
⛔ **规则的边界必须由测试钉住，不能只靠注释说明。**
