# 结论随测量方式变化时，先怀疑测量方式

> 类别：[工程方法](README.md) ｜ 返回总索引：[../README.md](../README.md)

| 项 | 内容 |
|---|---|
| **问题** | 要回答"PostgreSQL 从多少行开始会自发使用 HNSW 向量索引"。**同一个问题，我连续得出三个互相矛盾的结论**——而每次都以为已经测得够扎实了。 |
| **三次错法** | ①**漏 `ANALYZE`**：`rag_chunk` 入库后从未统计，`pg_class` 里 `reltuples=-1, relpages=0`，我拿着"规划器在没有统计信息下做的决定"去解释小表行为；<br>②**用 `UPDATE pg_class` 伪造行数扫门槛**：我改 `reltuples`/`relpages` 来"模拟"不同规模，得出"**5 万行也不选索引**"。但 **HNSW 的估算代价本身随表大小增长**，把表改大等于**同时把索引的代价也推高**，这条伪造出的代价曲线**没有意义**，结论与真实数据上实测的**正好相反**；<br>③**在 PL/pgSQL 里 `EXPLAIN … INTO 变量` 检测计划**：只捕获到计划**首行**（`Limit`），永远匹配不到索引名，于是**每一档都误报 `SeqScan`**。 |
| **转机** | 放弃"聪明"的批量写法，改做两件事：**逐档建真表**（`CREATE TABLE` + 建索引 + `ANALYZE`）与**用 `EXPLAIN (FORMAT JSON)` 解析整个计划**。结论立刻稳定，且与合成表、真实表**两处一致**：**541 行 → Seq Scan；≥1000 行 → HNSW Index Scan**。 |
| **真正的教训** | ⚠️ **当"结论随测量方式变化"时，第一嫌疑是测量方式，而不是被测对象。**<br>三次错法的**共同点不是"我不懂 PostgreSQL"，而是"我在改测量手段而不在改被测对象"**——每次结论反常时，我都在换一个更巧的测法，而没有先问"这个测法本身成立吗"。<br>具体三类**新的失手模式**（与此前那篇讲探针的[验证工具本身也要被验证](验证工具本身也要被验证.md) 不同，这次错在**环境准备**与**结果解析**）：<br>· **环境准备不全**（缺 `ANALYZE`）→ 测出的行为是环境的，不是数据的；<br>· **用代理指标替换真实条件**（伪造 `reltuples` 代替真造数据）→ 代理指标与被测对象的**代价模型耦合**，代理失效；<br>· **结果解析截断**（只拿到计划首行）→ 判据恒假，**每一档都误报**，且方向一致，看起来像"稳定的结论"。 |
| **工程含义（这才是重点）** | 这三类都会**静默产出看起来正常的结论**。若我没有交叉验证（真实表 vs 合成表、JSON vs 文本、`EXPLAIN` vs 实际耗时），就会把"5 万行也不走索引"写进文档——**那是一条会误导后续规模决策的错误结论**。<br>故规定：**凡是"规划器/优化器为什么不选 X"这类问题，必须同时给出①真实数据上的计划、②实际耗时、③至少一种交叉验证**；只有计划文本不算证据。 |
| **顺带修掉的真实缺陷** | 这次排查暴露出**入库流程缺 `ANALYZE`**——批量写入后未统计，等于让优化器盲选计划。**"表里有数据"≠"规划器知道表里有数据"**，且**不报错**。已据此要求入库后显式 `ANALYZE`。 |
| **可能被追问** | "你怎么确认最后那版结论是对的？"→ 答：**两种独立方式互相印证**（真实的 541 行业务表 + 独立合成的 541/1000/…/50000 行表，逐档一致），并用**实际耗时**佐证规划器选择的合理性（541 行上 Seq Scan 3.43 ms vs 强制索引 1.39 ms，都是毫秒级）。 |
