# 追加型内容不能用替换式编辑（变更日志：删过两次、又被黏成一行一次）

> 类别：[工程方法](README.md) ｜ 返回总索引：[../README.md](../README.md)

| 项 | 内容 |
|---|---|
| **问题** | 我向 `docs/DECISIONS.md` 追加变更日志时，用了"替换某个已有条目"的编辑方式，结果**把那条已有记录整条覆盖删掉了**（第一次删掉"校验脚本自身缺陷"记录，第二次删掉"运河节点港校验"记录）。 |
| **为什么危险** | 变更日志的价值在于**不可篡改的历史**。被静默覆盖的记录，是**决策审计链的断裂**——而且它**不会报错**，只有主动去数条目时才会发现。 |
| **怎么解决的** | 改用"**以被替换条目为锚点、在其前插入**"的方式追加；两次删除都恢复，并核对条目总数确认无重复无遗漏。 |
| **业务含义** | **不同性质的内容需要不同的编辑方式**：追加型（日志、流水、审计）应当用 append 语义，覆盖型才用 replace 语义。把 append 当 replace 用，是**静默数据丢失**。 |
| **可能被追问** | "这在实际项目里对应什么？"→ 答：对应**审计日志 / 事件流的写入设计**——追加型数据必须保证"只增不改"，任何替换式更新都应当是**被禁止的**（在数据库层面不给 `UPDATE`/`DELETE` 权限，而不是"约定小心操作"）。 |
| **⚠️ 我犯两次的说明** | 第一次发生后我记录了教训，**但第二次仍然复发了**——因为当时我是在"写一条新记录"的心智下操作，没有把它当成 append。**说明：只记住原则不够，要改变操作方式**（现在固定用"以旧条目为锚点插入"）。 |

## 第三种失手形态（同一张表，又咬了一次）：`old_string` 只给"行首" → **两行黏成一行**

| 项 | 内容 |
|---|---|
| **现象** | 我往 `docs/DECISIONS.md` 变更日志表**追加一行**时，`old_string` 只写了目标行的**行首**（到"…**✅ 三项 A 类决策确认**"为止的十几字，**没覆盖到该行末尾**）。替换后，**新行与旧行的正文被黏进同一行**。 |
| **代价** | 那一行长度变成 **1004 字符**（当时实测，含两行的全部正文）。⚠️ 表格**仍能正常渲染**，肉眼几乎看不出异常——**一行的语义却已经被破坏**，这正是这类错误难发现的原因。 |
| **怎么修的** | ⛔ **不手工重打内容**（手打等于把刚犯的错再犯一次），而是写一个**一次性脚本按分隔标记拆分**：找到 `\| 用户逐项确认：**D2 → C-26**` 这个**全表仅出现一次**的分隔点，左半补上分隔符作为一行、把被替换掉的行首补回去 + 右半作为另一行，并**断言拆分后两行各自以 `\| 2026-09-21 \|` 开头**。随后发现拆出的行**少了分隔符后的一个空格**（表格仍能渲染，但与全表格式不一致），又单独修了一次。 |
| **现状（可核对）** | `docs/DECISIONS.md` 变更日志里现为**两条独立成行的记录**——**均以 `\| 2026-09-21 \|` 开头**，分别是**以「**✅ 三项 A 类决策确认（D2 / D4 / 执行顺序）**」开头的那一行**与**以「**✅ 第四项 A 类决策确认（D13 → C-28）**」开头的那一行**。⚠️ **锚点认引文，不认行号**：本条原先写「第 **553–554 行**」，而`DECISIONS.md` 是**持续追加**的变更日志——实测那两行现在已是 HNSW 的两条记录，**被引的两条已不在那个位置**（现行定位方式见上：认引文，不认行号）。**行号锚点失效时不报错，读者只会点到一段无关的文字。** |
| **教训** | 在**结构化文本（表格 / 列表）里插入**时，`old_string` 必须覆盖**到能唯一定位整行**的程度（一直给到行尾的分隔符）。只给行首，等于把"替换整行"偷偷降级成"**替换行首片段**"，新内容于是被插进了那一行的**中间**。三种失手形态（整条覆盖删除 → 黏成一行 → 格式少一个空格）的共同点都是：**锚点不够大**。 |
| **残余风险（如实记）** | 那个一次性拆分脚本**没有留档**（跑完即弃），所以"当时是 1004 字符"**现已无法复现**，可复现的只有修复后的终态（**变更日志里那两条独立成行的记录**，锚点见上格）。**下次同类修复应当把脚本留下来**，否则复盘只能靠叙述——而"靠叙述"正是本目录最反对的东西（见 [../README.md](../README.md) 全局约定 4）。 |
