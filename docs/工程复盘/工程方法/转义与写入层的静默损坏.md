# 转义与写入层的静默损坏（反斜杠数量必须实测，不能数）

> 类别：[工程方法](README.md) ｜ 返回总索引：[../README.md](../README.md)

| 项 | 内容 |
|---|---|
| **现象** | 切分器对**同一篇文档**：LF 版本切出 4 块（含 1 个表格块），CRLF 版本只切出 3 块且表格**整块消失**。全程**没有任何报错**。 |
| **根因** | 三个独立的转义错误叠在一起，且**每一个都静默失败**：① `replace` 的两个参数被写成**字面量**（反斜杠+r、反斜杠+n 各算两字符），于是它只在文本里找那串字符，**永远匹配不到真实 CRLF**，换行归一化事实上从未生效；② `split` 同理，**一行都切不开**，整篇文档变成 1 行；③ `String.join` 把**字面反斜杠+n**写进了 chunk 正文。 |
| **权威实测** | 写 `EscCompare.java` 做对照：同一个换行，源码里写"一个反斜杠"时运行时长度 **2**、**能**匹配真实 CRLF；写"两个反斜杠"时长度 **4**、**匹配不到**。结论与直觉相反——**必须靠跑，不能靠数**。 |
| **为什么难查** | 三个失败都不抛异常：`replace` 没匹配上就原样返回、`split` 切不开就返回单元素数组、表格解析拿到带 CR 的行判定"这不是表格"后就把表格当正文。**整条链路从头到尾都是"合法但错"。** |
| **最终修法** | **彻底不用字符串转义**：用 `String.valueOf((char) 13)` / `String.valueOf((char) 10)` 得到真实字符，再 `replace(cr + lf, lf).replace(cr, lf)`。理由：转义的反斜杠数量会被写入层折叠，而 `(char) 13` **任何工具都折不坏**，读者也不必数反斜杠。测试夹具同理，统一用 `static final String NL = String.valueOf((char) 10)`。 |
| **顺序也是语义** | 归一化必须**先收 CRLF、再处理落单 CR**。实测反过来（先 CR→LF）：**长度不变、LF 数翻倍**，每处换行多出一空行——同样不报错。 |
| **等价做法** | `normalizeText` 另有三个真实缺陷被同一次排查顺带修掉：CRLF 从未被归一化、`findBodyStartLine(rawText)` 拿到未归一化文本（同一文档 LF 返回 15、CRLF 返回 **29**）、`CorpusDocument` 构造器未把归一化钉在数据边界上。现在归一化放在 record 的紧凑构造器里，调用方拿不到未归一化的 `rawText`。 |
| **业务含义** | 这是**数据管道类系统最典型的静默退化**：输入格式变一点点（编辑器存成 CRLF、工具链带 BOM），输出就少一块、错一行，**而监控、日志、单测可能全绿**。所以"同一逻辑输入应产生同一输出"必须写成**断言**，而不是靠人工比对。 |
| **可能被追问** | "怎么保证以后不再犯？"→ 答：①用计算字符替代转义，从源头消除"数量会被折叠"这个变量；②把不变量钉在**数据边界**（record 构造器）而不是每个使用点；③单测里显式加 CRLF/BOM 变体的**等值断言**（该断言正是最后抓出表格消失的那条）。 |
