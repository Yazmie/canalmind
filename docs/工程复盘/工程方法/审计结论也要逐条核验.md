# 审计结论也要逐条核验：23 条待修订里，审计自己错了至少 3 处

> 类别：[工程方法](README.md) ｜ 返回总索引：[../README.md](../README.md)
>
> **一句话**：一次只读对抗式审计给出「**23 条待修订**」，我逐条核验后发现**审计自身至少 3 处问题**——
> 若整批照搬，就会把「**审计的错**」当成「**我的错**」改进数据集里，而且**改完不会有任何报错**。

| 项 | 内容 |
|---|---|
| **现象** | 数据集合成后，我安排了一次**只读对抗式复核**（不告知结论、目标是「证伪标注」），覆盖 40/40 题与全部 gold 全文 + 同条兄弟块 + 全库关键词/最长公共子串（40×541 = 21,640 对）扫描。它的结论是 **17 条可直接用、23 条需修订**（P0 3 / P1 15 / P2 5），并逐条给出了「候选等价块」。 |
| **我当时的判断（危险的那一步）** | 审计是**独立第二双眼睛**，而且它给的证据看起来具体（块 id、重合字数）——**我当时打算按它的清单整批采纳**。 |
| **核验方法与锚点** | 不看它的摘要，**自己把 40 题 gold 与候选块全文并排转储**（`backend/target/eval/p1_evidence.txt`，由 `p1_evidence_dump.py` 生成），再逐条**直接查库、自己算**（重合长度自己重算、数字写法自己 SQL 全库数）。审计产物留在 `backend/target/audit/`（`review_report.txt` / `gold_review.txt` / `extra.txt` / `lcs_report.txt` / `keyword_hits.txt` 等）。 |
| **核验发现：审计问题 ①（归类错，且错在方向）** | 审计把 `L2-008` 归为「**gold 缺失等价块**」（暗示 gold 有问题）。**实测是 gold 正确且含答案**：gold（02-第四条 TABLE）写「不迟于预计到达船闸时间前 **48 小时**」，它举出的候选块（11-第四条 `3aca6c885fec32e5`）写「**前四十八小时**」——**同一时限、两种写法**。真因是**中文/阿拉伯数字写法不统一**（对 BM25 是**完全不同的 token**：实测 `十个工作日` **全库 0 命中**、`10 个工作日` **4 命中**，见 `backend/target/audit/extra.txt` 该两项的 `命中=` 计数）。**所以这一条不该按「改 gold」处理，而应归到「数字归一化」这个检索问题**——被审计的错误归类带偏一步，就会改掉一个**本来正确的** gold。 |
| **核验发现：审计问题 ②（id 对、描述错）** | 审计把 `04d3ea4e3e8f448b` 描述成「**04-第一条**」，实测是 **`03-船舶尺度与吃水控制标准` 第一条「目的与依据」**（审计产物目录 `backend/target/audit/`：**语料全量转储 `chunks_all.csv` / `chunks_all.txt`**（由同目录 `01_dump.sql` 的 `\copy` 导出，`00_schema.sql` 是列结构、`02_docs.sql` 是每文档块数）与 **`extra.py` 产出的 `extra.txt`** 三处都写 `03-`；**锚点认「脚本名 + 产出的文件名」，不认行号**——原写的「第 285 / 396 / 163 行」随重新生成即失效。⚠️ **该目录不入库、`mvn clean` 会清空**，需要时按上述 SQL / 脚本重跑）。**危险之处**：这条 id 是要**写进 gold 的**，而描述错会让人以为「换成了另一篇文档的依据条」——**id 正确、描述错误，两者混在一句话里，核对时最容易只看 id 就点头**。 |
| **核验发现：审计问题 ③（判据过松）** | 审计给 `L2-028` 与 `L2-037` 的「等价块」**各只能回答一半问题**：`L2-028` 的三个候选分别只答「过闸费按哪个吨位」/ 只解释 GT / 只给 GT 与 DWT 全称而不答计费依据；`L2-037` 的两个候选一个只答「左闭右开」、一个只答「不得重叠」。**都不满足「单独取到即可回答」**。 |
| **由此逼出的一条可执行判据** | 等价块的判据**不是「相关」而是「单独可答」**——把候选块**单独**放进上下文，能不能答全题面？这条判据在核验中被反复使用，并最终写成修订记录里每一块的 `rationale`。它也解释了为什么**审计候选会被否决**：相关≠可答。 |
| **处置（逐条重判后才落改）** | 23 条**全部逐条重判**后才改，落成 `docs/评测报告/golden-l2-v2.json` 的 `revision.changes`：**30 条改动记录**，`counts` 记 **P0 3 / P1 采纳 13 / P1 否决 2 / P2 5**（合计 23 题）；其中 `P1-候选被否` **明细 9 条**，**整题候选全否 2 题**（`L2-028` 三块 + `L2-037` 两块 = **5 块**）。数据集实测 `acceptableChunkCount = 16`（跨文档 14 / 同文档 2）。决策记录见 `docs/DECISIONS.md` C-29。 |
| **教训** | **审计是线索，不是结论。** 它和[验证工具本身也要被验证](验证工具本身也要被验证.md) 讲的是同一件事，只是这次「工具」换成了一个**会写自然语言的复核者**：它的每一条都可能是对的、可能是错的，而**错的那些会被改成我的错**（我把正确的 gold 改掉 → 指标口径被破坏，且**不报错**）。正确姿势是：**逐条 + 用独立手段**（直接查库读全文、自己重算），而不是信任摘要。 |
| **⚠️ 未验证** | 「至少 3 处」是**我逐条核验时发现的**数量，**不排除还有我没发现的问题**；且审计的**完整叙述文本不在仓库里**（落盘只有 `backend/target/audit/` 下的产物），故本条目引的是**产物与 `revision.changes` 里的更正记录**，不是审计报告的原文。<br>⚠️ 另有一处**产物自身的不一致**（如实记）：数据集 `revision.basis` 字段当时只写了「至少 1 处误判（`L2-008`）」——那是**写该字段时**的已知数量，后来逐条核验又发现 ②③ 两处；**「至少 3 处」以核验后的实际数量为准**（`docs/DECISIONS.md` C-29 与 `docs/进度看板.md` §3.5 同此）。**字段写下来的那一刻是对的，之后就不是了——这类"曾经正确的记录"最容易留下来误导人。** |
| **可能被追问** | 「你自己核验的时候，怎么保证你不会也错？」→ 答：让核验依赖**与被核验对象独立的证据**——不重读审计的结论，而是**直接查库/读全文转储、自己重算**（如 `L2-039` 的最长公共子串我自己用动态规划重算，得 **161 字**，而审计报的是 **128**，差异来自是否剥离 Markdown 标记；**两种量法都足以支撑「近乎逐字重复」**，但我记的是自己算出来的那个数）。 |
