# 空作答被当成了成功作答

## 一句话

**接口返回"内容为空但并非错误"的响应时，作答器把它当成了一次成功的作答**——
于是批量运行报告 `failed=0`、`[PASS] 20 题作答完成`，
而其中**7 题的答案正文是空字符串**。判分器随后会把这些空答案记成"答错"，
**归因就此全错**：看起来像"模型不会答"，实际是"链路没能产出作答"。

## 锚点（可核对）

| 项 | 值 |
|---|---|
| 首次发现的批次 | 第 4 周 L5 层首次出分，`backend/run-L5.log` |
| 产物 | `docs/评测报告/layer-L5-answers-v1.json`（首版） |
| 现象 | **20 题中 7 题 `answer` 长度为 0**：`L5-002` / `L5-003` / `L5-004` / `L5-010` / `L5-013` / `L5-014` / `L5-016` |
| 同时的字段 | 这 7 题的 `toolStatus` 全是 `OK`、`contextChunkIds` 都有 5 条 ⇒ **两个通道都成功了，只有"组织语言"这一步产出为空** |
| 运行器当时的报告 | `failed=0`、`[PASS] 20 题作答完成`（**假 PASS**） |
| 根因 | 作答 `maxTokens` 设为 **1024**；L5 是复合题，提示词最长（数据表 + 5 条片段 + 事实），**预算被推理吃掉、正文没剩额度**，接口返回内容为空的响应 |
| 修法 | ①`maxTokens` 1024 → **2048**；②`AnswerComposer` 对**空白**内容**重试一次再抛异常**（⛔ 不再返回空串）；③原守卫只判 `null`、**没判空白**，这是关键漏洞 |
| 修后实测 | 重跑 L5：**三层再无长度 < 60 的作答**；且因运行器已支持续跑，**只重跑了那 7 题**（日志：`续跑跳过 13 题（本次未重复付费）`） |

## 为什么会漏掉（三个条件同时成立）

1. **判据写窄了**：原代码写的是
   `if (response == null || response.getResult() == null || response.getResult().getOutput() == null) throw ...`，
   只覆盖"对象为 null"，而**空白字符串是合法对象**。这个分支**永远不会被触发**。
2. **运行器的"失败"定义过窄**：`failed` 只在**抛异常**时自增。空串不抛异常 ⇒ 不算失败。
3. **没有对产物做"非空"校验**：产物写出去了、字段也在、长度却没查过。

三者叠加的结果是：**四层校验都说"好"，而答案是空的**。

## 教训（可迁移）

> **"返回了"不等于"返回了内容"。判据要覆盖"值合法但语义为空"。**

具体到本项目，值得写进规矩的三条：

1. **凡是"模型产出的文本"，都要显式区分三种结局**：
   `拿到非空文本` / `拿到空文本（可重试）` / `报错`。
   ⛔ 把前两者合成一种"成功"，就会制造假 PASS。
2. **批量的 `PASS` 判据不能只看"有没有抛异常"**，还要看**产物的关键字段是否真的非空**
   （本项目已改成：空正文 ⇒ 记为该题失败并保留在产物里，⛔ 不是跳过）。
3. **一次失败要追问"是谁的失败"**：本例若直接把 7 道空答案交给判分器，
   得到的会是"L5 通过率 65%"这样一个**把链路缺陷算在模型头上**的数字，
   而它会被写进《评测报告》当成技术指标。**归因错的分层数字比没有数字更糟。**

## 同一次批量里连踩的另外两处（重要：**同一根因与同一类误用**）

### ① 判分侧：空应答被记成了"三维 0 分"

同样的预算问题在**判分器**上又发生了一次，而后果更严重：

| 项 | 值 |
|---|---|
| 现象 | 首轮判分 `layer-L{3,6,5}-judged-v1.json`：**L3 解析失败 17/20、L6 7/15、L5 19/20** |
| 关键证据 | 失败项的 `reasoning` = **「裁判返回空应答」**，且 `rawResponse` **长度为 0** |
| 这意味着 | ⛔ **不是"JSON 格式错"，而是根本没返回内容** |
| 若不复核 | 汇总会打印「L3 严格口径通过 3/20 = 0.15」——**一个把链路缺陷算成模型答错的假数字**，而它会进《评测报告》 |
| 排查代价 | 首轮判分的产物里**没存原始应答** ⇒ 只能靠猜；补上 `rawResponse`（仅失败项）后**一次复测即定位** |
| 修法 | 判分 `maxTokens` 1024 → 2048 **仍为空** → 最终 **4096**（单题复测 `parseOk=true`，三维 `1/5/5` 且给了实质性理由） |
| 证据强度 | 修复后同题的 `reasoning` 是「回答正确说明无固定闸室水深刻度…但引用了不存在的参考资料条款号和未经服务端核对的具体吃水数值，事实忠实度判1分」——**判据真的在起作用**，不是空转 |

⚠️ **两个预算值都失败才说明问题不在"调大一格"**：1024 与 2048 都是空，4096 才通。
若只试到 2048 就下结论"不是 token 的问题"，会走偏很久。

⚠️ **重判时不能只补失败项**：首轮成功的 12 题是在 **1024** 预算下产出的，
与重判的 4096 **预算不一致**，混在一张表里不可比。故**删掉首轮产物、全量重判**——
宁可多花 12 次调用，也不让"分批预算不同"变成报告里说不清的口径差。

### ② 汇总侧：拿"给人看的标签"当机器判据

修这一处时又踩了**同一个家族**的另一个坑：

```java
boolean ok = "PASS".equals(ruleVerdict);   // ruleVerdict 实际是 "PASS（状态一致）"
```

`ruleCheck()` 返回的是**带说明的标签**（`"PASS（状态一致）"` / `"FAIL（期望 X，实际 Y）"`），
于是 `"PASS".equals(...)` **恒为 false** ⇒ 逐题节点里明明写着 `rulePass=True`（实测 L6-001~005 全 True），
汇总却打印 **`规则判据：0/15 = 0.0`**。

⛔ 正确写法是读**节点里那个布尔值**（`n.path("rulePass").asBoolean()`）。
**这与本项目早在 `verify_eval_record.sql` 上犯过的是同一个错**（当时是拿打印文本里有没有 `FAIL` 子串判成败，
而某个中文标签里恰好含 `FAIL`）。⇒ 归纳成一句硬规定：

> **人看的标签与机器判的分必须是两个值。凡是由文本派生判据的地方，都要问一句"这串字是我写的给人看的吗"。**
