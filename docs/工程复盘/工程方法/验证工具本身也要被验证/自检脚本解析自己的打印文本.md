# 自检脚本解析自己的打印文本

> **一句话**：自检项**失败时**会打印一行带 `FAIL` 字样的提示，而某个**自检项的中文标签里
> 正好含 `FAIL`**；脚本判定"有没有失败"的方式是**在输出里搜 `FAIL` 子串** ⇒
> **18 项全 OK，却报"失败 1 个"**。

## 锚点（可核对）

| 项 | 值 |
|---|---|
| 文件 | `backend/scripts/verify_eval_record.sql` |
| 症状 | 打印 `自检项 18 个，失败 1 个`，但逐项看**每一项都是 OK** |
| 根因 | 判定成败靠**搜自己打印的文本**，而不是靠**函数的返回值** |
| 修法 | 辅助函数 `expect_reject(...)` 返回 `0/1`，末尾对返回值**求和**；⛔ 不再解析自己的输出 |
| 修后 | 18/18，`[PASS]`，退出码 0 |

## 为什么这一类特别难自己发现

这是一次**假失败**（false failure），而假失败比假通过**更容易被忽略**：

- 假通过（假 PASS）通常会被人怀疑，因为"太顺了"；
- **假失败看起来像"检查起了作用"**——脚本报了问题，人第一反应是"去查那 1 项"，
  而不是"去查判定逻辑本身"。于是时间花在**一个不存在的缺陷**上。

⚠️ 而它恰好又是本项目反复出现的同一族问题的**反面**：
`工程复盘/工程方法/验证工具本身也要被验证/` 下已有多条「核对脚本谎报通过」，
本条补上镜像的一侧——**核对脚本也会谎报失败**。
两者根因相同：**判据取自"脚本自己说的话"，而不是取自"被检查对象的客观状态"。**

## 为什么"搜输出文本"是个陷阱（不只是这一处）

只要满足下面任一条，"解析自己的打印文本"就会出错：

1. **被搜的字符串会出现在"不该出现"的地方**（本例：中文标签里含 `FAIL`）；
2. **输出顺序/缓冲变化**（同族条目：[校验器输出顺序导致错误被吞.md](../校验器输出顺序导致错误被吞.md)）；
3. **输出被截断或分页**（管道的 `Select-Object`、日志轮转）；
4. **编码损坏**（本项目实测过的 [UTF8 按 ANSI 读丢换行](../../环境坑/UTF8按ANSI读丢换行/坑本身与四种读法实测.md) 会让中文标签变成乱码，
   于是"标签里含 `FAIL`"这件事**在别的终端上根本复现不出来**）。

⇒ **判据必须来自返回值或数据，而不是来自打印。**

## 正确做法

1. **每个检查项返回一个结构化结果**（`0/1` 或布尔），末尾**对这些返回值求和**；
   ⛔ 不要"打印 + 事后 grep 自己的输出"。
2. **退出码必须由同一份求和结果决定**，这样"打印"只是给人看的旁白，
   **删掉所有打印也不影响判定**（这可以当成一条自检：把打印注释掉，成败结论应当不变）。
3. **自检脚本自己也要被验**：故意注入一个违规，脚本必须报错；注入一个合法值，脚本必须放行。
   本项目 `verify_eval_record.sql` 的 12 类注入违规就是干这个的。
4. ⚠️ **另一条同类教训（同一轮踩到）**：并行的两条线**共享同一棵编译树**时，
   一条线的**编译错**会让另一条线的 `mvn test` 失败，而报错文本看起来像"环境问题"。
   本次实测：`eval/judge/LlmJudge.java` 在 `catch (Exception)` 上调了只属于
   `JsonProcessingException` 的方法 ⇒ 主源编译不过 ⇒ 另一个会话的测试运行连续两轮被挡。
   ⇒ **看到"跑不起来"先分辨是"我的代码错"还是"树被改坏了"**（`mvn -q compile` 单独跑一次即可区分）。
