# 用文本搜索统计落点，会把注释算成代码（假阳性）

> 类别：[工程方法](../README.md) ｜ 主题：[验证工具本身也要被验证](README.md) ｜ 返回总索引：[../../README.md](../../README.md)

## 现象（实测，2026-09-22）

要回答"规格书 §7.2 的 16 个 Span，到底有几个真的埋进了代码"，
我写了一条 `Select-String` 统计：对每个常量名搜 `AiSpans.<常量>`，**命中即算已埋**。

结果给出 **16/16 全有落点**——**与我刚写进文档的"15/16 已埋"直接矛盾**。
两者必有一错，于是当场去查那一处可疑命中。

## 真因：命中的是一行 javadoc 注释

`RetrievalPipeline.java` 里那一"落点"的原文是：

```java
* ⛔ 不为了凑齐 §7.2 的节点数而造一个空壳子 Span（同 {@code AiSpans.OUTPUT_VALIDATE}
  挂起的理由：一个只在无实质动作处触发的节点是**假证据**）。
```

——它恰恰是**解释"为什么没有埋这个节点"**的那句话。
**注释里提到常量名，不等于代码用了它。**

## 改正后的判据（两条，互相独立）

1. **只认代码行**：排除以 `*` / `//` / `/*` 开头的行后再统计。
   ⇒ 结果 **15/16**，未埋的正是 `OUTPUT_VALIDATE`，与文档一致。
2. **改搜字符串字面量** `ai.output.validate`（跨全仓）：
   只命中常量定义本身（`AiSpans.java:124`）⇒ **没有任何宿主启动它**，独立复现同一结论。

## 教训：它与「假阴性」是同一枚硬币的反面，而**这一面更危险**

本主题既有的 [局部搜索不能支撑否定结论](../局部搜索不能支撑否定结论/README.md) 记的是
**假阴性**：把**已修**的缺陷报成未修、把**存在**的东西说成不存在。
本条是反方向：把**注释**算成落点，把 **15 报成 16**。

| | 假阴性 | 假阳性（本条） |
|---|---|---|
| 表现 | "我没找到" → 断言**不存在** | "我找到字符串了" → 断言**已实现** |
| 后果 | 可能**改坏本来正确的做法** | 可能**以为已经做完**，于是不再做 |

⇒ **假阳性更危险**，因为它迎合"想尽快收工"的倾向，而且**不会引发任何追问**。
所以数字类的汇总句必须**同时做一次反向核验**：不是"搜到了什么"，
而是"**换个独立判据还成不成立**"（本例：排除注释 + 搜字面量，两条都指向 15）。

## 锚点

- 假阳性的来源：`backend/src/main/java/com/canalmind/rag/retrieve/RetrievalPipeline.java` 第 159 行的 javadoc。
- 反向核验命令：`git grep -n 'ai\.output\.validate' -- backend/src` ⇒ 只命中 `AiSpans.java:124` 一处定义。
- 该结论已写进 `docs/进度看板.md` §0.4.4（"15/16 已埋"）。
