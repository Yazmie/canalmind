# 把「命令失败」当成了「空结果」

> 类别：[工程方法](../README.md) ｜ 主题索引：[README.md](README.md) ｜ 总索引：[../../README.md](../../README.md)

**一句话**：核查脚本**自己报错**了，我却照它打印出来的「0 处」写结论——**「0」可以来自一个根本没跑成功的命令**。

## 实测（2026-09-21，本轮收尾时）

拆分 6 条超线条目后，我要核查「正文里是否还留着被删条目的旧路径」。第一版写法：

```powershell
Select-String -Path (Get-ChildItem docs -Recurse -Filter *.md).FullName, "AGENTS.md" -Pattern $pat
```

PowerShell 直接报错：`Cannot convert 'System.Object[]' to the type 'System.String' required by parameter 'Path'`
——`-Path` 拿到的是「一个数组 + 一个字符串」拼出来的**嵌套数组**，参数绑定失败，**命令等于没执行**。

而我的脚本只取了「命中行数」这一个量，于是它**打印出「0 行」**，我还差点据此写「已清理干净」。
换成 harness 的 `grep` 重做后，真实结果是 **15 处命中**，其中 **2 处是真残留**
（`docs/DECISIONS.md:589`、`docs/进度看板.md:1085` 的正文裸路径），已修。

## 可复用的三条判据

| # | 判据 | 本次怎么用 |
|---|---|---|
| ① | **「计数为 0」必须和退出码/错误流一起看** | `0` 只有在「命令成功」时才是事实；报错时的 `0` 是**空变量**，不是空结果 |
| ② | **给工具加对照探针**（搜一个必定命中的词） | 同一条 grep 搜 `split` ⇒ 命中原文第 11 行 ⇒ 证明**工具是活的**、待查词确实不在 |
| ③ | **stderr 是失败信号，不是噪音** | 报错被我的脚本吞掉了；后续脚本一律先判 `$LASTEXITCODE` |

## 代价

这类错的危险在于**它的输出和「真的没问题」长得一模一样**：都是「0」。
如果没做对照探针，交付里就会多一句「已清理干净」——而这正是本主题要防的那类**假 PASS**。
