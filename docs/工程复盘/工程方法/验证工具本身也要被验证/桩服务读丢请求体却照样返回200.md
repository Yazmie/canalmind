# 桩服务照常返回 200、链路照常绿：取证工具自己读丢了请求体

> **一句话**：本地回显桩（用来证明"哪个模型名真的被发出去"）**根本没读到请求体**，
> 但它**照常返回 200**、链路**照常打印 `[PASS]`**——因为它本来就不校验输入。
> 只有**日志里的 `model=?`** 露出了真相。

## 实测现场（2026-09-22，C-56 两档模型取证）

要知道"CLI 到底把哪个模型名发给了服务端"，最省的办法是让**服务端回显**：
写个本地桩，把每条请求的 `model` 记下来，再把 `DEEPSEEK_BASE_URL` 指过去（**零付费**）。
第一版桩是这样读请求体的：

```python
length = int(self.headers.get("Content-Length") or 0)
raw = self.rfile.read(length)
```

跑完得到 4 条日志，**每条都是 `model=? json_mode=- msgs=0`**：

```
model=? json_mode=- msgs=0 head=
model=? json_mode=- msgs=0 head=
...
```

⚠️ 关键点是**同一趟里 CLI 是绿的**：`[cli-exit=0]`、`[PASS] 链路已跑通`、作答还是桩返回的固定文本。
⇒ 桩坏了，**链路不会报错，只会"绿给你看"**。

## 真实原因（实测，不是推测）

给桩加上请求头日志后一眼看到：

```
POST /v1/chat/completions len=13073 ct=application/json te=chunked ce=None model=deepseek-v4-flash ...
```

**Spring AI 这条链路的请求体是 `Transfer-Encoding: chunked`，没有 `Content-Length`。**
而 `http.server.BaseHTTPRequestHandler` **不会**自动解分块：
`Content-Length` 缺失 ⇒ `int(None or 0) = 0` ⇒ 读到**空体** ⇒ `json.loads("")` 抛异常
⇒ 被 `except` 吞掉 ⇒ `body = {}` ⇒ 全字段落成默认值。

修法：**按 `Transfer-Encoding` 分支手动解分块**（逐块读长度行、读块、吃掉块尾 CRLF），
再按需 `gzip.decompress`；**并把请求头与体长一起记进日志**——这样"读体失败"会显式暴露成 `len=0`。

修好后同一趟跑出**真正的证据**：

| 桩收到 | 模型 | 提示词角色 |
|---|---|---|
| 3 次（抽取重试） | `deepseek-v4-flash` | 「结构化查询参数抽取器」= 小档 |
| 1 次 | `deepseek-v4-pro` | 「用简洁、准确的中文回答业务人员的问题」= 最终生成 |

## 判据（可复用）

1. **回显/桩类工具必须自校验输入**：读到空体、字段全默认值（`?`/`0`/`-`）时**必须报错或显著标注**，
   ⛔ 不要让"我没读到"表现成"客户端没发"。
2. **看日志，不看 PASS**：链路绿只说明"桩返回了合法响应"，**与桩是否读懂了请求无关**。
   这一步是本轮唯一发现问题的动作——`[PASS]` 那一行什么都没证明。
3. **记录"我读到了什么"而不只是"我理解出什么"**：`len=` / `ct=` / `te=` 这类原始量，
   是区分"输入坏了"和"逻辑坏了"的唯一线索。
4. **`Content-Length` 不是请求体存在的充分条件**：HTTP 里还有 chunked。
   凡自己实现 HTTP 读体，**两种都要处理**。
