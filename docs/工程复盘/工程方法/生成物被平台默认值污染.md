# 生成物被平台默认值污染（产物换行必须自己钉死）

> 类别：[工程方法](README.md) ｜ 返回总索引：[../README.md](../README.md)

| 项 | 内容 |
|---|---|
| **现象** | 同一份清单，我在 Windows 上生成出来是 **CRLF**，而仓库 `.gitattributes` 声明 `*.json text eol=lf`。于是**每跑一次生成命令，产物就变一次换行**——diff 里全是无意义噪音，评测基线也"看起来总在变"。 |
| **第一反应（错的）** | 我断定是 `Files.writeString` 把 `\n` 归一成了平台换行，还写了注释说明这个"原因"。**实测推翻了这个判断。** |
| **真正根因** | **Jackson 的 `DefaultPrettyPrinter` 默认缩进器用的是 `DefaultIndenter.SYS_LF`**（即 `System.lineSeparator()`）。所以在 Windows 上，**`writeValueAsString` 返回的字符串里本身就含 `<CR><LF>`**——问题出在**序列化阶段**，根本轮不到文件写入。 |
| **实测证据** | 三组对照（`WriteProbe` / `WriteProbe2` / `WriteProbe3`）：<br>①`Files.writeString(p, "a\nb")` → `a<LF>b`（**不归一**，我的猜测错了）；<br>②`Files.write(byte[])` → `a<LF>b`；<br>③`mapper.writeValueAsString(map)` → **`{<CR><LF>  "a" : [ 1, 2 ]<CR><LF>}`**（**字符串里就有 CR**）。<br>再加一组：只把 `indentArraysWith` 改成 LF 时，**对象级换行仍是 CRLF**——说明**两个缩进器要分别设置**。 |
| **正确修法** | 显式指定两个缩进器，再按字节写出：<br>`DefaultPrettyPrinter pp = new DefaultPrettyPrinter();`<br>`DefaultIndenter lf = new DefaultIndenter("  ", LF);`<br>`pp.indentObjectsWith(lf); pp.indentArraysWith(lf);`<br>`Files.write(out, mapper.writer(pp).writeValueAsString(m).getBytes(UTF_8));`<br>修后实测：`CR=0 LF=18851`（原为 `CRLF=13864 / LF总=13864`，即 100% CRLF）。 |
| **教训一：别把"我能想到的解释"当根因** | 我不仅判断错了，还**把错误解释写进了代码注释**——这比单纯判断错更糟，因为注释会被后来的人（包括我自己）当事实。**注释里的因果必须也是实测出来的。** |
| **教训二：跨平台产物的"环境相关默认值"要主动清点** | 同一类陷阱至少有四处：`System.lineSeparator()`（Jackson 缩进器、`PrintWriter.println`、`BufferedWriter.newLine()`）、`File.encoding`（影响编码）、`Files.writeString` 的换行（**实测不归一**）、JVM 默认 locale/timezone（影响格式化与日期）。**产物要跨平台可比，就必须逐个钉死。** |
| **业务含义** | 这类问题在**评测/数据管道**里格外致命：产物不可比 → 无法判断"这次差异是模型变好了，还是只是换行变了"。**"可复现"不只是"跑得出同样内容"，还包括"跑得出同样的字节"。** |
| **可能被追问** | "怎么保证以后不再犯？"→ 答：①产物写出时**显式指定换行**，不用框架默认；②把"编码 + 换行"做成**可执行的检查**（本项目 `verify_chunks.py` 会读产物，`audit_java_escapes.py` 查源码转义，编码检查独立跑）；③**入库前查 `.gitattributes` 的声明与工作区实际是否一致**——本次就是这样发现的（`git add` 时 git 警告 `LF will be replaced by CRLF`）。 |
