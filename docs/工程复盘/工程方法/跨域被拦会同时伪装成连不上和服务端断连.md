# 跨域被拦会同时伪装成"连不上"和"服务端断连"

> 类别：[工程方法](README.md) ｜ 返回总索引：[../README.md](../README.md)

| 项 | 内容 |
|---|---|
| **故障（2026-09-24，实测）** | 前端页切「后端接口」发送「你好」⇒ 页面显示 **`接口不可用：无法连接 http://127.0.0.1:8080（Failed to fetch）`**；同时后端日志留下 **`SseEmitter.send` 写 socket 失败**：`java.io.IOException: 你的主机中的软件中止了一个已建立的连接`。**两条现象指向两个不同的凶手**：前端像"连不上"，后端像"客户端崩了"。 |
| **真相** | **两个现象是同一件事的两面**：后端**收到过请求、已经开始推 SSE** ⇒ 连接层、端口、路由**全都没问题**；是**浏览器丢弃响应并主动断开**——因为响应里缺 `Access-Control-Allow-Origin`。⇒ 注意**判据是时序**："后端已经开始写"这句话同时证伪了"连不上"，也解释了"为什么后端会看到断连"。 |
| **⚠️ 为什么会被带偏（两条，都值得记）** | ①**`Failed to fetch` 不是证据**：它是浏览器给的**唯一**文本，同时对应**跨域被拦 / 后端没起 / 中途断网**三种成因——把它读成"连不上"就是**拿现象当结论**；②**我自己的文案是二次污染源**：页面当时把一切都印成"接口不可用：无法连接 …"，**等于在故障现场立了一个错的路标**——排查被带偏的直接原因就是它。⇒ 已改为分类文案（跨域/断网类只说"可能原因"，HTTP 状态码类单独说），并加断言钉住。 |
| **零成本定位手法（可复用）** | ⛔ 不要靠"再点一次/换个浏览器试"来猜。三条**不花钱、不调模型**的探针即可定案：①`curl -H "Origin: null" <一个不调模型的端点>` ⇒ 看响应里**有没有** `Access-Control-Allow-Origin`；②`curl -X OPTIONS -H "Origin: null" -H "Access-Control-Request-Method: GET" <接口>` ⇒ 无 CORS 配置时 Spring 固定回 **403 `Invalid CORS request`**；③**全仓搜 `Cors` / `CrossOrigin` / `allowedOrigin`** ⇒ 0 命中即"从来没配过"，不用再读代码。 |
| **为什么"简单请求"让这件事必然发生** | 该请求是 GET、无自定义头 ⇒ **浏览器不预检**，直接把请求发到后端；后端没配 CORS 时**照样执行控制器**（并真去调模型！），只是响应被浏览器拒收。⇒ 所以症状一定是"**后端有日志、前端说连不上**"这种自相矛盾的组合，而不是干脆的 403。⚠️ 反过来，**配上白名单之后**，界外来源会在**进控制器之前**被 403——顺带省下付费调用。 |
| **可复用判据** | **凡"前端说连不上、后端却有日志"，先怀疑"响应被拒收"，而不是连接层。** 并且：**任何被显示给用户的错误文案，都必须区分成因类别**——文案合并成因，等于把排查成本转嫁给下一个人（可能就是你）。 |
