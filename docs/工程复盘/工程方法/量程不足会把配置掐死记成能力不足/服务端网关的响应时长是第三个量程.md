# 服务端网关的响应时长是第三个量程

> 主题：[量程不足会把配置掐死记成能力不足](README.md) ｜ 分类：[工程方法](../README.md)

本主题原本只有两个量程旋钮——`max_tokens`（输出额度）与 `timeout`（**我们**的调用超时）。
2026-09-23 实测补上**第三个**，而它**不在我们的配置里**：**中继网关在 ~60 秒处切断长请求，返回 HTTP 504**。

## 现象与证据（2026-09-23 判分重跑）

| 项 | 值 |
|---|---|
| 表现 | 判分题大量 `0/0/0`、`parseOk=false`，`reasoning` = 「裁判调用失败（`LlmHttpFailure`：HTTP 504）」 |
| 规模 | L3 **16 题中 10 题 504**；L5 **7 题中 6 题 504**（**86%**） |
| 关键数字 | 连续失败的**间隔恒为 ~61 秒**（L5：10:24:36 → 10:28:39 = 243 s / 4 = **60.8 s**） |

判定它是"网关墙"而不是别的东西，靠**三条互斥解释逐条排除**：

| 看起来像 | 实际不是，依据 |
|---|---|
| **我们的读超时** | 本项目 `LlmReranker.DEFAULT_TIMEOUT` = **90 秒**，**比墙更长**；且 504 是**服务端真实状态码**（`DeepSeekHttpErrorHandler.failureOf` 取 `response.getStatusCode()`），**不是**本地超时伪装的 |
| **框架偷偷重试** | `LlmHttpFailure extends RuntimeException`，**不是** `TransientAiException`，而 Spring AI 1.1.2 的默认重试只认后者（`javap` 实测 `maxAttempts(10)` + 指数退避）⇒ **Spring 层零重试**、付费调用数 = HTTP 请求数 |
| **上游不可达** | 同一时段 `GET /v1/models` **HTTP 200**，且有 6 题判分**成功**（全 5/5/5）⇒ 端点**活着**，只是**长请求过不了墙** |

## 处置与教训

1. **量程可以长在别人的服务里**：诊断"长请求批量失败"时，**先把墙的高度量出来**
   （看**失败间隔是否恒定**），再把自己的 `timeout`、框架重试策略、端点存活**各排一次**
   ——三者会伪装成**同一个 504**。
2. ⛔ **别把量程类失败记成能力类失败**：504 落进产物就是 `0/0/0`，
   **与"模型答错 / 空应答"在表面上一模一样**，只有 `reasoning` 那一列能分开。
   这正是本主题最早的教训，只是**换了一个量程**再犯一次。
3. ⚠️ **"重试"能救的量程是有限的**：本项目 C-62 的空应答重试**刻意不重试网络异常**，
   于是**唯一能脱离"下界"的路被这个量程堵住** ⇒ **重试策略与量程必须一起评估**，
   否则会出现"我做了重试，却永远等不到它触发"。
4. **先算账再决定要不要撞墙**：撞一次墙 = **1 次付费调用 + ~61 秒**；本项目两次中止共花 **23** 次。
