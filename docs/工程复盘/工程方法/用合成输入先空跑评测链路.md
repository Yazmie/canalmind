# 用合成输入先空跑评测链路

> 类别：[工程方法](README.md) ｜ 返回总索引：[../README.md](../README.md)

| 项 | 内容 |
|---|---|
| **做法** | 指标脚本 `backend/scripts/eval_retrieval.py` 写完之后，**真实检索结果还没拿到**（那是另一条并行的线）。于是我先造一份**合成命中**（40 条题，命中名次分别为 1 / 12 / 25 / 未命中）**空跑一遍完整 I/O 路径**——不追求数字有意义，只要求"这条管道从头到尾真的走通了"。⚠️ 这份合成命中文件**当时是一次性用的、未留档**，故上面的名次分布不可复现（下一条给出的是**可复现**的对账）。 |
| **抓到 bug 1（会报错的）** | SQL 拼装时把 id 列表 `", ".join(...)` 得到的**字符串**又做了一次 `" OR content LIKE ".join(...)`——第二次 join 是在**字符串的字符**上做的，于是拼出 `LIKE % OR LIKE ' OR LIKE ,` 这样的**语法错误 SQL**，占位兄弟分析直接抛错。 |
| **抓到 bug 2（不报错的，更隐蔽）** | 修好语法后，分析**静默返回 0 条**。原因：匹配串写成 `content LIKE '%[TABLE:<id>]%'`，**要求 id 后紧跟 `]`**；而语料里真实标记**带行列信息**，写作 `[TABLE:<id> rows=N cols=M]`，于是**一条都匹配不上**。改成 `'%[TABLE:<id>%'` 后立刻正确（当时"涉及 13 条题"）。 |
| **bug 2 的机制（本轮复测，可复现）** | SQL 直接对账：`rag_chunk` 中 `chunk_type='TABLE'` 共 **87** 个，其中占位标记里 **id 后紧跟 `]` 的 = 0 个**、**id 后接空格 + 行列数的 = 87 个**；实际标记形如 `[TABLE:a96c50878545f717 rows=6 cols=2]`。**即第一版的匹配串在真实语料上必然命中 0，且不报任何错。**（⚠️ 当时"13 条题"这个数没有留档产物，不可复现；87/0 这两个数可随时重跑。） |
| **两处都写进了代码注释** | `eval_retrieval.py` 中**以「这正是本项目反复出现的」开头的那段注释**，含"先空跑 I/O 路径的价值"与"空跑第二次抓到真 bug"两段说明（同处还有变量 `hit_counts` 的声明/实际一致性检查）——**坑要沉进工具链，而不是记在脑子里**。 ⚠️ **锚点认注释引文与变量名，不认行号**：该脚本已 600 余行且还会增长（同族证据见 [规则过严会把正确的东西判成错的](规则过严会把正确的东西判成错的.md)）。 |
| **为什么值得** | **"能跑通"和"跑对了"是两件事。** bug 2 尤其典型：它不报错、不抛异常，只是**静默为空**——如果直接上真实数据，我极可能把它读成"**这类失败不存在**"，于是漏掉一个真问题（本项目特有的"占位 BODY 排在表格本体之前"失败模式）。合成输入的成本是几十行手工 dict、几分钟，换来的是**不必等上线才发现**。 |
| **合成输入的真正作用** | 真实数据到位后，脚本出错时**无法区分"是脚本错了"还是"检索真的不行"**。合成输入的预期值是**我自己构造的**，所以能**把这两个变量分开**：合成命中下数字不对 → 一定是脚本的问题。 |
| **边界（未验证，必须说清）** | 空跑只证明**I/O 与统计路径**通，**不证明指标口径对**——口径自证是 [验证工具本身也要被验证](验证工具本身也要被验证/README.md) 里 `--selftest` 的职责；它也**不能代替真实数据**。⚠️ 因此**本条不写任何真实检索指标数值**：这两个 bug 全部是**在真实命中到位之前**用合成输入空跑时抓到的，由合成输入得到的"涉及 13 条题""名次分布"都**不能当检索结论**（`AGENTS.md` §6 第 1 条：每个指标都要有出处）；真实指标属另一条并行线，出处以《评测报告》为准。 |
| **可能被追问** | "合成数据会不会把问题掩盖掉？"→ 反了：合成数据的**期望值是我手算的**，它把"脚本算错"暴露成"与期望不符"，而真实数据只能暴露"结果不好看"。"合成跑通就能上线吗？"→ 不能，见上条边界。 |

## 同族的另一个形态（2026-09-21）：**命令写在「开关存在」之前**

> 本条讲的是「**先空跑**」；下面这条是它的反面——**没空跑，就把命令写进了后台作业**。
> 两者要防的是同一件事：**让「工具面」的问题伪装成「数据面」的问题。**

| 项 | 内容 |
|---|---|
| **当时我做了什么** | 我把一批评测命令**写进一个后台作业**：**32 题产物**（dev 子集）**按 40 题全量出分**——命令里**没有** `--subset`，因为**当时 `backend/scripts/eval_retrieval.py` 里根本还没有这个开关**（它是后来才加的；现在的 `--help` 逐字写着：「子集出分：只对产物里【实际存在】的题目出分，不因缺席而失败（默认关闭时缺席任一题仍 [FAIL]）。」）。 |
| **工具给了我什么** | 出分步骤 `[FAIL]`、**退出码 2**，给的理由是「**缺席 8 题**」（32 题产物对 40 题金标集，差的正是 8 条 holdout）。 |
| **我据此发出的结论** | 「**缺席 8 题**」——一个**数据面的失败理由**（读起来像「题目丢了 / 产物不全」）。⚠️ 但它其实是**工具面**的事：命令里用了一个**当时还不存在**的开关。 |
| **真相是什么** | **产物本身没有问题**（那 32 题 dev 产物是完整、正确的）；真正的错是**我按「我以为工具已经有的能力」去写命令**，而工具当时**还没有这个能力**。影响是**流程中断**：出分只能**事后补跑**（补跑时开关已在，**退出码 0**）。 |
| **可复用的纪律** | **给批处理 / 后台作业写命令时，命令里用到的每一个开关都必须先在工具里「存在」且「实测过一次」**——⛔ 不按「这个开关应该有」去写；因为这类失败的措辞会落在**数据面**（它说的是「缺席 8 题」，而不是「没有这个开关」），把「**工具还不具备该能力**」伪装成「**数据缺了 8 题**」。 |
