# 字面量搜索与字段读错的假结论

> 类别：[工程方法](../README.md) ｜ 主题索引：[README.md](README.md) ｜ 返回总索引：[../../README.md](../../README.md)

> 本文件对应原条目《局部搜索不能支撑否定结论》的**实测 ①** 与**实测 ②**：两者都是
> **工具给出了一个看起来正常的输出**（搜索命中的 3 处 / 整齐的「不变 40」），而我**把它当成了事实**。
> 两节的原文标题，以及全部实测数字、文件路径锚点，均原样保留。

| 项 | 内容 |
|---|---|
| **实测 ①（搜源码 → 误报「缺陷未修」）** | 我用**字面量** `config.rerankTopN()` 搜源码，搜到引用就报「**B1 未修**」——但那条引用**早已改成带守卫的分支**（`if (config.rerankEnabled())` 之内），缺陷其实**已修**。实测该字面量在 `backend/src` 里仍有 **3 处**：其中真修处那一处现在**被 `rerankEnabled` 守卫包着**，另两处只是 banner 打印与产物序列化。<br>→ **字面量搜索既会把已修的地方误报成未修**（修法是「加守卫」而不是「删掉这个字段访问」），**也会漏掉改写后的变体**——反向实测：搜修法的写法 `rerankEnabled ? rerankTopN : fusionTopK`，命中的**全是 `RetrievalConfig` 的契约/校验/标签**，**恰恰不含真修处 `RetrievalPipeline`**。 |
| **实测 ②（按不存在的字段名读数据 → 假的「0 处差异」）** | 我写脚本复核「RRF 相对向量各题名次变化」，读了一个**并不存在的逐题键**（`rankOfFirstGold`——它其实是**顶层直方图**的名字，真名 `rankOfFirstGoldHistogram`），于是每题都取到 `None`，脚本输出「**变好 0 / 变差 0 / 不变 40**」——**一个完全假的「没有变化」结论，长得和真结论一模一样**。<br>→ 修法**不是**改字段名，而是**让脚本自证「数据真的读到了」**：加 `assert 命中题数 > 30`。实测读到 **39/40（向量）、40/40（RRF）** 之后才输出真实结果：**变好 8 / 变差 8 / 不变 24**。（本条写作时按同一口径**独立重算**过，数字一致 ✓，口径见下。） |

## 实测 ① 的动作对照：搜索命中了，缺陷却是修好的

| 我搜的写法 | 命中 | 能不能支撑结论 |
|---|---|---|
| `config.rerankTopN()` | **3 处**：`RetrievalPipeline`（**在 `if (config.rerankEnabled())` 分支内**＝已修）、`RetrievalQueryCli`（banner 打印）、`RetrievalResultJson`（产物序列化） | ⛔ **不能**：已修处的字面量**还在**，修复形式是「**加守卫**」，不是「删掉字段访问」 |
| `rerankEnabled ? rerankTopN : fusionTopK` | 全部在 `RetrievalConfig`（契约注释/校验/档位标签） | ⛔ **不能**：真修处 `RetrievalPipeline` 用的是 `if (config.rerankEnabled())`，**不含这个三元写法** |

**能支撑结论的证据（两个独立 oracle）**：

- **行为**：真机现场取证产物 `backend/target/selfcheck/b1-live-proof.txt`（免费档，不调付费模型）——
  `--no-rerank --fusion-top-k 30 --rerank-top-n 3 --top-k 5` 的每题 `hits` 是 **5** 条，
  而**旧实现这里会是 3**；`--rerank-top-n 3 --top-k 30` 档是 **30** 条（旧实现是 3）。
- **回归测试**：`hitsSizeAlwaysEqualsTopKForEveryLegalConfig`、`noRerankWithSmallRerankTopNKeepsContextTopN`
  （在 `backend/src/test/java/com/canalmind/rag/retrieve/RetrievalPipelineTest.java`）。
  把旧行为塞回去，两条测试确实变红（`expected: 30 but was: 10`、`Expected size: 5 but was: 3`）。

> **判据**：**「缺陷修没修」是行为问题，不是文本问题**——文本搜索只能给出**线索**，
> 而线索必须由**跑出来的产物或会变红的测试**收口（与 `AGENTS.md` §7.2 里
> 「`javap -v` 看真实产物 + 跑测试 + 并排对照」是同一套手法）。

## 实测 ② 的根因：字段名错了，脚本会安静地给出一份「像结论的输出」

- 度量产物里与「每题首个 gold 的名次」最接近的键是**顶层直方图** `rankOfFirstGoldHistogram`
  （实测 `backend/target/eval/item5/metrics-v2-rrf.json` 里为
  `{'1': 22, '12': 1, '2': 9, '3': 3, '4': 3, '6': 1, '8': 1}`），
  **并没有**逐题的 `rankOfFirstGold`；该文件的 `results` 只有 5 个聚合块
  （`all` / `byQuestionType` / `bySplit` / `byTopicClass` / `exclKnownLimitation`）加 1 个说明字符串 `exclFlaggedNote`。
- 于是「按逐题键读」**每题都取到 `None`**，而 `None == None` 会被算成「**不变**」——
  40 题全部落进同一格，输出「变好 0 / 变差 0 / 不变 40」。**这不是崩溃，是一份格式完好、数字自洽的假结论。**
- **修法（可复用）**：读完数据先**自证**——`assert 命中题数 > 30`。
  修后实测 **39/40（向量）、40/40（RRF）**，真实结果 **变好 8 / 变差 8 / 不变 24**。

> 本条写作时按同一口径**独立重算**以确认这组数字（口径写全，便于别人复算）：
> 数据源 `docs/评测报告/golden-l2-v2.json` 的每题 `goldChunkIds`，
> 对比产物 `backend/target/eval/item5/v2-vec.json` 与 `v2-rrf.json`；
> 「名次」＝ `hits` 中**第一条 `chunkId` 属于 gold 的记录的 `rank`**（前 30 名内找不到即记为未命中）；
> 比较两路名次，小者为「变好」。按此复算得 **39/40、40/40、变好 8 / 变差 8 / 不变 24**，与上表一致 ✓。
