# 桩替身"用尽后的默认值"会伪装失败原因

## 现象

第 3 周自检里有一条断言**红了**，红得"很有道理但其实不是被测代码的问题"：

```
[FAIL] Schema 不合规应降级 SCHEMA_INVALID，实际 NOT_JSON
```

被测逻辑（`ToolArgumentExtractor`）的重试路径看起来是对的：第 1 次应答不被 Schema 接受 →
带着错误反馈重试 → 用尽重试上限 → 按**最后一次**的错误类别降级。
按设计，三次都给同一份"Schema 不合规"的应答，降级原因就该是 `SCHEMA_INVALID`。

## 根因

**测试桩的行为把它自己的失败模式混进了被测逻辑。**

桩的写法是"按剧本依次返回，剧本用尽就返回空串"：

```java
List<String> queue = new ArrayList<>(replies);
JsonChatInvoker stub = (sys, user) -> queue.isEmpty() ? "" : queue.remove(0);
```

于是实际发生的是：

| 尝试 | 桩返回 | 抽取器判定 |
|---|---|---|
| 1 | `{"tool":"query_tariff","arguments":{"fee_type":"过路费"}...}`（枚举越界） | SCHEMA_INVALID |
| 2 | **`""`（剧本用尽）** | **NOT_JSON** |
| 3 | **`""`** | **NOT_JSON** |

降级原因取"最后一次"，于是报 `NOT_JSON`。
**问题不在被测代码，而在"我用一个与场景无关的输入把场景覆盖了"。**

## 教训（可迁移）

1. **替身的"默认行为"必须与场景一致，且显式声明**。
   "剧本用尽 → 返回空串"是一种**默认值**，它恰好等价于"模型返回了非 JSON"——
   一个与被测场景完全无关的失败模式。正确做法是**用尽后重复最后一个应答**
   （模型重试时通常仍给同样形状的错答，这也是更接近真实的假设）：

   ```java
   String[] last = {""};
   JsonChatInvoker stub = (sys, user) -> {
       if (!queue.isEmpty()) { last[0] = queue.remove(0); }
       return last[0];
   };
   ```

2. **"降级原因写错"这种红，比"断言失败"更难查**：它看起来像被测逻辑的问题
   （"为什么是 NOT_JSON？"),排查方向一开始就是错的。
   ⇒ 遇到"降级/异常类别与预期不符"时，**先看替身喂了什么，再看被测代码**。

3. **同类坑的通用形态**：凡是"用尽/超时/为空"的边界默认值（`queue.isEmpty() ? ""`、
   `map.getOrDefault(k, null)`、`readLine()` 返回 null 后当空串），
   都会**把宿主场景的失败伪装成另一个失败**。写替身时就要问一句：
   *这个默认值，会不会自己制造出我要观察的那个分支？*

## 锚点

- 修复：`backend/src/main/java/com/canalmind/structured/StructuredQueryCli.java` 的 `extractWith(...)`
  （剧本用尽后重复最后一个应答，含注释说明）
- 复现与回归：`StructuredQueryCli --selftest`（该断言此前红、修复后 2 项全绿）
- 同类断言在 `backend/src/test/java/com/canalmind/structured/ToolArgumentExtractorTest.java`
  的 `StubInvoker` 里用的是**重复最后一个应答**语义，故从未出现这个假红——
  两处语义不一致本身就是信号：**同一场景的两个替身给了不同的默认行为**。
