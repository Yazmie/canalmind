# 检查有效性必须被验证（"注入错误"测试）

> 类别：[工程方法](README.md) ｜ 返回总索引：[../README.md](../README.md)

| 项 | 内容 |
|---|---|
| **做法** | 每新增一条校验（如"钢材必须属金属"、[运河节点港名单一致](../数据一致性/运河节点港名单耦合.md)、[费率表列头统一](../数据一致性/费率表列头统一.md)），就**故意把违规内容写回文件**，确认脚本真的会报错、退出码变 1，**然后恢复**，再跑一次确认回到 PASS。 |
| **为什么必须做** | 校验规则写错的典型形态不是"不该报却报了"，而是"**该报却不报**"——正则没匹配上、字段名写错、循环根本没进。**这种情况脚本依然打印 PASS，看不出任何异常。** |
| **实测例子** | ①把 `25-术语与定义.md` 的「钢材」放回 `建材` 行 → 校验报错、退出码 1；恢复后 PASS。②把 `01` 的「钦州港」错标为"否" → 报 `种子数据 is_canal_node=True（应为 是）`，退出码 1；恢复后 PASS。 |
| **业务含义** | 这就是**变异测试（mutation testing）的思路**：**一个从不失败的检查，无法证明它有效。** 只有让它失败过，才知道它真的在守门。 |
| **可能被追问** | "生产上会不会太耗时？"→ 答：这是**写检查时做一次**的开发期动作（通常几秒），不是每次 CI 都跑。收益是"这条规则真的有效"有了证据。 |
