# Maven 增量编译把过期类留在 target 里

> 类别：[环境坑](README.md) ｜ 返回总索引：[../README.md](../README.md)

| 项 | 内容 |
|---|---|
| **现象** | `mvn test` 报 `Nothing to compile - all classes are up to date`（或 BUILD SUCCESS），但测试运行时报 `java.lang.Error: Unresolved compilation problem`，指向一个**我刚刚已经修好**的语法错误。**构建工具说"没事"，运行时说"有事"。** |
| **根因** | 一次失败的编译会把**带有 ECJ 错误标记的 .class** 留在 `target/classes`。此后源文件的修改时间若不比它新（例如被脚本整体重写、mtime 变化很小，或改了别的文件），Maven 就认为无需重编，于是**继续使用那个"编译失败的产物"**。它不是一个可运行的类，只会在被加载时抛出错误。 |
| **最迷惑的地方** | 报错内容指向**已经不存在于源码里的**错误位置。人会本能地去翻源码找那行，而源码是干净的——于是开始怀疑"是不是没保存""是不是改了别的文件"。 |
| **修法** | 每次重编前显式清理：`Remove-Item -Recurse -Force target\classes, target\test-classes`。清理前按项目约定**先列影响面**（见[工程方法/批量删除前先列出影响面](../工程方法/批量删除前先列出影响面.md)）——这两个目录都是纯构建产物，可安全删除。 |
| **另一处推论** | 排查"改了代码但行为没变"时，**先确认产物真的重新生成了**：比对 `target/classes/**.class` 与源文件的修改时间，或直接 `javap -v` 看字节码里的常量池。本轮正是靠 `javap -v` 看到 `String \\r\\n`（长度 4）才定位到真因——**源码看着对、字节码里是另一个东西**。 |
| **业务含义** | "构建成功"不等于"产物是新的"。任何依赖增量构建的排查，都必须先建立**产物与源文件的对应关系**，否则所有结论都可能建立在过期产物上。 |
| **可能被追问** | "为什么不用 `mvn clean`？"→ 答：本项目在受限沙箱下跑离线 Maven，`clean` 会连 `target` 下的其他东西一起清（可接受），但更精确的做法是只删 `classes`/`test-classes`，避免每次重编都丢掉可复用的东西。关键是**显式**，而不是指望增量判断正确。 |
