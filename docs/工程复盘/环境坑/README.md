## 本类最有价值的部分（**这才是该讲的**）

环境坑本身不值钱，**值钱的是两条共同教训**：

### 1. 同一件事在不同文件类型上要求**相反**

| 文件类型 | BOM | 换行 |
|---|---|---|
| `.md` / `.py` / `.sql` / `.yml` | ⛔ **无 BOM** | LF |
| `.ps1` | ✅ **必须 BOM** | CRLF |
| `.bat` / `.cmd` | — | CRLF |

**所以"BOM 要不要"不能靠记忆，必须由文件类型决定，并且写进 `.gitattributes` + 仓库文档。**
否则**每换一个人（或每换一个工具）就会重踩一次**——我自己就在这个问题上反复踩了三次。

### 2. 环境坑要"沉进工具链"，而不是"记在脑子里"

我把每个坑都**落到了具体位置**，而不是只在对话里说一遍：

| 落点 | 例子 |
|---|---|
| **写进脚本注释** | `verify_pgvector.ps1` 里注明为什么不用 `pg_ctl`、为什么必须 `psql -f` |
| **写进校验器规则** | BOM 检查进了 `validate_corpus.py` → [BOM 那次是工具当场抓出来的](../数据一致性/校验器抓出BOM.md) |
| **写进仓库文档** | `docs/进度看板.md` §6「已知坑」表 + `AGENTS.md` §7.2/§7.3 |
| **写进长期约定** | `AGENTS.md` 每个会话自动加载，新会话不会重犯 |

> **业务含义**：**"口头传承的知识"会随人员流动消失；"沉进工具链的规则"会一直生效。**
> 这是我认为工程师最应有的习惯之一——**遇到坑的产出物不该只是"我知道了"，
> 而应是一条以后会自动拦住的检查或约定。**

### 3. "挂起 + 无输出"先怀疑**子进程在等交互输入**

不是网络慢、不是 SQL 慢、不是死锁——**是它在等人输入口令，而人永远不会输入**。
而且 `stdin=subprocess.DEVNULL` **挡不住**它：交互式程序（如 psql）的提示读的是**控制台**，不是 stdin。

两条很便宜的做法：

1. 让子进程"**宁失败不等待**"（互斥式开关，如 `psql -w`：口令缺失时立刻报错）；
2. 显式 `timeout=`，把"永久等待"变成"**一条清楚的错误**"。

→ 详见 [psql从子进程调用会挂住](psql从子进程调用会挂住.md)
