# 产物写进了另一个同名目录树

> **一句话**：用**相对路径**指定输出位置，而命令又可能在**两个不同工作目录**下运行 ⇒
> 产物落到另一棵树里，**引用它的文档与它本身指向两个文件，且两边都不报错**。

## 锚点（可核对）

| 项 | 值 |
|---|---|
| 命令 | `java -cp … com.canalmind.intent.IntentRouterCli --selftest --json docs/评测报告/intent-routing.json` |
| **实际落点** | `backend/docs/评测报告/intent-routing.json`（123500 字节） |
| **文档里写的落点** | `docs/评测报告/intent-routing.json` |
| 发现方式 | `git status --short` 里出现一条**没人预期过的** `?? backend/docs/` |
| 修法 | `IntentRouterCli.outputPath()`：相对输出路径锚到"存在 `docs/评测报告/` 的那一层" |

## 为什么会发生

本项目的命令**存在两个合法的工作目录**，且**都不是错的**：

- `mvn` 必须在 `backend/` 跑（仓库根没有 POM，报 `no POM in this directory`）；
- `docs/` 在 `backend/` 的**上一级**。

于是同一条相对路径在两个 CWD 下指向两个不同的文件。而**读入**侧早就处理过这件事
（`IntentRouterCli.locate()` 会依次试 `docs/评测报告/` 与 `../docs/评测报告/`）——
**但写出侧没有**：`Path.of(args[i])` 就是原样按 CWD 解析。

⚠️ **真正危险的地方在于它全程不报错**：
- 命令退出码 0，自检打印 `[PASS]`；
- 产物**确实生成好了**，内容也正确（把它挪到正确位置后，重跑生成的字节与它**完全相同**）；
- 只有"按文档去根目录找产物的人"会发现文件不在那儿。

⇒ 这类错误的**暴露延迟很长**：它不会在你运行的那一刻暴露，而是在**别人**（或三个月后的你）
按文档去找文件时暴露。本项目早有一条同族条目（[同一个相对路径解析到两个目录.md](同一个相对路径解析到两个目录.md)），
但当时只把"**读**"这一侧堵住了。

## 更坏的一层：记录里跟着写了一个**假数字**

发现路径错位时，同时发现此前记录的"产物 124110 字节 / LF=3002"**对不上实测的 123500 / 2992**。
那个数字来自**更早的一次运行**（当时的落点也不同），被顺手当成了"本次产物"的属性写进决策记录。

⚠️ 这与本项目已记录的 [中间产物值被当成最终值沿用](../诚实记录/中间产物值被当成最终值沿用.md)
是同一类：**数字本身是真的，只是不属于它被贴上去的那个对象**。
⇒ **产物属性（字节数 / 行尾 / 哈希）必须由"刚刚这次运行"实测得出，⛔ 不沿用上一轮。**

## 正确做法（已落地并自证）

1. **输出路径要和输入路径锚在同一棵树**：读入用哪套前缀去探测，写出就用同一套去定位根，
   ⛔ 别一边锚仓库根、一边锚 CWD。
2. **绝对路径最省事**，但既然相对路径更常用，就把它做成**位置无关**的——这正是 `outputPath()` 的取法：
   取"存在 `docs/评测报告/` 的那一层"作为锚点，两个 CWD 下解析到同一个文件。
3. **自证方式**：改完之后**重跑一次**，比对 sha256。
   本次实测修前/修后都是 `96ACC1C022C6E773538526B2B616F88C2A7B727B02FBC8B4F9084F2DFD8399BE`
   ⇒ 证明**产物本来就是确定性的，错的只是落点**（这个区分很重要：它把"产物不确定"与"路径解析错"两种病因分开了）。
4. **`git status` 要看"有没有预期之外的新目录"**，而不只是看自己改的文件——
   本次就是靠一条 `?? backend/docs/` 发现的。

## 顺带记住

杂散目录删掉之后要**确认它没被重建**（重跑后 `Test-Path backend\docs` 必须为 `False`）——
否则"修好了"只是"这次碰巧没触发"。
