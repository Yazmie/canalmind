# 依赖写进了不生效的位置，而构建照样全绿

> **一句话**：`spring-boot-starter-data-redis` 被写进了 **`<dependencyManagement>`**——
> 那里**只声明版本、不引入依赖**。于是 `mvn test` **照样全绿**、608 例全过，
> 而**类路径里根本没有 lettuce**：代码 `import io.lettuce...` 直接编译不过。
> **"构建绿"与"依赖可用"是两件事**，而前者不会替你发现后者。

## 现场（2026-09-22，C-55 作答缓存的前提）

用户为 C-55 加了 Redis 依赖，我核对时看到 `git status` 里 `pom.xml` 有 12 行新增，
`mvn test` **通过**（608 例 0 失败）——如果就此收工，"依赖已就绪"这句话是**假的**。

真正的暴露点是**编译**：`RedisAnswerCache` 一 import 就报

```
错误: 程序包 io.lettuce.core 不存在
```

## 两个坑叠在一起（第二个只在"必须离线构建"的项目里才出现）

1. **位置坑**：`<dependencyManagement>` 里的依赖**不会**进入构建。
   ⟹ 修法：挪进 `<dependencies>`（版本仍由 import 的 BOM 管）。
2. **版本坑**：挪对位置后 `mvn -o` **直接失败**，报的是

   ```
   Cannot access huaweicloud (…) in offline mode and the artifact
   io.lettuce:lettuce-core:jar:6.6.0.RELEASE has not been downloaded from it before.
   ```

   实测本机离线仓库里 lettuce 只有 **6.1.10 / 6.3.2 / 6.5.5**，而 Boot 3.5.9 的 BOM 要 **6.6.0.RELEASE**
   ⟹ 该 starter **在本机根本无法离线解析**。最终改用**纯客户端 Jedis 6.0.0**
   （仓库里 jar 齐备、不经 Spring 容器、版本显式钉住——本项目无 `spring-boot-starter-parent`）。

## 我自己的浅验证（这一条比上面两个坑更值得记）

我当时的核对方式是：

```powershell
Test-Path ".m2repo\io\lettuce\lettuce-core"     # ⇒ True
```

于是我在回复里写了"离线仓库里四个 jar 全在"。**那是错的判据**——
`Test-Path` 只回答了"**目录**在不在"，没回答"**这个版本**的 jar 在不在"。
`io/lettuce/lettuce-core/` 目录确实在（6.1.10 等在里面），而 BOM 要的 **6.6.0.RELEASE** 不在。
⛔ **目录存在 ≠ 可用版本存在 ≠ 会被本次构建用到**。

## 判据（可复用）

1. **验证依赖，要跑"真的会用到它的那一步"**：至少一次会触发编译的构建
   （`mvn test` / `mvn dependency:build-classpath`），⛔ 不是看目录、不是看 `git status` 里有没有那条改动。
2. **"构建绿"是必要条件，不是充分条件**：编译**不会**因为"依赖声明在错的地方"而失败——
   它只会因为"**用到**了不存在的依赖"而失败。所以**必须真写一行用到它的代码**，才算验过。
3. **离线项目的版本要按"仓库里有什么"来定**，而不是按"BOM 说要什么"来定；
   两者冲突时，要么同步仓库（用户侧动作），要么换一个**仓库里确实有**的实现。
4. **`dependencyManagement` / `<profiles>` / 注释掉的块**——凡"写了但可能不生效"的位置，
   一律当成**未配置**看待，直到有一条构建证据。
