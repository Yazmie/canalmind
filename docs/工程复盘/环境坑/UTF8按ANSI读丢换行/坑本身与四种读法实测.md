# 坑本身与四种读法实测

> 主题：[UTF8按ANSI读丢换行](README.md) ｜ 类别：[环境坑](../README.md) ｜ 返回总索引：[../../README.md](../../README.md)
> 这条坑是什么，以及**同一次会话里四种读法的实测数字**（含 GBK 解码的旁证与 PS 版本）。

| 项 | 内容 |
|---|---|
| **坑** | **PowerShell 5.1 的 `Get-Content` 不带 `-Encoding` 时，按 ANSI／系统代码页解码**（本机默认代码页是 **GBK**）。GBK 是**双字节**编码：当行尾最后一个中文字的字节与紧随其后的 **LF（0x0A）** 被拼成**一个双字节序列**时，那个 LF 就被**吞掉** ⇒ **换行凭空变少**，而且**一个字都不报错**。 |
| **实测对象** | `backend\target\eval\l2-queries-v2-dev.txt`：**2423 字节 / LF=32 / CR=0 / 无 BOM / 32 条非空行**（`[System.IO.File]::ReadAllBytes` 与 `ReadAllLines` 实测）。 |
| **现场症状** | 我用**不带编码**的 `Get-Content` 统计开发集查询数，日志里打印「开发集查询文件：**22 行**」；而**同一批运行实际处理了 32 题**——产物 `backend/target/eval/item6-ctx10-norank.json` 里字段 `queryCount` 的值是 **32**。⇒ **日志与实际不一致，且不报错**。 |
| **⚠️ 最反直觉的一条** | **`-Raw` 并不免疫**——它同样按默认编码解码，所以「一次性读全文、再自己切」**照样丢换行**。⛔ 别把 `-Raw` 当成绕过编码问题的办法。 |
| **为什么难察觉** | 错的是「**数出来的行数**」，**数据本身没坏**：文件仍是 2423 字节、仍是 32 条查询，检索照跑。所以它看起来不像故障，只像**一句说得不对的日志**——⚠️ 而**换个脚本就会错在数据上**。 |

## 同一文件、四种读法（同一次会话实测）

| 读法 | 得到行数 |
|---|---|
| `(Get-Content <文件> \| Measure-Object).Count`（⛔ **不带 `-Encoding`**） | **22** ⛔ |
| `(Get-Content <文件> -Encoding UTF8 \| Measure-Object).Count` | **32** ✓ |
| `[System.IO.File]::ReadAllLines(<文件>).Count` | **32** ✓ |
| `((Get-Content <文件> -Raw) -split [char]10).Count` | **22** ⛔ |

> 会话环境：`$PSVersionTable.PSVersion` = **5.1.26100.9444**。
> ⚠️ 末行那个 **22** 是**按行**的口径：`-split` 会留下一个**末尾空元素**，表达式直接取 `.Count` 会得到 **23**——
> 两者都**远少于 32**，要记的点是「**它也丢换行**」，⛔ 不是「哪个数才对」。

**同一份编码错误的旁证**：同一文件用 `[System.IO.File]::ReadAllText` **按 UTF-8** 解出 **901 字符**、
**按 GBK（代码页 936）** 解出 **1286 字符**（多出来的正是把三字节 UTF-8 中文当双字节配对读的结果）；
GBK 那条路径上**幸存的 LF 只剩 22 个**（32 − 22 ⇒ **被吞掉 10 个**）。
