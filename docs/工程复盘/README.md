## 一条主线（贯穿全部文件）

"一致性"在 RAG 系统里会以**三种完全不同的面目**出现，处理方式要**逐层升级**：

1. **同一份语料内部**的矛盾 —— 靠人眼审查能发现 → [闸室尺度跨文件互斥](数据一致性/闸室尺度跨文件互斥.md)
2. **跨来源**的矛盾（文档 vs 数据库）—— 人眼看不出来，必须靠脚本做跨源比对 → [钢材归类跨来源冲突](数据一致性/钢材归类跨来源冲突.md)
3. **校验脚本本身失效** —— 最危险，因为**它让前两层看起来是绿的** → [校验器输出顺序导致错误被吞](工程方法/校验器输出顺序导致错误被吞.md)

> **讲法**：前两层是"认真"，第三层才是"可靠"。
> 真正的工程成熟度不在于"我写了很多检查"，而在于**我会去验证检查本身是否真的在工作**。

## 第二条主线：**"合法但错"是最难查的一类**

第二轮排查暴露出一类此前没写进本目录的错误形态，值得单独成线：

1. **代码合法、编译通过、测试也绿，但行为是错的** ——
   [转义与写入层的静默损坏](工程方法/转义与写入层的静默损坏.md)：
   同一处换行写成"一个反斜杠"或"两个反斜杠"，运行时分别是 2 字符与 4 字符，
   写错的那个**永远匹配不到**，于是归一化失效、表格整块消失，**一句报错都没有**。
2. **诊断它的工具自己也会错** ——
   [验证工具本身也要被验证](工程方法/验证工具本身也要被验证.md)：
   一个跨语言的假结论让我启动了全局替换，把 4 个文件改坏，回滚又过度纠正。
3. **改坏的经过必须留痕** ——
   [一次假结论引发的两轮错误修复](诚实记录/一次假结论引发的两轮错误修复.md)。

> **讲法**：这类问题的正确应对不是"更仔细地读代码"（读不出来），
> 而是**换判据**：并排 A/B 对照实验、码点/十六进制级断言、`javap -v` 看真实产物、
> 干净重建后跑测试。**"我看过了"不构成证据，"两个独立 oracle 一致"才算。**

4. **平台默认值悄悄污染产物** ——
   [生成物被平台默认值污染](工程方法/生成物被平台默认值污染.md)：
   Jackson 的默认缩进器用 `DefaultIndenter.SYS_LF`，于是"生成清单"这件事在 Windows 上
   产出 CRLF，而仓库声明 LF —— **每跑一次命令，diff 就变一次**。
   ⚠️ 这是我在本次**先猜错、再实测推翻自己**的一条：我原以为是 `Files.writeString` 归一的，
   实测发现它并不归一，真凶在**序列化阶段**。**"我能想到的解释"不等于根因。**

## ⚠️ 全局约定（新增条目时必读）

### 1. 用**语义化路径**定位，不用编号

条目文件名就是它的标题（如 `HNSW索引过滤条件静默少返回.md`）。
**不要引入编号**——编号会随重组位移，导致所有"见 §2.3"式引用失效；
语义路径在文件移动时只需改链接文本，且**看文件名就知道内容**。

**引用条目一定要写成 Markdown 相对链接**（便于点击跳转、也便于机械校验）：

| 场景 | 写法 |
|---|---|
| 引用**同类**条目 | 反引号包裹：`` `[标题](文件名.md)` `` |
| 引用**跨类**条目 | 反引号包裹：`` `[标题](../其他类/文件名.md)` `` |
| 引用**某类目录** | 直接链到该目录的 `README.md`，如本文件顶部的分类表 |

> ⚠️ **写示例时要把链接用反引号包起来**（如上表），
> 否则**示例本身会被链接校验判为失效链接**——这是个真实会咬人的小事。

### 2. 新增一个"种类"怎么办

**直接新建一个分类目录**，并在其中放一个 `README.md` 作为该类索引。
**不需要改任何既有文件的位置。**

若新种类当前只值一两条，先放进最接近的既有类；
**攒到 3 条以上再独立成目录**（避免空目录）。

### 3. 同一类下的"不同问题"再分层

**递归规则**：某条目内容长到**超过约 40 行**（或明显含多个独立子问题）时，
就地新建**主题子目录**，把它拆成多条：

```
检索工程/
├── README.md
├── 近似索引/                   ← 新增的主题层（示例）
│   ├── HNSW索引过滤条件静默少返回.md
│   └── 迭代扫描的代价.md
└── ...（其余条目）
```

**层数不设上限**——每层都用同一条规则判断"要不要再拆"。
但**不为未来预留空目录**：目录应当在有内容时才出现。

### 4. 每条记录必须有的要素

| 要素 | 要求 |
|---|---|
| **可核对锚点** | 文件路径 + 行号 / 实测数据 / 脚本名。⛔ 禁止"我记得当时…" |
| **业务含义** | 一条记录若说不出"这对真实系统意味着什么"，就不算复盘 |
| **可能被追问** | 面试防守用；想不出追问点，说明这条讲不透 |

### 5. 发现自己的错误结论 → **必须**在 [诚实记录](诚实记录/README.md) 留痕

不得静默改掉。

### 6. ⚠️ 批量删除/移动前，先列出**将要被影响的文件**

**真实案例**：我在把本目录从"单文件"重构成"分类目录"时，
用 `Get-ChildItem *.md | Remove-Item` 清理旧文件——
结果把**同一批里刚新建的 `面试速查卡.md` 一起删掉了**（新文件也在顶层、也匹配 `*.md`）。

**发现方式**：不是我看出来的，是**刚写好的 `check_links.py` 当场报**
`✗ 缺少顶层文件：面试速查卡.md`。
**这就是"把约定做成机器检查"的价值——它在新方法第一次使用时就开始兜底了。**

**因此的纪律**：

| 场景 | 要求 |
|---|---|
| **批量删除/移动** | **先打印匹配到的清单并核对总数**，确认无误再执行；⛔ 不要直接 `Remove-Item` 通配符 |
| **重构/改名后** | **必须**跑 `check_links.py`（本目录的结构完整性检查就是为这类事故准备的） |
| **新建 + 清理同批发生** | 格外小心——**新文件往往也匹配"旧文件"的筛选条件** |

> **业务含义**：**通配符删除的危险不在"删错文件"，而在于它删除的是"当时恰好匹配的东西"**，
> 而你对"当时匹配了什么"的认知来自**上一次的目录状态**，不是执行那一刻的真实状态。
> 所以生产环境的 `DELETE` 也应当先 `SELECT COUNT(*)` 核对——**同一个道理，只是规模不同。**
