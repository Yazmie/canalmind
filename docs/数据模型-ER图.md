## 三、四个设计关键点

### 1. `tariff_rule` 带生效期 —— 让「同一问题不同答案」成立

每条费率规则有 `effective_from` / `effective_to`（`NULL` = 长期有效）。
查询某业务日期的费率，必须按时间点过滤。

**没有这个字段，结构化查询就退化成单表 `SELECT`，Text-to-SQL 类任务失去意义。** 有了它，「2026 年 6 月过闸费多少」和「现在的过闸费多少」是两个不同答案，才需要真正的查询能力。

### 2. `tariff_rule` 的 EXCLUDE 防重叠约束 —— 保证费率唯一命中

```sql
EXCLUDE USING gist (
    fee_type       WITH =,
    cargo_category WITH =,
    tonnage_basis  WITH =,          -- ★ V5 加入（决策 C-31）
    numrange(min_ton, max_ton, '[)')              WITH &&,
    daterange(effective_from, effective_to, '[)') WITH &&
)
```

依赖 `btree_gist` 扩展。**从数据库层面保证「任一时点、任一货类、任一口径、任一吨位段」最多命中一条费率**，避免应用层靠代码保证唯一性。

> `tonnage_basis` 必须进这个 key：**「载货吨位 500 吨」与「船舶总吨位 500 吨」不是同一件事**，
> 不加这一维，两套吨位语义会共用 `min_ton/max_ton` 而互相排他。

> 注：`tariff_rule` 仅 **99 行**（C-31 前为 420 行），用 `EXCLUDE` 的写入开销可接受。若未来这张表变成高频写入，需重新评估（属 A 类决策）。

### 2.1 ★ `tonnage_basis` + `vessel.gross_tonnage` —— 两种计费吨位口径（决策 C-31 新增）

语料 `25-第十二条` 规定：**过闸费、港杂费、装卸费按「载货吨位」分档；
引航费、停泊费按「船舶总吨位」分档**（`08-第二条`：引航费与泊位费"与货物所属货类无关，
不得因货类不同而调整"）。

原模型只有 `vessel.deadweight_ton`（载重吨），且所有费用一律按货重算 ⇒
**引航费、停泊费按语料口径根本算不出来**（实测旧库把 0.80 元/吨 的基准直接当 `元/次`，
得到 0.60~1.34 元/次 的荒谬费率）。V5 因此补两处结构：

| 结构 | 作用 | 约束 |
|---|---|---|
| `tariff_rule.tonnage_basis` | 标明这条规则按哪种吨位分档 | CHECK `tariff_basis_pair_chk`：引航费/停泊费 **必须**是 `船舶总吨位` 且 `cargo_category='不区分'`；其余三种费用**必须**是 `载货吨位` 且货类不得为 `不区分` |
| `vessel.gross_tonnage` | 船舶总吨位（引航费/停泊费的分档依据） | CHECK `vessel_gross_ton_chk`：`> 0`；⛔ `25-第十一条` 明确它是**容积**指标、**不等同于**载重吨，故**不得**用 `deadweight_ton` 顶替（仿真数据按 0.55 系数派生，见 `generate_seed_data.py` 的 `GROSS_TON_FACTOR`）|

⚠️ **覆盖面限制（如实记录）**：本项目船队载重吨 800–5,500 ⇒ 总吨位 501–3,017，
因此引航费/停泊费的 **[5000, 10000) 与 [10000, ∞) 两档没有任何仿真数据触发**；
同理过闸费/港杂费的 **[5000, ∞) 档**也未触发（运单货重恒 < 5,000 吨）。
这不是缺陷，但**评测出题时必须知道**：费率查询题可以覆盖全部档位（查的是规则表），
而"从历史数据反推费率"类题目覆盖不到上述档位。实测清单见
`backend/scripts/verify_corpus_db_rates.py` 的 `[4] 覆盖与未实现清单`。

### 3. `fee_record.calc_basis` (JSONB) —— 费用可审计

金额不能只存结果，必须能回答「这个数怎么算出来的」：

```json
{"as_of": "2027-06-20", "days": 1, "formula": "吨位 × 单价",
 "relief": "1.00", "surcharge": "1.30", "rule_code": "CT-过闸费-集装箱-2000-20270101",
 "rule_source": "07-过闸费费率表（2027版）.md:104",
 "tonnage": "4343.08", "tonnage_basis": "载货吨位", "unit": "元/吨",
 "unit_price": "5.5000", "weight": "4343.08"}
```

C-31 后 `calc_basis` 增加了四个可审计字段：**计费吨位与口径**（`tonnage` / `tonnage_basis`）、
**减免与附加系数**（`relief` / `surcharge`）、以及**规则出处**（`rule_code` / `rule_source`
直接指到语料文件的行号）。理由是语料 `05-第十五条` 要求费用可追溯：
只存一个金额，事后无法回答"这 30% 加收是加在哪一步、依据哪一条"。

这是**费用计算通道（确定性计算）**的输出依据，也是评测时 Execution Accuracy 的比对基础。

### 4. `port.is_canal_node` —— 区分运河节点与外围港

用于「运河专项」类查询（如「运河沿线港口的吞吐量」），无需靠港口名字符串匹配。

## 四、数据窗口：通航后一年（决策 P-04 方案 B）

业务窗口为 **2026-09-16 ~ 2027-09-15**，系统「今天」为 **2027-09-15**。

### 为什么不是「截至真实今天」

平陆运河 **2026-09-16** 正式通航，而真实今天是 2026-09-18 —— **只通航了两天**。若窗口覆盖通航前，实测后果是：

| 指标 | 窗口截至 2026-09-18 | 窗口取通航后一年 |
|---|---|---|
| 运河业务占比 | 0.92% | 见下方口径说明 |
| 过闸费占费用明细 | 0.30% | **28.57%**（C-18 前为 29.05%）|

> ⚠️ **口径更正记录（2026-09-19，探针实测 → 决策 C-18）**：本表原写「运河业务占比 100%
> （全部经运河）」，该说法**不严谨**，已按实测拆分口径；
> 后由 C-18 统一为航线级口径，见下方说明。

### 运河业务占比：口径已由 C-18 统一

`port.is_canal_node` 是**港口**属性，只能回答「这个港口是不是运河节点」，
**无法回答「这条航线是否穿越运河」**。这正是原先两个口径打架的原因：

| 口径 | 定义 | C-18 前 | C-18 后 |
|---|---|---|---|
| **过闸费覆盖率** | 被收取过闸费的运单占比 | **100%**（生成器设为必收项） | 与航线口径**严格一致** |
| **端点节点占比** | 航次起终点至少一端是运河节点 | **97.67%**（2,344 / 2,400 航次） | **即为 `voyage.via_canal`** |

**C-18 的处置**：新增 `voyage.via_canal` 字段，取值口径即「起点或终点为运河节点」，
并让**过闸费只在 `via_canal` 为真时收取**。于是两个口径合并为同一个，
`南宁港六景作业区 → 北海港` 这条 56 航次 / **743 票**的航线被明确判为**不经运河**，
不再收过闸费。原先"两端非运河节点却收过闸费"的矛盾消失。

探针 7 已加**不变式检查**，两个计数必须恒为 0：

| 检查项 | 实测 |
|---|---|
| 非运河航次却收过闸费 | **0** |
| 运河航次漏收过闸费 | **0** |

> ⚠️ **口径声明（不得省略）**：`via_canal` 是**仿真数据的简化口径**，
> 依据端点节点而非真实航道几何。真实世界需按航道判定，属方案 B（航段路径表）
> 的范畴。对外表述时必须带上这句限定，**不得称其为真实运河业务占比**。

**运河业务在数据中几乎不存在（窗口截至今日时），项目名不副实。** 所有「运河闸费」「运河吞吐量」类评测题都缺乏数据支撑。因此窗口整体后移到通航之后。

### ⚠️ 代价与纪律

本数据集是**前瞻模拟**（时间点在真实今天之后），**不是历史真实数据**。

- README 必须主动交底这一点，不得含糊为"历史数据"
- 不得基于此数据集对外宣称任何准确率或业务结论
- 过闸费占 `fee_record` 的 **28.57%**（C-18 前为 29.05%），构成费用明细主体。
  其收取规则已与 `voyage.via_canal` 绑定（C-18），但 `via_canal` 本身仍是
  **生成器的简化口径**，不是从真实航道几何推导出来的——见上方口径声明

## 五、数据生成的可复现性

- **固定随机种子** `SEED = 20260918`：任何人任何机器跑出的数据完全一致。
- 这是评测可复现的前提 —— 数据集每次不同，指标就没有意义。
- CSV 产物**不入 git**（`.gitignore`），只提交生成脚本（决策 C-09）。

### ✅ 已验证：生成器确定性（2026-09-19 实测）

不靠"应该一致"下结论，而是**两次生成后逐文件比对 SHA256**：

```
结论: ✅ 完全确定性：同目录重跑，全部 11 个文件字节一致
```

> 注：比对时必须让两次输出到**同一目录**。若输出到不同目录，
> `load_seed.sql` 里的 `\copy ... FROM '<路径>'` 会因路径不同而不一致 ——
> 那是路径差异，不是数据差异（首次比对时踩过这个坑）。

### 命名与 id 约定

- 业务表用 `GENERATED ALWAYS AS IDENTITY`，`COPY` 不允许直接写 `id`。
- 装载脚本走「临时表 → `INSERT ... OVERRIDING SYSTEM VALUE`」两步，
  既保住 DDL 强约束，又让仿真数据的 `id` 与外键引用完全可控。
- 装载末尾用 `setval` 修正 identity 序列，避免后续自增冲突。
- **`port` / `cargo_type` 没有 `id` 列**（用业务主键 `port_code` / `cargo_code`），
  `setval` 只对这 7 张含 `id` 的表执行（见脚本内 `TABLES_WITH_ID`）。
- **编号年份与日期保持一致**：`voyage_no` / `waybill_no` 的年份段取实际业务日期年份（避免出现「VY2025」却挂在 2027 年航次上的矛盾）。

### 业务时序自洽规则

生成器不只是"随机填数"，而是保证业务语义成立：

- 运单日期锚定所属航次的离港日（−168h ~ +72h），运单不会凭空出现在航次之外
- 运单状态按相对系统「今天」的日龄推断：>30 天多为「已结算」，3–30 天为「已卸船/在途」，<3 天为「待装船/在途」
- 所有日期夹回业务窗口 `[BUSINESS_START, BUSINESS_END]`
