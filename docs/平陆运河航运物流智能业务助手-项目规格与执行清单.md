## 零、设计取舍：为什么是双通道，而不是纯 RAG

### 0.1 纯文档 RAG 方案的三个问题

本项目最初的设计是"平陆运河航运物流智能客服"——一个基于 RAG 的知识库问答系统（该方案存档于 `平陆运河航运物流智能客服系统.md`）。经评估后放弃，原因有三：

**问题一：知识载体选错了。**

原方案的价值主张是"垂直领域知识库质量 > 模型本身"。但平陆运河 **2026-09-16 才正式通航**，可获取的"过闸费标准、港区收费、通行规则"等文档大概率是新闻通稿与通用内河法规的拼盘，**无法保证版本权威性**。

更深一层：运河刚开通，业务上最紧迫的需求不是"某个规则怎么写的"（话术型问题），而是"这条船这趟货要多少钱、排哪个闸次、需要哪些单证"——**这些答案的权威载体是结构化运营数据，不是散文式文档**。

**问题二：技术内核过于单薄。**

纯 RAG 问答在 2026 年已是基线能力，缺乏区分度。而航运业务的核心诉求（运价测算、运量统计、费率查询）**本质是结构化数据检索**，恰恰是纯 RAG 无法覆盖的：

| 能力维度 | 纯文档 RAG | 本项目 |
|---|---|---|
| 自然语言 → **结构化数据**检索 | ❌ 无 | ✅ 核心能力 |
| 传统**搜索/排序模型** + 向量模型结合 | ❌ 仅向量 | ✅ BM25 + 向量 + RRF + Rerank |
| 数值计算正确性 | ❌ 依赖模型算术 | ✅ 确定性代码 + SQL 聚合 |

**问题三：产出无法验证。**

原方案的问答话术中反复出现"准确率从 60% 提升到 85% 以上"，但**没有 Golden Set、没有分层、没有消融、没有基线定义**——该数字无法复现，也就无法证明任何优化真实有效。`AI 应用评测体系` 第 3 行开篇即指出这类判断方式的缺陷。

**另需修正的技术错误**：原文档第 275 行称"余弦相似度……**取值范围是 0 到 1**"。余弦相似度实际为 **[-1, 1]**；PgVector 的 `<=>` 是**余弦距离** = 1 − 相似度，范围 [0, 2]。

> ⚠️ 原文档第 147–356 行的问答参考答案**不可照抄**，问题清单见 §9.2。

### 0.2 本方案的三个改动

| # | 改动 | 收益 |
|---|---|---|
| 1 | **知识载体**：从"纯文档知识库"改为"**结构化业务数据库 + 规则文档库**"双载体 | 绕开问题一。数据库为自建仿真数据集，数据质量完全可控 |
| 2 | **技术内核**：从"文档 RAG 问答"改为"**意图路由 + 受控结构化查询 + 混合检索 + 评测闭环**" | 覆盖结构化检索、混合检索、Agent 编排 |
| 3 | **产出形态**：从"能跑的系统"改为"**能跑的系统 + 可复现的评测报告 + 可回放的 Trace**" | 所有指标有出处，技术结论可验证 |

### 0.3 能力边界：结构化查询的两阶段设计

知识库对 **Text-to-SQL / Schema Linking 零覆盖**（全库搜索无任何命中）。这是本方案难度最高的部分，但：

- 它是航运业务最真实的需求（运价、运量、费率查询），**不能整块砍掉**；
- 它缺少内部知识库支撑，**不能贸然做通用 NL2SQL**。

因此采用**两阶段形态**：

- **阶段一（必做，第 3 周）**：**Schema 契约驱动的受控查询工具集**。不追求模型自由生成 SQL，而是限定业务查询维度，用 JSON Schema 契约约束参数，服务端参数化查询。该路线由 `大模型结构化输出：从 JSON 契约到 Function Calling 落地.md` **全程覆盖**，风险低、有现成弹药。
- **阶段二（加分，第 5 周视余量）**：升级为模型自生成 SQL，配只读账号 + 表白名单 + `LIMIT` + 超时。

**差异化重心放在评测与可观测性上**——这两块知识库深度充足（`AI 应用评测体系`、`AI 可观测性与 Trace` 两篇合计 1200+ 行），且多数同类项目不做。

## 一、项目定位

**项目名称**：**CanalMind**（运河智答）
**全称**：平陆运河航运物流智能业务助手
**英文全称**：CanalMind — Passenger & Cargo Business Assistant for Pinglu Canal Shipping Logistics

> **命名用意**：`Canal`（运河/航运域）+ `Mind`（智能）。不绑死"平陆"二字，可迁移到任何内河/港口场景；同时 `canalmind` 是合法干净的 Java 包名段（`com.canalmind.*`）。

**一句话定位**：面向内河航运物流场景的**双通道智能业务问答系统**——对结构化业务数据做受控查询，对规则文档做混合检索，由意图路由统一编排，并具备**可复现的评测闭环与全链路 Trace**。

**设计价值**：

- **场景真实性**：贴合平陆运河通航后的真实内河航运业务形态（港区、船闸、运单、费率、单证）
- **技术栈完整**：Spring AI + 混合检索 RAG + 受控结构化查询 + 意图路由
- **结论可验证**：评测报告 + Trace 链路，所有技术论断可复现而非主观描述
- **数据可掌控**：业务数据自建，不依赖无法获取且版本不明的行业文档

**核心设计主张**：

> "通用大模型答不了航运业务问题，因为答案分散在两个地方——规则在文档里，数值在数据库里。系统要做的不是'检索文档'，而是**判断该查哪儿、然后去查**，并用一套分层评测集证明每一步优化真的有效。"

## 二、业务领域建模

### 2.1 设计原则

- 表结构、约束、计费规则**按公开的内河航运业务逻辑设计**，不虚构不合逻辑的字段
- 数据量：核心表 3–5 万行仿真数据，让索引和聚合查询有真实意义
- **README 中必须主动交底**："业务库为自建仿真数据集（真实企业数据不可获得），表结构与计费规则按公开业务逻辑设计"

> 主动说破比被问出来强。这句话本身也体现工程诚信。

### 2.2 核心表设计（10 张）

| 表名 | 说明 | 关键字段 | 索引要点 |
|---|---|---|---|
| `port` | 港区/作业区 | `port_code`, `name`, `river_section`, `type` | `port_code` 唯一 |
| `lock` | 船闸与闸次 | `lock_id`, `name`, `chamber_no`, `capacity_ton`, `operating_hours` | `(lock_id, chamber_no)` 联合 |
| `vessel` | 船舶 | `vessel_id`, `name`, `vessel_type`, `deadweight_ton`, `draft_m`, `owner_id` | `vessel_type`、`deadweight_ton` |
| `cargo_type` | 货类 | `cargo_code`, `name`, `category`, `is_dangerous`, `hazard_class` | `cargo_code` 唯一 |
| `customer` | 客户 | `customer_id`, `name`, `type`, `credit_level`, `contact` | `type` |
| `voyage` | 航次 | `voyage_id`, `vessel_id`, `origin_port`, `dest_port`, `etd`, `eta`, `status` | `(vessel_id, etd)`、`status` |
| `waybill` | 运单 | `waybill_no`, `voyage_id`, `customer_id`, `cargo_code`, `weight_ton`, `freight_amount`, `status`, `created_at` | **`(created_at)`、`(cargo_code)`、`(customer_id)`** |
| `documents` | 单证 | `doc_id`, `waybill_no`, `doc_type`, `status`, `submit_time`, `audit_time` | `(waybill_no, doc_type)` |
| `tariff_rule` | 计费规则 | `rule_id`, `fee_type`, `cargo_category`, `min_ton`, `max_ton`, `unit_price`, `effective_from`, `effective_to` | **`(fee_type, cargo_category, effective_from)`** |
| `fee_record` | 费用明细 | `fee_id`, `waybill_no`, `fee_type`, `amount`, `calc_basis`, `created_at` | `(waybill_no)` |

**两个设计要点**：

1. **`tariff_rule` 带生效期（`effective_from` / `effective_to`）**。费率是随时间变的，这天然引出"**按时间点查询**"的语义——直接对应你知识库 `AI 应用评测体系` 第 374 行讲的"固定快照回归要明确以某个时间点为参照"，是很好的叙事支点。
2. **`fee_record.calc_basis` 存计算依据**（用了哪条 `rule_id`、什么公式）。审计和溯源的基础，也让"费用计算"这条链路的 Trace 有真实内容可记。

## 四、模块规格

### 模块 1：意图路由层

**做什么**：判断用户问题该走哪条通道（结构化查询 / 文档检索 / 计算 / 复合 / 拒答）。

**演进路线**（对应 `大模型网关详解` 第 336 行"先让系统可控，再让系统省钱，最后才让系统变聪明"）：

1. **规则优先**：关键词 + 正则命中明确意图（"多少钱"→计费，"需要什么材料"→文档）
2. **分类器兜底**：规则未命中时用小模型分类
3. **复合意图**：拆成多步 plan，并行执行后汇总

**关键约束**：路由结果必须在**调用开始前固定**并写入 Trace。`大模型网关详解` 第 150 行专门警告：调用结束后重新路由再记 usage，会把 A 产生的费用记到 B 头上。

**对应文档**：`大模型网关详解`（第 326–340 行）、`AI 工作流中的 Workflow、Graph 与 Loop`

### 模块 2：结构化查询通道（原 Text-to-SQL，降级实现）

**做什么**：回答"六景到广州港 100 吨水泥多少钱""上个月哪个货类运量最大"这类**数值/聚合**问题。

#### 阶段一：受控查询工具集（第 3 周，必做）

不生成自由 SQL，而是**定义一组业务查询工具**，每个工具有严格的 JSON Schema：

```
QueryTool: queryFreightEstimate
  参数: originPort(enum), destPort(enum), cargoCode(enum),
        weightTon(number), queryDate(date, 用于选生效费率)
  实现: 参数化 SQL，查 tariff_rule + 聚合

QueryTool: queryWaybillStats
  参数: dimension(enum: cargo/port/customer), timeRange, metric(enum)

QueryTool: queryDocumentRequirement
  参数: bizType(enum: 出口报关/船舶过闸/...), cargoCode(enum)
```

**这个形态的全部工程细节你库里都有**（`大模型结构化输出`）：

| 要点 | 文档位置 | 内容 |
|---|---|---|
| Schema 设计 | 第 274 行 | 一个字段只表达一件事 |
| 字段说明 | 第 290 行 | 写"何时用"和"何时不用" |
| 枚举优先 | 第 308 行 | 枚举优先于自由文本 ← **本模块关键** |
| 必填字段 | 第 320 行 | 谨慎但不要偷懒 |
| Schema 版本 | 第 331 行 | Schema 也要有版本号 |
| 失败重试 | 第 343 行 | 让模型修正具体错误 |
| 降级策略 | 第 366 行 | 别让一个 JSON 拖垮主流程 |
| Java 示例 | 第 446 行 | 把订单查询做成可校验工具（可直接改写成运单查询） |

**安全要点**（`大模型结构化输出` 第 382–445 行）：参数校验、权限控制、敏感操作二次确认、幂等、审计日志、超时重试短路。另外 `Agent 安全实战` 全文可作工具越权的补充论据。

#### 阶段二：模型自生成 SQL（第 5 周，加分）

若余量允许，升级为：
- **Schema Linking**：只注入相关表/列（表一多这是必需项，不是加分项）
- **执行报错自纠正循环**：≤2 次，对应第 343 行"让模型修正具体错误"
- **SQL 安全**：只读账号、表白名单、`LIMIT`、`statement_timeout`、关键字黑名单

> **重要**：费用计算**绝不让模型算**。"从六景到广州港 100 吨货多少钱"的正确解法是——模型只负责**抽取参数**，金额由 SQL 聚合 + 代码计算得出。这是本项目的重要设计原则：**不信任模型的算术，只信任它的意图理解**。

**对应文档**：`大模型结构化输出`（主力）、`Agent 安全实战`、`大模型 API 调用工程实践`

### 模块 3：文档检索通道

**做什么**：回答"出口报关需要哪些材料""船舶过闸流程是什么"这类**规则/流程**问题。

#### 3.1 链路（严格按 `RAG 优化` 第 176 行的五步）

```
Metadata 预过滤 → Hybrid Search 粗召回 30–100 条
  → 去重并合并相邻片段 → Rerank 选出 5–10 条
  → 压缩后写入 Prompt
```

#### 3.2 三档 Top-K 必须分开（`RAG 优化` 第 147–149 行）

| 参数 | 建议值 | 作用 |
|---|---|---|
| `recall_top_k` | 30–100 | 防止漏召回 |
| `rerank_top_n` | 5–10 | 控制精排成本 |
| `context_top_n` | 3–6 | 由模型实际可阅读的证据量决定 |

> 文档第 151 行强调：**三者应在同一评估集上一起调整**。原方案只提了单一 Top-K，这是典型的知识盲区。

#### 3.3 混合检索（BM25 + 向量）

**RRF 融合**，理由见第 123 行：*"RRF 只依据候选名次融合，不必把 BM25 分数与向量余弦分数直接换算到同一尺度"*。

**但要注意适用边界**，第 125 行明确写了：

> *"文档高度结构化且查询几乎不含关键词时，Hybrid 的增益可能不明显。相反，错误码、产品型号、配置项和专有名词占比较高的查询，需要保留关键词通道。"*

**航运场景恰好属于后者**——"六景港区""过闸费""EDI 申报"这类专有名词占比高，向量检索容易把近义但错的内容排前面。**这就是你做混合检索的业务理由**，比泛泛说"混合检索更好"强得多。

#### 3.4 Query Rewrite

第 141 行关键约束：**原始 Query 和改写结果要一起参与召回并融合**，因为改写模型可能理解错（"改把退款理解成取消订阅时，原始 Query 仍能保留正确的召回入口"）。第 135 行补充：改写要"补出可检索的表达，但不能替用户改变问题的含义"。

#### 3.5 Rerank

#### 4.1 向量索引（`RAG 向量索引算法和向量数据库`）

### 模块 5：上下文工程与多轮对话

**做什么**：会话管理、上下文裁剪、多轮改写。

**要点**（`上下文工程`）：

## 六、评测闭环（★★★ 核心差异化）

> **这一节是本项目最重要的部分。** 它决定所有技术指标有没有出处，也是"套壳 RAG"和真工程师的分界线。

### 6.1 Golden Set 构建

**规模**（`AI 应用评测体系` 第 94 行）：

> *"第一版可以先用 20 到 50 条真实任务验证评测流程。这一数量只是启动用的工程样本，无法支持统计结论。"*

**目标**：先跑通流程，再扩到 **150–200 条**。

**分层维度**（第 100 行一句关键的话）：

> *"样本分布往往比总量更先决定评测能否发现问题。**200 条同类问题不如 100 条覆盖 10 类场景**。"*

本项目分层设计：

| 层 | 条数 | 说明 | 数据来源 |
|---|---|---|---|
| L1 结构化可答 | 40 | 运费、运量统计、费率查询 | 人工构造（数据库反查） |
| L2 文档可答 | 40 | 报关流程、通行规则、单证要求 | 从知识库文档反向生成 + 人工审核 |
| L3 **应拒答** | 20 | 知识库和数据库都无答案 | 人工构造 ← **最容易被忽略** |
| L4 多轮改写 | 25 | 依赖上文的追问 | 人工构造 |
| L5 复合意图 | 20 | 同时需要查库和查文档 | 人工构造 |
| L6 边界/对抗 | 15 | 参数缺失、单位错误、越权请求 | 人工构造 |
| **保留集** | 30 | **不参与任何调参** | 见 6.2 |

第 66 行提醒：*"用户只说'东西坏了'时，订单、时间和故障细节都缺失，**预期行为应是先追问**"* —— 本项目对应"用户只说'运费多少'但没说航线"。

#### 6.1.1 用蜕变测试扩展覆盖（第 86 行）

不必为每个变体准备唯一答案，而是规定**输入变化前后应保持的关系**：

- 加入一段无关上下文 → 结论不应改变
- 缺少目的港 → 应先追问，不应瞎猜
- 同一问题换同义问法 → Outcome 应一致
- 请求越权数据 → 必须拒绝

#### 6.1.2 保留集纪律（第 88 行）

> *"扩展出来的样本还要留一部分作为保留集，**不参与 Prompt 调整、示例选择和规则调参**。否则团队会逐渐记住已有 Case，却不知道系统对新表达、新上下文和新故障是否仍然有效。"*

**这条纪律本身也是工程成熟度的体现** —— 说明团队理解过拟合评测集的风险。

#### 6.1.3 Golden Set 不是一次性资产（第 110–116 行）

三个维护动作：覆盖度复查、失败样本回流、**版本记录**（Golden Set / 模型版本 / Prompt 版本一起保存，否则跨版本对比失真）。

### 6.2 评测指标

#### 检索侧 + 生成侧**必须分段**（`RAG 优化` 第 21、218 行暗示，`AI 应用评测体系` 明确）

|---|---|---|

⚠️ **第 196 行的重要警告**：

## 七、Trace 可观测性（★★★ 第二差异化）

### 7.1 基础 ID 体系（`AI 可观测性与 Trace` 第 52 行）

```
sessionId：串起同一段多轮会话
runId：串起一次任务，包括暂停和恢复后的执行
traceId：标识一次实际执行产生的调用链
spanId：标识调用链中的某个操作
attempt：标识同一步骤的第几次尝试
```

### 7.2 本项目 Span 设计

框架自动埋点覆盖 AI 基础组件，**业务编排要自己补**（第 436 行）。本项目：

```
ai.agent.run                        ← 根 Span
├── ai.intent.route                 ← 意图路由（记录 route_reason）
├── ai.structured.query             ← 结构化通道
│   ├── ai.tool.param.extract       ← 参数抽取
│   ├── ai.tool.param.validate      ← 参数校验
│   └── db.sql.execute              ← SQL 执行（记录耗时、行数）
├── ai.rag.retrieve                 ← 文档通道
│   ├── ai.rag.rewrite              ← Query Rewrite
│   ├── ai.rag.hybrid               ← BM25 + 向量 + RRF
│   │   ├── db.vector.search
│   │   └── db.bm25.search
│   ├── ai.rag.rerank               ← 重排前后顺序对比
│   └── ai.rag.context.build        ← 上下文裁剪
├── ai.fee.calculate                ← 确定性计算
├── ai.llm.generate                 ← 模型调用
└── ai.output.validate              ← 输出校验
```

### 7.3 基数（cardinality）纪律（第 202、448 行）

> *"Spring AI 的观测设计也采用了类似原则：**低基数键会进入 Metrics 和 Trace，高基数键只进入 Trace**。"*

- **低基数**（进 Metrics）：`ai.rag.strategy`、`ai.rag.result`（`hit`/`empty`）、`ai.intent.type`
- **高基数**（只进 Trace）：`knowledge_base_id`、`result_count`、文档 ID

第 451 行提醒：**不要把原始查询和文档正文直接设为默认 Tag**。

### 7.4 接入方式

- Spring Boot 4 用 `spring-boot-starter-opentelemetry`，OTLP 发到 Collector（第 424 行）
- 业务 Span 用 **Micrometer Observation API**（第 448 行有完整 `RagObservationService` 示例代码）或 `@WithSpan`（第 453 行）
- ⚠️ 第 459 行：**不要同一个操作既用 Micrometer Observation 又手工建 OpenTelemetry Span**，会出现重复节点
- 采样：默认 `probability: 0.1`；开发环境临时改 `1.0`（第 430 行）
- **内容记录开关默认全部关闭**，按数据等级逐项开启（第 432 行）

   本项目主打 SSE 流式 → **一定会遇到这个**。提前知道并写进 README，即为"已识别框架限制并理解其成因"。

2. **`@SpringBootTest` 不自动配置上报组件**（第 484 行）：
   > *"测试环境看不到导出结果时，先确认是否显式配置了上报组件，不要直接把它判断为上下文传播问题。"*

### 7.6 验证清单（第 474–482 行）

至少准备 8 个集成测试场景（正常问答、模型超时重试、工具业务失败、并行执行、流式响应、HTTP/消息队列下游、Agent 暂停恢复、敏感信息）。验证点包括父子关系、每次重试独立 Attempt、错误状态、Token/模型版本/文档 ID 可查、跨线程 `traceId` 一致、敏感字段脱敏。

### 7.7 badcase 定位速查

## 九、设计问答（自检清单）

以下问题用于检验设计是否真正想清楚。**建议在第 4 周评测完成后逐条自答并写入《评测报告》附录**，作为设计决策的论证记录。

### 9.1 核心设计论证

1. **怎么证明混合检索比纯向量好？**
   → 消融实验数据（见 §6.3），不接受主观判断。

2. **结构化查询为什么不让模型直接生成 SQL？**
   → 安全性与正确性优先。契约化受控查询把参数空间前移到 JSON Schema，规避注入与越权；自由生成 SQL 属阶段二加分项。

3. **费用计算为什么不让模型算？**
   → 不信任模型算术。模型只做参数抽取，金额由 SQL 聚合 + 确定性代码计算。

4. **Golden Set 怎么防止过拟合？**
   → 保留集纪律（`AI 应用评测体系` 第 88 行）+ 版本记录（Golden Set / 模型 / Prompt 三者绑定）。

5. **LLM Judge 用在哪里、不用在哪里？**
   → 客观正确性给证据（SQL 执行结果做 oracle），主观质量才给 Judge（第 196–198 行）。

6. **知识库更新时向量库和业务库不一致怎么办？**
   → 元数据库为 source of truth + `index_status` 状态机 + 补偿任务（`RAG 知识库文档如何更新` 第 83 行）。

7. **为什么现阶段不做 GraphRAG？**
   → 遵循 `GraphRAG` 第 89 行判据：先用评测确认失败类型。若 badcase 明确指向多跳关系/跨文档归纳，再引入图结构；否则向量 + 混合检索 + rerank 更划算。

8. **Trace 里怎么区分低基数和高基数字段？**
   → 低基数进 Metrics，高基数只进 Trace，原始查询与文档正文不入默认 Tag（`AI 可观测性与 Trace` 第 202、451 行）。
