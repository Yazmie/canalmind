## 四、口径与限制（如实声明）

1. **准确率只覆盖 L1**（结构化可答）。L2 见 `检索段-纯向量基线.md`；L3/L4/L5/L6 本轮只建数据集与金标准（决策 C-34 / C-35），**没有编造它们的分数**。
2. **L1 的追问/拒绝/降级计入分母、算作错**，但**单独归类**（「该答却追问」「降级未作答」与「答错（数值不符）」分开）。⚠️ 判据在 2026-09-22 被**修正过一次**：初版把 L1 的追问也排除出分母，那会把「抽取漏掉参数」这个真实缺陷洗成「不参与评分」；C-35 的「缺参按是否追问判」针对的是**题面真的缺参数**的那类题（L6），不是 L1。
3. 判分脚本 `backend/scripts/eval_execution_accuracy.py` 是**唯一判据实现**；取数驱动 `ExecutionAccuracyRunTest` 只负责跑与落盘，不判分（避免两套判据漂移）。判分器自身先过 `--selftest`（用金标准反向伪造结果并注入 4 类已知错误，验证它真的会拦）。
4. 保留集（holdout）**不参与任何调整**：本报告同时给出 dev 与 holdout 两个数，调 Prompt/契约只许看 dev。

## 五、怎么读这个数（诚实说明）

本轮 EA = **100.0%**（dev 32/32，holdout 8/8）。这个数**偏高，且偏高的原因是可知的**，不要把它读成「端到端准确率」：

1. **题面是我自己写的、而且把参数写全了**（费种、货类或货种、吨位、业务日期都在句子里）。真实用户口吻会省略、会含混、会一次问两件事，那属于 L4/L5 要测的东西，本轮**没测**。
2. **覆盖窄**：只有 40 题、5 个费种、7 个货类；且**84 个费率档位里有 18 个在仿真数据中不可达**（见 `进度看板.md` §0.2），L1 里不可能出现那些档。
3. **金标准与实现读的是同一张表**：它验证的是「链路与口径是否一致」（SQL 侧独立算一遍、Java 引擎再算一遍、两边到分相等），**不验证数据本身的正确性**——后者由 C-31 的跨源逐格校验负责。
4. **判据不含表述质量**：只比数值/结果集，不过 LLM 判分（D14 仍未决），故「答对了但话说得别扭」不扣分。
5. **本轮对实现只做了一处修改**：`categoryOf()` 漏了「只给货种」这条入口（属实现缺陷修复，**不是**按 dev 集调参；Prompt 上加过一条说明但**对结果没有影响**，因为真正的病根在服务端）。dev 与 holdout 同为满分，**没有任何一条题是按分数挑出来的**。
