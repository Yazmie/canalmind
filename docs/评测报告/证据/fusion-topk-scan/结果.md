# `fusionTopK` × `recallTopK` 独立扫描（零付费、dev 32 条）

**日期**：2026-09-22 ｜ **执行**：本次会话（DSH 子代理）
**问题**：`fusionTopK`（成本旋钮：决定送进重排提示词的候选数）能压到多低而不损失检索指标？
它与 `recallTopK` **是否必须同值**？

**边界**：全部 `--no-rerank`（⛔ 不启用重排、⛔ 不给任何模型 API 发请求；唯一模型调用是本机
Ollama `bge-m3` 嵌入）｜ 只用 `l2-queries-v2-dev.txt`（**dev 32 条**，已实测校验只含 dev）
｜ ⛔ 未读、未用保留集 ｜ 未改 `backend/src`、未改 `pom.xml`、未做任何 git 操作。
产物全部在 `backend/target/eval/fusion-topk-scan/`（该目录被 `.gitignore` 忽略）。

## 1. 结论（先说答案）

1. **`fusionTopK` 在 dev 32 条上找不到断点。** 实测 `fusionTopK ∈ {1, 2, 3, 5, 10, 20, 30, 50, 100}`
   （固定 `recallTopK=50`），**每一个可比截断位上的指标都逐位相同**；更强的是
   **逐题比较 chunkId 序列，所有可比前缀 0/32 题不同**（见 §3 `prefix-identity.txt`）。
   ⇒ 从 **30 压到 10**（乃至 1）在**无重排档的检索指标上零损失**。
2. **`fusionTopK` 与 `recallTopK` 不必同值。** 实测 `recallTopK=50` / `fusionTopK=1`
   （相差 50 倍）与 `fusionTopK=100` 的前缀完全一致。⇒ **"同值"从来不是要求**。
3. **但两者之间存在硬性结构耦合，且不是"同值"那种耦合**：
   - `contextTopN ≤ fusionTopK`（关重排时，`RetrievalConfig` 第 97–107 行强制）⇒
     **`fusionTopK < k` 时连 `@k` 都算不出来**（产物池深不足）。
   - `fusionTopK` 至多等于**该题两路候选的并集大小**（≤ 2×`recallTopK`，实测常明显更小）⇒
     实测 `recallTopK=20 + fusionTopK=30` **构造上就填不满 30 条**（每题 24~30 条），
     `recallTopK=10 + fusionTopK=30` 只有 12~19 条。两者都被 `eval_retrieval.py` **大声拒绝**
     （退出码 1，见 §4），**没有产生静默错数**。
4. **⚠️ 一句话不能外推**：`fusionTopK` 正是"送进重排的候选数"，而**重排那一路（付费）本轮没跑** ⇒
   "压到 10 不掉分"**只对无重排档的检索指标成立**，**不得**据此把冻结值改成 10。
   反证很具体：`L2-034` 的 gold 在 `recallTopK=30` 档排 **rank 12**、`recallTopK=20` 档排 **rank 9**、
   `recallTopK=50` 档排 **rank 7** —— 若同时把 `fusionTopK` 压到 10，**在 r30 档该 gold 根本不在重排候选里**，
   而看板 §3.6 记录重排恰恰把这题从 rank 12 提到 rank 3。

## 3. 为什么"断点不存在"这句话是可核对的（而不是"指标看着没掉"）

指标只在**截断位上**取值；"没掉"可能是"恰好落在临界点"。故做了更强的核对：
**逐题比较 chunkId 序列**（`compare_prefix.py` → `prefix-identity.txt`）：

```
── recallTopK=50：基线 = hits-r50-f100.json（声明 topK=30，每题最少 30 条）
   比较 hits-r50-f01.json(声明 topK=1，每题最少 1 条) vs 基线：深度 1，32 题中**不同 0 题**
   比较 hits-r50-f02.json(声明 topK=2，每题最少 2 条) vs 基线：深度 2，32 题中**不同 0 题**
   比较 hits-r50-f03.json(声明 topK=3，每题最少 3 条) vs 基线：深度 3，32 题中**不同 0 题**
   比较 hits-r50-f05.json(声明 topK=5，每题最少 5 条) vs 基线：深度 5，32 题中**不同 0 题**
   比较 hits-r50-f10.json(声明 topK=10，每题最少 10 条) vs 基线：深度 10，32 题中**不同 0 题**
   比较 hits-r50-f20.json(声明 topK=20，每题最少 20 条) vs 基线：深度 20，32 题中**不同 0 题**
   比较 hits-r50-f30.json(声明 topK=30，每题最少 30 条) vs 基线：深度 30，32 题中**不同 0 题**
   比较 hits-r50-f50.json(声明 topK=30，每题最少 30 条) vs 基线：深度 30，32 题中**不同 0 题**
```

⇒ **`fusionTopK` 从 100 压到 1，进上下文的候选序列逐位不变**（每一步都是"取更长排序列表的前缀"，
而 `fusionTopK` 只截断列表长度、**不改变次序**——这也解释了为什么指标必然不变）。

**`recallTopK` 则不是前缀关系**：它改变的是两路各自的名次 → 改变 RRF 分数 → 改变次序。
实测只有**两题**的首命中名次对 `recallTopK` 敏感（其余 30 题稳居 rank 1–4）：

| 配置 | `L2-016` gold rank | `L2-034` gold rank |
|---|---|---|
| r20 f30（topK 20） | 10 | 9 |
| r30 f30（topK 30） | 8 | **12** |
| r50 f30（topK 30） | 8 | 7 |

（取自各档 `metrics-*.json` 的 `scoreMarginAnalysis.detail`）
⇒ 这正是看板记的"`recallTopK` 30→50 只买到 1 条题"那条的逐题形态；且**两题在 r20 档都还在前 10**
⇒ **`recallTopK=20` 的 `HitRate@10` 反而是 1.0000、`recallTopK=30` 是 0.9688**——
这是 **1 题 = 1/32 = 0.03125** 的单题噪声，**不得**据此说"20 比 30 好"。

## 4. 结构性失败的两档（**原始报错照抄**）

这两档**不是"掉分"，是"构造上填不满"**：融合结果 = 两路候选的**去重并集**，
其大小 ≤ 2×`recallTopK`（实测明显更小），于是 `fusionTopK` 要不到那么多条，
产物"声明 `topK=30`、实际只写得出 24~30 条" ⇒ 评测入口按设计拒绝。

| 档 | CLI 退出码 | 产物每题实际条数 | `eval_retrieval.py` 退出码 | 原始报错（照抄） |
|---|---|---|---|---|
| `r10-f30`（`recallTopK=10`、`fusionTopK=30`、`--top-k 30`） | 0 | 12～19 | **1** | `[FAIL] 产物声明 topK=30，但每题实际命中条数为 12~19，二者不一致。` |
| `r20-f30`（`recallTopK=20`、`fusionTopK=30`、`--top-k 30`） | 0 | 24～30 | **1** | `[FAIL] 产物声明 topK=30，但每题实际命中条数为 24~30，二者不一致。` |

完整原始输出（含 PowerShell 包装的错误头与后两行提示）：
`eval-r10-f30-FAILED.txt`、`eval-r20-f30-topk30-FAILED.txt`。
两档的命中文件仍保留（`hits-r10-f30.json`、`hits-r20-f30.json`）作为现象证据，⛔ 但**不出分**。

**处置（按项目纪律，不改评测脚本、不放宽校验）**：`r20-f30` 改用**该档能填满的最深深度**
`--top-k 20` 重跑（`hits-r20-f30-t20.json`），跨臂比较只取**公共的 k ≤ 20**；
`r10-f30` 不重跑（没有可比的公共深度，`r10` 的信息已由 `recallTopK=20/30` 两档覆盖）。

> 这与看板 §8.3 记的既有现象同源（当时是把 `recallTopK` 设成 10/20 被拒），
> 本次是**在 `fusionTopK` 轴上把它再测了一遍**：**失败是响亮的，不是静默的**。
