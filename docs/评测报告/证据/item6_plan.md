# 第 6 项：三档 Top-K 调参 + 四路对照（设计与验收标准）

> 本文件是**执行前的设计稿**（随第 5 项交付而更新）。数字一律不在这里手写，只写"从哪里读"。

## 1. 要回答的问题（只回答这三个，不扩展）

1. **`recall_top_k` 取多少**：候选池要挖多深才够？（依据：`recall_depth.md` 的饱和点）
2. **`rerank_top_n` 取多少**：LLM 重排留几条，值不值得为更深的输入付 token 与延迟？
3. **`context_top_n` 取多少**：最终给生成模型看几条？（依据：各 k 处指标是否已饱和）

⚠️ **`rrf_k`（C-26 默认 60）本轮不动**：它是融合公式的常数，属另一个消融轴；本轮四路对照里固定 60，避免"一个网格里同时动两个轴"（`AGENTS.md` §6 第 2 条）。

## 2. 四路对照（同一评估集、同一 `recall_top_k`、同一 `fusion_top_k`）

| 路 | 命令要点 | 说明 |
|---|---|---|
| 纯向量 | `--channels vector --no-rerank` | 单通道基线；**必须与既有 `VectorQueryCli` 逐题逐名次一致**（等价性核对） |
| 纯 BM25 | `--channels bm25 --no-rerank` | C-25 通道第一次进入管线；回答 D3（是否启用混合检索）的一半 |
| RRF 融合 | `--channels vector,bm25 --no-rerank` | C-26 主实现 |
| RRF + LLM 重排 | `--channels vector,bm25`（不加 `--no-rerank`） | C-27 主实现；⚠️ 真发 40 次请求 |

## 3. ⚠️ 评估约定（三条硬约定，违反则数字不可比）

1. **"宽上下文评估档"**：产物的 `hits` 就是**最终上下文**（`hits = r.context()`），条数 = `--top-k`。
   要评估到 `@k`，必须 `--top-k >= k`。故四路统一用 `--top-k 30`，**这是为了把排序看到第 30 名**，
   ⛔ **不代表生产 `context_top_n` 是 30**；生产取值由第 1 节的第 3 问决定（取指标饱和点）。
2. **`--top-k` 必须 ≤ `--rerank-top-n`**（`RetrievalConfig` 校验）。故四路的 `--rerank-top-n` 一并给到 30，
   否则 rerank 那一路构造期就报错。
3. **重排那一档的深度由 `rerank_top_n` 决定**：若把 `rerank_top_n` 设成 10，则该档只能评估到 `@10`。
   跨路比较**必须在共同可比的 k 上做**（例如四路都在 `@5`/`@10` 比），
   而 `@20`/`@30` 只用于无重排的三路——**不得把不同深度的数字并排放进同一张表而不加注**。
   **✅ 本轮已用离线前置检查解除了这个限制**（见下），故四路可统一 `rerank_top_n=30`、在 `@30` 上全可比。

### 3.1 ✅ 重排档深度：离线前置检查（2026-09-21，**未花任何 API 费用**）

按 `backend/target/eval/item5/rrf.json` 的 30 条候选逐题估算提示词规模（候选行 = `chunkId` + 文档标题 + 条号 + 条标题 + 版本 + 400 字符片段，另加约 600 字符模板）：

| 量 | 实测/估算 |
|---|---|
| 候选数/题 | **30**（= `fusionTopK`） |
| 提示词字符数 | 最小 13 748 / 最大 13 885 / 平均 **13 804** |
| 输入 token（按中文 ≈0.7 token/字符估） | 约 **9 663/题**，40 题共约 **38.7 万** |
| 输出 token | 30 个 `chunk_id` 的排序 ≈ 600 字符 ≈ **420** |

**结论（含一处我先前判断错的更正）**：
- ⚠️ **我先前的担心搞错了方向**：我说过"30 条候选的提示词可能撞上 `maxTokens=4096`"——
  但 `max_tokens` 约束的是**输出（completion）**，而排序输出只有数百 token，
  **4096 绰绰有余**。故 `LlmRerankerFactory` 的 `maxTokens(4096)` **不需要改**，
  重排档可以直接按 `rerankTopN=30` 跑，四路在 `@30` 上全部可比。
- 输入约 1 万 token/题在 DeepSeek 上下文内；40 题一次跑完约 38.7 万输入 token
  （**成本量级在"一次可接受"的范围，但仍是付费调用，故只跑一次**）。
- ⚠️ **估算的已知偏差**：产物**不存片段文本**（只存 id/标题/条号/条标题/版本），
  故上面的字符数是按 `snippetChars=400` 的默认值推算的。**若重排实际取的片段更长，输入会更大**——
  验收时以 `LlmReranker` 真实发出的提示词为准（若它记录了长度），不要把这个估算当实测。

⚠️ **两条纪律**：
- **holdout 8 条不参与任何调参**（知识库《AI 应用评测体系》第 88 行；`AGENTS.md` §6 第 4 条）。
- **不得因单题定参**：`L2-034` 的 gold 排 rank 32 只说明"严格口径是下界"，**不是**把 `recall_top_k` 定成 40 的理由（它在可答口径下 rank 3 就命中）。

## 5. "哪一档更好"的判定标准（先写死，避免事后挪门槛）

- **主判据**：**严格族**在 dev 32 条上的 `HitRate@k` 与 `MRR@30`（只算 gold，读作下界）；
- **辅判据**：可答族 `answerableRate@k` / `answerableTop1`（含等价块）；**两族并列报告、不得混用**；
- **不判**：`Precision@k` 在 k 小于上下文深度时的绝对值（分母含"取多了"的惩罚，属另一问题）；
- **成本与延迟**：四路的**端到端耗时**必须记录（重排那路会显著变慢，这是取舍的一半）；
- **降级**：重排那路的 `rerankDegraded` / `degradedQueryCount` **必须是 0**；若有降级，该路结论**作废**并查原因
  （降级会让"重排没效果"与"重排没跑成"看起来一样）。
- ⚠️ **同分并列的敏感性**：本项目已有 4 条题的金榜分差在 0.01 以内（`L2-024` +0.00132 等），
  故"某一档多命中 1 条"**不构成结论**——结论必须由**多条题的一致方向**支撑，并写清样本量只有 32 条。
