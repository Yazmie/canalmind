## 为什么有这个目录

本项目大量结论（`rank 32`、候选池饱和点、空应答清零、L6 缺口实测…）**正文数字是入库的** ✓，
但它们的**原始证据**原本只存在于 `backend/target/eval/**`——那个目录被 `.gitignore` **整目录忽略**，
`mvn clean` 还会清空。⇒ **新 clone 的读者能读到结论，却点不开证据、只能先重跑**
（需要库 + Ollama + 541 块语料 + 分词档案，有些还要**付费调用**）。

本目录就是这些证据的**入库落点**，目的只有一个：**让读者能靠"读"完成核验**。

## 入库规则（⛔ 边界要清楚，否则仓库会膨胀）

| 类别 | 处置 | 理由 |
|---|---|---|
| **人写的 `.md` 结论文档** | ✅ **入库**（本目录） | 可读、可 diff、体积小（**8 份合计仅 133 KB**）；结论的唯一书面载体 |
| **原始机器产物**：`.json`（**41 MB**，多为 `hits` 大文件）、`.txt` 运行日志（4 MB）、`.class`/`.log`/`.pyc` | ⛔ **不入库** | 体积大、可由**已文档化的命令**重跑；且多为中间产物 |

**判据是"能否靠读完成核验"，不是"文件重要不重要"。** 一份 1.5 MB 的 `hits.json` 再重要，
也不如它旁边那份人写的结论文档有用——后者把"从这堆 hits 里读出了什么"固定下来了。

## ⚠️ 本目录是**快照**，不是工作目录

- 这里的文件是 `backend/target/eval/**` 对应文件的**逐字节副本**（2026-09-23 复制时已用
  **SHA256 复核 IDENTICAL**）。
- **工作副本仍留在 `backend/target/eval/**`**（不入库、`mvn clean` 会清掉）——
  两者**不自动同步**；若重跑后工作副本变了，**必须重新复制并复核哈希**。
- ⚠️ **今后新增"人写的证据文档"直接写在本目录**（要入库），机器产物仍留在 `backend/target/eval/**`。
  这是 **C-64** 的落地约定。
