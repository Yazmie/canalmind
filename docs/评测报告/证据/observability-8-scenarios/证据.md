## 二、逐场景：断言什么 / 用哪条测试方法 / 实测结果

### ① 正常的 RAG 问答

- **断言什么**：`ai.agent.run` 是根（父为 null）；`ai.intent.route`、`ai.rag.retrieve` 都挂它下面；检索段的 3 个子步骤（`db.vector.search` / `ai.rag.hybrid` / `ai.rag.context.build`）都挂检索段下面；`ai.llm.generate` 的父是谁（实测）；除根外每个 Span 都有父且父也在本次记录里；所有 Span 名 ∈ §7.2 的 16 个登记名。
- **测试方法**：`ObservabilityEightScenariosTest#scenario1NormalRagQuestionKeepsRetrievalAndGenerationInOneChain`
- **实测结果**（完整 Span 树，直接取自断言失败消息/记录器）：

```
ai.agent.run                     parent=null                attrs={ai.intent.type=RETRIEVAL}
├─ ai.intent.route               parent=ai.agent.run        attrs={ai.intent.type=RETRIEVAL, ai.config.version=R2-规则话题-检索}
├─ ai.rag.retrieve               parent=ai.agent.run        attrs={ai.rag.result=hit, ai.rag.strategy=vector, ai.rag.result_count=2, knowledge_base_id=canalmind-rules}
│  ├─ db.vector.search           parent=ai.rag.retrieve     attrs={ai.rag.result_count=2}
│  ├─ ai.rag.hybrid              parent=ai.rag.retrieve     attrs={ai.rag.strategy=rrf, ai.rag.result_count=2}
│  └─ ai.rag.context.build       parent=ai.rag.retrieve     attrs={ai.rag.document_ids=c1,c2, ai.rag.result_count=2}
└─ ai.llm.generate               parent=ai.agent.run        attrs={ai.config.version=v1, attempt=1}
```

- ⚠️ **如实记的差异**：**生成段挂在根下，不是挂在检索段下**（两者是兄弟）。含义：Trace 上能看出「先检索、后生成」的**时间先后**，却看不出「这一次生成用的是**哪一次**检索的结果」。知识库第 476 行要求核对「父子关系是否正确」——这条差异已在此留档；本任务只许改 `test/**` ⇒ **不改生产代码**。测试里那条断言写的是**实测值**，并在失败消息里写明「若将来把生成嵌进检索段，断言会变红，届时改成 `ai.rag.retrieve`」。

### ② 模型超时后重试

- **断言什么**：抽取层拿到「不可用的应答」后重试时，**每次尝试各建一个 Span**（不是把重试合并进同一条记录）；`attempt` 从 1 起逐次递增；两次尝试**互为兄弟**（同一父）；每次尝试都走一遍 `ai.tool.param.validate`。
- **测试方法**：`ObservabilityEightScenariosTest#scenario2EachRetryGetsItsOwnAttemptSpan`
- **实测结果**：`ai.tool.param.extract` 恰好 **2** 条，`attempt` = `1`、`2`，两次的父相同（兄弟），`ai.tool.param.validate` ≥ 2 条 ✅
- ⚠️ **如实记的现状**：本项目**只有抽取层这一处**会为每次重试新建 Span；`LlmCallGuard`（C-58）的退避重试**不产生独立 Attempt Span**。依据：读 `LlmCallGuard` 与其 17 个测试（`LlmCallGuardTest`）+ 本测试只做 `contains` 记录，**未**为它新增断言 ⇒ 见第五节第 6 条（依据薄弱项）。

### ③ 工具返回业务失败

- **断言什么**：工具返回**业务失败**时——`ToolResult.ok()` 为 false；**没有任何 Span 被记成错误**（业务失败 ≠ 技术错误）；根 Span 上 `ai.rag.fallback` 的真实取值；`answer.retrievalFallback()` 的真实取值；路由仍留在结构化通道。
- **测试方法**：`ObservabilityEightScenariosTest#scenario3ToolBusinessFailureIsNotASpanError`（抽取永远回非 JSON ⇒ 重试用尽）
- **实测结果**：
  - `answer.tool().ok()` = **false** ✅；`rec.errors()` **为空** ✅（业务失败没有被记成技术错误）
  - 根 Span 上 `ai.rag.fallback` = **null** ⛔；`answer.retrievalFallback()` = **false**；`route().channel()` = `STRUCTURED`
  - ⇒ **这次业务失败在 Trace 上一个键都没留下**（知识库第 478 行「错误状态、业务结果是否准确」在这条路径上**未达成**）
- **对照用例**：`ObservabilityEightScenariosTest#scenario3bToolNoneBusinessFailureDoesFallBackAndLeavesAKey`
  - 实测：`TOOL_NONE` 型业务失败**会**回退检索，根 Span 上 `ai.rag.fallback=true` ✅，且无 Span 记错误 ✅
  - ⇒ 两种业务失败在 Trace 上的可区分标志**只有** `ai.rag.fallback` 这一个键；§7.3 白名单里**没有**任何键能承载 `ToolResult` 的业务状态（`NO_DATA`/`REJECTED`/`DEGRADED`…）

### ④ 线程池 / 虚拟线程并行

- **断言什么**：把子 Span 丢进 `ForkJoinPool.commonPool()` 执行后——子 Span **确实产生了**（先证伪「压根没 Span」），其**父指针为 null**；并**在运行时真查类路径**是否存在 tracing 桥（决定本项目有没有 traceId 可言）。
- **测试方法**：`ObservabilityEightScenariosTest#scenario4CommonPoolLosesTheParentButKeepsTheSpan`
- **实测结果**：子 Span 存在、父指针 = **null**（与既有 `AiObservationThreadPropagationTest#commonPoolLosesTheParent` 一致）；`classpathHasTracingBridge()` = **false**（运行时扫 `java.class.path`，未命中 `micrometer-tracing` / `opentelemetry`）
- **命令侧旁证**（110 → 124 个 jar 的类路径快照）：`target/cp.txt` 里 `micrometer-observation-1.15.7.jar`、`micrometer-core-1.15.7.jar` 存在，`micrometer-tracing*` 与 `opentelemetry*` **无**。
- ⛔ **因此知识库第 480 行「跨线程和跨服务以后 `traceId` 是否一致」在本项目无法断言**——不存在 `traceId` 这个量；本项目用**自写导出器的 Span 树**（C-54）代替。测试里那条断言写成「类路径无 tracing 桥」的**反面判据**：一旦有人接入 tracing，它会变红，强制复核。

### ⑥ 通过 HTTP 调用下游

- **断言什么**：跨进程 HTTP 调用**确实发生**（桩服务器收到请求、路径正确）；请求带的是桩密钥（⛔ 绝不接触真实中转）；出站 `Accept` 的真实取值；请求头里 `traceparent` 的真实取值。
- **测试方法**：`ObservabilityStreamingAndDownstreamTest#scenario6DownstreamCallHappensButNoTraceContextIsPropagated`
- **实测结果**：
  - 桩收到请求，路径 = `/chat/completions` ✅
  - `Authorization` = `Bearer stub-key-for-test` ✅（本地桩密钥，零付费）
  - `Accept` = **`*/*`** ⚠️（**不是** `text/event-stream`；流式靠**响应头** `Content-Type` 判定）
  - `traceparent` = **null**（无该请求头）⛔
- ⛔ **「跨服务 `traceId` 一致」在本项目无法断言**：类路径上没有 tracing 桥（见 ④）⇒ 没有 `traceId`、也没有 `traceparent`。测试里那条断言是**现状判据**：一旦接入 tracing 就会变红，强制复核。
- ⚠️ 知识库第 470 行是「通过 HTTP **或消息队列**调用下游」：本项目**没有 MQ**（C-12 无 Docker、未引入消息队列）⇒ **只覆盖了 HTTP 这一半**。

### ⑦ Agent 暂停后恢复

- **断言什么**：⚠️ 本项目**没有 Agent**，所以断言的是**映射**（多轮会话续接）的三件事：①上一轮的问答确实存进了会话状态（续接的事实基础）；②第二轮**每轮各起一棵树**（根恰好 1 个，既不缺也不泄漏）；③全部 Span 名 ∈ §7.2 的 16 个登记名，且**不存在**任何名字含 `resume` / `pause` / `session` 的节点。
- **测试方法**：`ObservabilityEightScenariosTest#scenario7MultiTurnContinuationIsANewTreeNotAResume`
- **实测结果**：会话状态里上一轮问题文本在 ✅；第二轮根 Span 恰好 **1** 个 ✅；Span 名全部来自 §7.2 ✅；无 `resume`/`pause`/`session` 名字 ✅
- ⛔ **这是映射，不是 Agent 挂起**：第 ③ 条断言的作用是**防止有人为了凑场景而造一个恒不触发的假节点**（同 `ai.output.validate` 按 **D23** 挂起的处置）。本项目没有 Agent，因此**不存在**「暂停/恢复」这个环节——按用户要求**如实标注为映射**，⛔ 不造假的挂起节点。

### ⑧ Prompt / 工具结果含敏感信息

- **断言什么**：把密钥串塞进**问句**（最容易被顺手写进属性的路径）后——导出产物里**不含**密钥串、**不含**问句原文、**不含**问句的任何片段；导出产物里的**全部属性键**都在 §7.3 白名单内（外加 Micrometer 自带的 `error.type`）；且白名单键**确实出现了**（防止「只含白名单键」因为产物里没有键而假绿）。
- **测试方法**：`ObservabilityEightScenariosTest#scenario8SensitiveInputNeverReachesExportedAttributes`
- **实测结果**：密钥串 `sk-live-SECRET-…` 未出现 ✅；问句片段未出现 ✅；属性键 ⊆ 白名单 ✅；白名单键非空 ✅
